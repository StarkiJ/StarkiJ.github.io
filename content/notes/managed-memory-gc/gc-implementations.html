OOM、内存观察与排查

Java OutOfMemoryError是运行时无法满足相应分配请求的错误；Linux/Android 因全局或进程内存压力终止进程，是另一条路径。抛 OOM 不等于在该指令处必定立刻被系统杀死，但捕获异常也不自动恢复可用内存或业务状态。

区分泄漏、峰值与容量不足

托管对象泄漏通常是“业务已经不需要，引用链仍让它可达”。例如长寿缓存一直保留请求结果，或异步任务一直持有已退出的页面。GC 正确地保留了可达对象，问题在持有关系；这与 native 中丢失指针却未释放存储的泄漏表现不同。

  1. 先确认是 Java 堆分配失败、native 分配失败、地址空间/碎片问题，还是系统杀进程；保留日志和构建信息。
  2. 记录失败申请大小、存活量、堆目标/上限、GC 前后变化及进程内存分类。
  3. 对比多轮相同业务的 heap dump，沿 GC Roots 引用链查不必要的持有；native 增长另查分配调用栈。
  4. 应用侧减少峰值同时存活数据、按需加载、缩小图片/缓存、及时取消任务；修复引用链后用同负载复测。

若相同业务往返后，回收后的存活量持续上升，优先查长期持有；若只有并发峰值时分配失败、峰值后能恢复，优先查同时存活的数据规模；若稳定负载始终超过容量，再评估资源预算。单次占用高不能独自证明泄漏，回收前后采样也要保证口径可比。

HPROF 是堆转储格式之一，可用于分析托管对象和引用。dump 本身有开销，且不覆盖所有 native、映射或图形资源；“Java 堆不涨”不能排除进程内存问题。

扩堆是否一定减少 OOM？

扩大堆可能延后容量上限，仍需检查泄漏、同时存活数据和系统内存压力；更大的活对象集合也可能增加扫描与复制工作。

参考：JDK 21 诊断工具 · NMT · Android meminfo · heapprofd · 退出原因。

从大小排名走到支配关系

Shallow size是对象自身占用；retained size是在相应引用处理规则下，该对象不可达时可随之变得不可达的对象集合大小。一个很小的容器可能保留大量数组，而一个大数组未必能因删除某一条引用就回收。

若从根到 Y 的所有保留路径都经过 X，则 X 支配 Y。堆分析的 dominator tree 用于汇总保留关系，但树边不一定是原始对象的直接字段引用；它也不是编译器 CFG 的支配树，虽然用到了相似的图论定义。

根 → Cache → Entry → byte[]
若数组只有这条保留路径，Cache 可支配数组。

另一个根 → Worker ─────────→ byte[]
加入这条路径后，移除 Cache 仍不能使数组不可达。

先用数量 / retained size 排名选候选，再查看通向根的真实引用路径与业务生命周期。分析器是否排除弱 / 软引用、dump 采集时机和活对象处理方式都会影响解释，不能把对象浅大小相加就当成进程 RSS。

从一条持有链定位到创建与清理代码

示意 heap dump 中的一条强保留路径：
GC Root（已加载类的静态字段）
  → Registry.listeners
  → ArrayList.elementData[i]
  → PageListener.owner
  → 已退出的 Page
  → imageBytes

业务代码的可疑对应关系：
enter()：创建 listener，注册进全局 Registry
exit() ：停止显示页面，却没有注销同一个 listener

先确认 Page 在业务上已结束，再查 owner 字段赋值处、listener 的创建和注册调用栈，以及退出、取消和异常分支的清理代码。heap dump 展示采样时的对象图，通常不能单独还原历史分配调用栈；需要分配记录、日志或可重复调试补齐“何时、由谁创建”。

修复应让拥有注册关系的组件在适当生命周期释放它，例如保存注册句柄并在退出时关闭，处理重复注册、异常和仍在执行的回调。仅把某个局部变量设为 null，不能解除 Registry 中的强引用；直接改成弱引用也可能让本该存活的回调过早消失。

复测使用相同次数的进入 / 退出，等待任务取消与清理完成，在可比采样条件下比较已退出页面数量、根路径和回收后存活量。若仍有第二条路径保留 Page，解除第一条路径不等于问题已经解决。

两个增长案例：长期持有与并发峰值

以下是排查示意，不是实测数据。案例一：每次进入页面注册 listener，退出后忘记从长寿 Registry 移除；listener 捕获页面，页面保留图像缓冲。重复相同进出操作后，观察回收后的页面数量和保留量，沿 Registry → listener → page 取证。修复注册 / 注销与取消协议后，重复同样负载，并给异步清理足够的完成条件；只有内存下降而没有确认这条关系被解除，还不足以证明原因。

案例二：多个请求同时解码大图，处理结束后存活量能回到基线，但并发时分配失败。记录同时存活任务数、输入尺寸、失败申请与 GC 后可用量，检查是否是容量或连续空间压力。通过限制并发、分块处理或减少解码尺寸降低峰值，再检查延迟与吞吐代价。此时仅寻找永久持有链可能查错方向。

若托管堆稳定而 RSS 增长，转看 native 分配、映射、图形资源或分配器保留，不应强行套入上面两个 Java 堆案例。

参考：MAT：Shallow / Retained Heap · MAT：Dominator Tree。

GC 与编译器、ABI 的协作

要点回顾：三色标记用白、灰、黑表达发现和扫描状态，颜色不等于对象当前是否可达。应用修改引用，既可能让尚需保留的对象逃过扫描，也可能让本轮已保留的对象变成浮动垃圾；前者必须由正确的标记协议防止，后者可留待后续收集。STW 阻止应用在协调窗口内修改对象图，并发阶段则依靠相应屏障与根处理协议。移动对象后，G1 在疏散暂停中更新引用，ZGC / ART CC 则使用各自的读屏障等机制协调并发访问；不能把读屏障视为所有移动 GC 的共同步骤。

复习问题：GC 为什么需要编译器和 ABI 配合？

GC 需要知道机器状态里哪些值是引用；编译器生成安全点信息并插入所选收集器需要的屏障，调用约定又规定值如何跨调用保存。异常展开需要恢复上一帧，但 DWARF CFI 描述恢复规则，OopMap 描述对象引用位置，二者不是同一份信息。

复习问题：malloc 的指针为什么通常不能这样搬？

普通 native 调用者可以复制、隐藏裸指针，分配器没有完整根集合和编译器屏障协作，不能擅自移动已交付的活块。realloc 可以返回新地址，但必须由调用者更新使用方式；详见malloc 专题。

复习时画出漏标交错、浮动垃圾的时间顺序与旧新地址映射；比较收集器时，分别看暂停阶段、并发工作、屏障开销和迁移所需空间。
