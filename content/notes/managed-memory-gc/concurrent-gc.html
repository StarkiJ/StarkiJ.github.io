二、并发标记与对象移动

本部分以前一部分的根、回收范围和记忆集为基础；先明确回收要维护的关系，再看并发修改与对象移动。

应用修改引用图、GC 标记和对象搬迁可能交错发生。下面分别讨论保持可达性、取得可靠根集合、访问正确对象和发布唯一副本的条件；HotSpot 的实现示例随对应机制说明。

7. 三色标记与并发漏标

颜色记录扫描进度，不是对象当前的生死

三色是逻辑状态，不要求对象头真有三个颜色值。白色表示尚未发现；灰色表示已发现但引用尚未扫描完；黑色表示已扫描完。可用标记位图和工作队列表达：已标记但仍待扫描的是灰色，已处理的是黑色。

初始化：对象视为白；从根发现的对象染灰、入队
循环：取一个灰对象，发现其白色后继并染灰、入队
      扫描完该对象后，将它视为黑色
终止：工作队列及线程缓冲中的待处理工作均已收敛
回收：本轮收集范围内仍白、且无特殊保留规则的对象

在图不变化的模型中，从根可达的节点会逐步被发现。强三色不变量是不存在黑对象直接指向白对象的边；白对象仍可由灰色前沿保护。下面的并发交错会破坏这一保证：

初态：根 → A（黑），根 → B（灰），B.ref → C（白）
应用：A.ref = B.ref    // 新增 A（黑）→ C（白）
应用：B.ref = null     // 删除灰色前沿通向 C 的最后一条路径
GC：  扫描 B，只看到 null；不会重扫已黑的 A
结果：C 仍白，却能从根经 A 到达，若回收便发生漏标

这是没有相应屏障保护、黑对象不再重扫的模型。关键是两个变化组合：黑到白的新边出现，且灰色前沿发现该白对象的路径被切断。仅出现一条黑到白的边不一定漏标；若 C 仍能被其他待扫描路径发现，就可能被保住。不同并发算法维护的不变量不同，SATB 也不要求始终没有黑到白边。

复习问题：如何修复上面的交错？

可暂停应用，固定引用图后扫描；也可在引用修改时记录必要信息，让并发标记恢复发现 C 的能力。必须连同根变化、分配期间的新对象和终止协议一起处理，不能只说“多加一个标记位”。

参考：Dijkstra 等：并发垃圾收集与颜色不变量。

浮动垃圾：对象后来不可达，本轮仍然保留

浮动垃圾指并发回收期间已经变得不可达，却仍按本轮存活信息保留、未在本轮回收的对象。原因在于应用继续修改引用，而本轮标记并不持续撤销已建立的存活判断。标记对象时它完全可能仍然可达，因此不能把原因概括为“GC 标错了”或“多标导致对象变成垃圾”。

假设 A.ref 是通向 B 的唯一强可达路径，且无特殊保留规则：
t0：根 → A → B，B 可达
t1：GC 已发现并扫描 B，B 为黑色；此时的标记正确
t2：应用令 A.ref = null，且没有其他根或引用保留 B；B 变得不可达
t3：本轮仍保留 B 的存活标记，不回收它；B 成为浮动垃圾
后续：覆盖 B 所在范围、重新判定可达性的收集才有机会回收它

若把本轮保留集合与回收结束时的实际可达集合比较，可把多保留的部分称作“多标”，但这是结果描述，不是浮动垃圾的独立成因。漏标则是仍需保留的活对象没有被正确保护；若因此回收，会破坏内存安全。浮动垃圾也不同于“业务不用、却一直被强引用链保留”的托管内存泄漏。

SATB 会保留标记开始时可达、随后失去引用的对象，即使它在失去引用前还没来得及被扫描。浮动垃圾也并非 SATB 独有：采用增量更新的 CMS 同样可能保留已标记、后来不可达的对象。不能仅靠更换这两种屏障策略就保证本轮回收所有新产生的垃圾。

参考：Oracle：CMS 的浮动垃圾与增量更新 · JDK 21 G1：SATB 保留起始存活对象。

8. STW、安全点与根扫描

STW（Stop-The-World）表示在一段协调窗口内暂停执行应用托管代码的线程；GC 工作线程仍可并行执行。并行描述多个工作线程一起做事，并发描述 GC 与应用的执行在时间上重叠。并行 GC 完全可能处于 STW。

HotSpot 在安全点等受控状态获取可靠的机器状态。编译代码的 OopMap描述特定程序位置的哪些寄存器或栈槽保存对象引用；不是把所有像地址的整数都当成对象。暂停请求到达后，各线程还要到达或被判定处于安全状态，因此“请求暂停”不等于“立即开始 GC 工作”。native 线程可以通过线程状态协议被视为安全，但返回托管执行前仍要遵守协调规则。

教材中的安全区域（Safe Region）可理解为一段无需继续执行托管代码、其引用状态仍可按协议处理的区间。阻塞或 sleep 线程不会因为没有抵达下一个轮询点就必然阻止 GC；关键是运行时能确认它的状态，并在重新进入托管执行前完成协调。不能把所有 JNI 调用都当成无需约束的安全区；ART 的线程根切换实例见ConcurrentCopying。

STW 可用于建立根快照、完成标记收敛或切换关键阶段；具体工作随收集器变化。G1 有并发标记，但 Young / Mixed 的疏散复制与引用更新在暂停中进行，Remark 也需要暂停。不能把“有并发标记”推导为“对象搬迁同样并发”。

观察一次延迟时分开看：
到达安全状态所需时间 → 安全点内的 GC / VM 操作时间 → 恢复应用
另看整轮 GC 墙钟时间、累计 CPU、分配停顿与应用尾延迟
复习问题：有读屏障是否就能完全消除 STW？

不能据此保证。读屏障主要让应用安全地使用引用，根处理、阶段切换和工作收敛仍需要协议。有些工作能改成并发扫描或线程握手，但必须说明具体收集器和版本；更短暂停也可能付出屏障、CPU 和预留空间成本。

参考：JDK 21 G1：并发标记与暂停疏散。

9. 写屏障、读屏障与引用协作

屏障解决的不同问题
机制记录或检查什么在漏标例子中的作用
SATB（起始快照）写前屏障覆盖引用前，记录旧引用；标记线程处理缓冲覆盖 B.ref 前保留 C，使起始快照中的存活关系仍可被追踪
增量更新写屏障关注新边，可把新目标染灰或让源对象重扫，具体条件依算法建立 A.ref → C 时保护 C，维护相应标记不变量
卡表 / remembered set 屏障记录可能产生跨代、跨区域引用的槽或粗粒度区域局部收集时能找到收集范围外指向范围内的引用
GC 读 / load 屏障读取引用后、使用对象前检查引用是否需要处理并发移动期间把旧引用解析到当前可访问对象；有的设计还承担标记

SATB 的逻辑是保存标记起始时的可达快照，实际可保守地多留对象；它不要求任何时刻都严格满足“没有黑到白边”。本轮开始后分配的对象也有专门保护规则。卡表屏障与 SATB 屏障可以出现在同一次写入周围，但服务于不同目的。

写引用(slot, new):                   // SATB 概念伪代码
    old = *slot
    若本轮标记需要：把 old 记入线程缓冲
    *slot = new
    若需跨区域追踪：记录 slot 所在区域

读引用(slot):                        // 并发移动的概念伪代码
    old = *slot
    若 old 为空或状态已满足要求：返回可用引用
    current = 运行时解析或协助迁移(old)
    尝试有条件地将 slot 中的 old 修复为 current
    返回 current

上述仅表达职责，省略内存序、标记队列并发、弱引用、阶段状态和机器码优化，不能直接实现为普通 C++ 并发读写。修复槽通常需要比较交换等协议，避免把应用同时写入的新值覆盖掉。快速路径让多数正常引用低成本通过；慢路径才处理需要修复的情况。

读屏障不是所有移动 GC 的必需配置。例如 G1 在疏散暂停中移动对象并更新引用，应用恢复后使用已更新的引用；ZGC、ART CC 则通过各自的屏障和阶段协议，让应用与对象移动并发执行。上面的读引用伪代码只表达某类并发移动方案，不能套到所有收集器。

GC 屏障与 CPU 内存屏障不同。前者维护对象图或引用有效性；后者约束内存访问排序和可见性。GC 屏障内部可能使用原子操作或排序指令，但一个 acquire load 不会自动找到搬迁后的对象。

复习问题：ZGC 是不是只有读屏障？

不能这样概括。JDK 21 的分代 ZGC 同时有 load 与 store 屏障：普通强引用 load 路径负责取得可用的对象地址，store 路径参与标记及代际引用维护；弱引用等访问还有专门处理。非分代 ZGC 的职责分配不同，回答时必须限定模式和版本。

参考：JDK 21 分代 ZGC：屏障与 self-healing。

参考：JDK 21 G1：SATB 写前屏障与卡表写后屏障。

9.1 卡表：把引用修改变成可重扫的范围

卡表把一段堆地址划成固定大小的 card，用小型表项记录相应范围是否需要处理。例如对象 A 执行 A.child = B，写后屏障可把 A 所在的 card标脏；它记录可能含有新引用的位置，不是给 B 贴上“活对象”标签。

示意：假设一张 card 覆盖 512 字节（仅为算例）
card_index = (对象 A 的地址 - 堆起点) / 512
A.child = B
card_table[card_index] = dirty

后续扫描该 card 覆盖的对象 / 引用槽，再判断目标是否需要处理。
多个字段共用一张 card，所以标脏是保守记录。

它有两类常见用途：局部回收找入边，例如只收年轻代时重新检查老年代脏卡；并发标记补查修改，例如重扫标记期间发生过引用写入的对象范围。卡表是记录手段，具体算法决定何时标脏、处理后如何清理，以及与并发写入怎样协调；不能把所有卡表都限定为“老年代到新生代”。

Remembered set 表达需记住的跨区域引用信息，可能由脏卡细化生成，也可能采用其他表示；不一定就是卡表本身。SATB 缓冲记录旧引用，脏卡记录需重查的源范围，信息不同。ART 的常规字段写屏障以非空引用写入为条件之一，调用卡表的 MarkCard(dst)；CC 与下文 CMC 如何消费这些信息须分别看阶段协议。

参考：Android 14：字段写屏障 · ART 卡表。

10. 对象移动、转发与身份

假设对象 O 从 0x1000 复制到 0x9000，堆字段、栈槽或寄存器仍可能暂时保存旧引用。转发信息表达“旧对象位置 → 权威新位置”，让这些引用最终指向同一个对象。实现可以借用旧对象头、设置额外间接指针或建立旁路转发表；不能一概说“转发地址永远存在 Mark Word”。

复制前：p ─┐
          ├→ O @ 0x1000
        q ─┘
复制后：转发表 0x1000 → 0x9000（O 的权威副本）
        p 已更新 → 0x9000
        q 仍为旧引用 → 经屏障解析 → 0x9000
  1. 唯一性：GC 线程和应用线程可能同时尝试迁移同一对象。发布转发结果需要原子协议，使观察者收敛到唯一新地址；允许投机复制的设计还必须处理竞争失败的副本。
  2. 可见性与写入：新地址可供解引用前，副本初始化必须满足发布协议。应用的字段写入也须与搬迁协调，否则写在旧副本上的更新可能丢失；并非有一条转发记录就自动正确。
  3. 身份与元数据：多个别名仍要指向同一对象，身份哈希、锁等状态也必须保留或转移。地址变化不应改变语言层的对象身份。
  4. 回收时机：旧存储与转发元数据的寿命未必相同。只有旧引用已被更新，或仍能由可靠元数据安全解析时，才可按协议复用旧区域；不能在无保护下把旧地址重新解释成另一个对象。
复习问题：两个线程复制同一个对象，为什么不能各用自己的副本？

那会把一个对象分裂成两个身份：通过 p 的写入可能无法通过 q 观察到。需要原子决定权威副本；未获胜者转向已发布的新地址，而不是仅保证两份初始内容相同。

参考：JDK 21 ZForwarding：查询、并发插入与转发表生命周期。
