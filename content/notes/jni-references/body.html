1. 调用边界与线程

1.1 native 方法与调用参数

JNI是 JVM / Android 托管代码与 native 代码交互的接口。Java 用 native 声明本地方法，Kotlin/JVM 用 external 声明本地实现的函数，并加载相应库；运行时通过名称匹配或 RegisterNatives 找到 native 实现。普通实例 native 方法接收 JNIEnv* 和 jobject，普通静态方法接收 JNIEnv* 和 jclass，再接收显式参数。特殊优化调用约定另有约束。

语言声明：Kotlin/JVM 使用 JNI。

1.2 JavaVM、JNIEnv 与线程附加

JavaVM用于取得线程的运行时接口；JNIEnv与当前线程关联，不能从一个线程缓存后交给另一线程使用。native 创建的线程需要先附加到 VM，使用自己的 JNIEnv，并在自己负责附加的线程退出前 detach。

经典问题：把主线程的 JNIEnv 放进全局变量，工作线程继续使用可以吗？

不可以。缓存 JavaVM，在工作线程调用 GetEnv；若尚未附加再 AttachCurrentThread。JNIEnv 和 local reference 都不能因此跨线程复用。

参考：Android JNI：线程与接口。

接口规范：JNI 概述 · 线程附加与 Invocation API。

1.3 注册本地方法与加载器上下文

运行时按导出名称寻找 native 方法，或由 JNI_OnLoad 调用 RegisterNatives 显式绑定。“类名、方法名、描述符、函数签名”必须一致；实例 / 静态方法的第二个参数不同。下面只演示固定接口注册，实际工程还要配置库加载及 R8 保留规则。

#include <jni.h>
// Java: package demo; class Native { static native int answer(); }
static jint JNICALL answer(JNIEnv*, jclass) { return 42; }

extern "C" JNIEXPORT jint JNICALL
JNI_OnLoad(JavaVM* vm, void*) {
    JNIEnv* env = nullptr;
    if (vm->GetEnv(reinterpret_cast<void**>(&env), JNI_VERSION_1_6) != JNI_OK)
        return JNI_ERR;
    jclass type = env->FindClass("demo/Native");
    if (type == nullptr) return JNI_ERR;
    JNINativeMethod methods[] = {
        {const_cast<char*>("answer"), const_cast<char*>("()I"),
         reinterpret_cast<void*>(&answer)}
    };
    jint status = env->RegisterNatives(type, methods, 1);
    env->DeleteLocalRef(type);
    return status == JNI_OK ? JNI_VERSION_1_6 : JNI_ERR;
}

本例的 JNI_OnLoad 按约定符号名发现，C++ 中的 extern "C" 明示 C 语言链接，JNIEXPORT 则处理相应平台的导出可见性，两者职责不同。answer 由 RegisterNatives 通过函数地址绑定，无需为了名称查找加 extern "C" 或导出，但签名和调用约定仍须匹配；普通 extern 与语言链接的规则见C++ 核心知识。

Android 的 JNI_OnLoad 有加载该库的类加载器上下文；自行 attach 的 native 工作线程若没有应用 Java 调用栈，FindClass 可能走不含应用类的系统查找路径。症状是 Java 调用路径查类成功、工作线程查应用类失败。先记录调用上下文和待处理异常，不要靠反复 attach 解决。

常见设计是在适当的初始化上下文取得类并保存 global reference，或显式传入需要的 Class / 加载器；使用已保存的类时仍要用当前线程 JNIEnv。类身份与委派见共同基础。

2. Local、Global 与 Weak Global

2.1 引用种类与释放责任

这里分类的是 JNI 引用句柄的有效期与释放责任。Java 的强、软、弱、虚引用及可达性语义见托管引用基础；两种分类有关联，但不是同一组 API。

引用种类
引用有效期 / 回收影响释放
local reference属于线程与本地引用帧；普通 native 调用返回时自动清理，存在期间保持相应强可达性可提前 DeleteLocalRef；循环中可配合 Push/PopLocalFrame
global reference跨调用有效并强持有对象；跨线程使用时仍需当前线程的 JNIEnv 和业务同步DeleteGlobalRef
weak global reference句柄存在不阻止目标被 GC；使用前须提升并检查DeleteWeakGlobalRef

2.2 对象身份与成员标识

jobject 是运行时管理的引用句柄，不应作为普通 C++ 对象地址解引用。两个句柄可能指向同一个 Java 对象却有不同值，判断对象身份用 IsSameObject。jmethodID/jfieldID 是成员标识，不是 local/global 对象引用。

2.3 弱引用提升与局部引用清理

jobject strong = env->NewLocalRef(weak);
if (strong != nullptr) {
    // 使用 strong；不能先检查 weak 未空，再直接依赖 weak
    env->DeleteLocalRef(strong);
} else {
    // 目标可能已回收；还需按接口规则检查是否存在待处理异常
}
经典问题：native 线程一直运行，local reference 会自动很快回收吗？

不能这样假设。附加的 native 线程若没有不断返回的 Java→native 调用帧，局部引用可能持续保留到显式删除、弹出本地帧或线程 detach。循环创建对象应主动控制局部引用数量。

2.4 成员 ID 缓存不会替你保活类

jmethodID / jfieldID 可缓存，但通常只在相应类未卸载时有效。它们不是对象引用，不能对 ID 调用 NewGlobalRef 或 DeleteLocalRef；缓存 ID 也不能自动保证类持续存在。若设计要求类和 ID 长期可用，可明确持有相应 jclass global reference，并在拥有者关闭时成对清理；这也会延长类加载器的寿命。

插件重载场景应让“类、ID、回调、native 资源”属于同一代的拥有者，不要从新类取得实例却继续使用旧代成员缓存。检查工具只能帮助发现错误，不能替代这套生命周期约定。

3. 创建对象与访问成员

设计规范：引用、方法绑定与对象访问。

3.1 查类、取 ID 与访问成员

  1. 取得目标类：由参数传入、GetObjectClass，或在正确类加载器上下文中 FindClass。
  2. 按名字与签名取得构造器/方法/字段 ID，区分 static 与实例接口。
  3. 用 NewObject 分配并调用指定构造器；访问字段用 Get/Set<Type>Field，调用方法用匹配的 Call<Type>Method。
  4. 检查空返回和待处理 Java 异常；清理自己持有的引用与缓冲，再返回或按约定处理错误。

3.2 构造对象示例

示例：从 native 构造一个 Integer 
#include <jni.h>
// 对应 Java: package demo; class Native { static native Integer box(int n); }
extern "C" JNIEXPORT jobject JNICALL
Java_demo_Native_box(JNIEnv* env, jclass, jint value) {
    jclass type = env->FindClass("java/lang/Integer");
    if (!type) return nullptr; // 保留待处理的 Java 异常
    jmethodID ctor = env->GetMethodID(type, "<init>", "(I)V");
    if (!ctor) { env->DeleteLocalRef(type); return nullptr; }
    jobject result = env->NewObject(type, ctor, value);
    env->DeleteLocalRef(type);
    return result; // 允许把有效 local ref 作为此次 native 调用结果返回
}

这是需接入 Android/JNI 工程的函数示例，不是独立 main 程序。NewObject 得到 local reference；返回给 Java 是合法路径。AllocObject 则不调用普通构造器，不能无条件代替 NewObject。调用实例、静态或显式非虚方法要选择对应 API。

3.3 待处理异常与清理

经典问题：有待处理 Java 异常时，还能继续任意调用 JNI 吗？

不能。许多 JNI 操作此时不允许调用；应检查异常，执行允许的清理操作并返回，或明确清除并处理。也不要让未处理的 C++ 异常穿过 JNI 边界。

参考：JNI 函数规范。

4. GC 与 native 缓冲

4.1 GC 协作与缓冲获取

GC 追踪有效 JNI 强引用，并通过运行时引用机制维持对象移动后的可访问性。native 保存的任意裸地址不因此成为 GC Root。GetStringUTFChars、Get<PrimitiveType>ArrayElements 等接口可能提供副本或受约束的直接访问，必须与对应 Release 配对。

4.2 Release、Critical 与编码

数组 Release 的 mode 决定是否回写和是否释放副本；JNI_COMMIT 不是最终释放，仍需完成对应释放。Critical 接口期间应尽快结束，遵守不能任意阻塞或执行其他 JNI 调用等约束。GetStringUTFChars 使用 Modified UTF-8，不能把所有 JNI 字符串接口都当作普通 UTF-8。

4.3 泄漏与长期持有排查

常见泄漏或持有问题
原因修复方向
NewGlobalRef 无匹配删除为持有者定义明确关闭时机；用当前有效 JNIEnv 清理
local reference 在长循环积累及时删除或使用本地帧
字符/数组缓冲未 Release建立成对作用域清理，覆盖异常与提前返回
native 自己 new/malloc 后未释放由 C++ 所有权与 RAII 负责，Java GC 不自动接管
经典问题：Java 对象已经没有 Java 变量引用，为什么还活着？

可能仍被 JNI global reference、线程、静态字段、回调或其他根路径持有。查看引用链和 JNI heap 视图；不要仅根据某个方法已经返回判断可回收。

4.4 Release 路径与 CheckJNI

#include <jni.h>
// 调用者保证 array 非空且没有待处理异常；只读取首元素。
static bool readFirst(JNIEnv* env, jintArray array, jint& out) {
    if (env->GetArrayLength(array) == 0) return false;
    jint* elements = env->GetIntArrayElements(array, nullptr);
    if (elements == nullptr) return false; // 按接口约定处理待处理异常
    out = elements[0];
    env->ReleaseIntArrayElements(array, elements, JNI_ABORT);
    return true;
}

这里没有修改元素，因此副本无需回写；JNI_ABORT 不保证撤销对直接访问缓冲已经发生的写入。若只需小段复制，也可选择 GetIntArrayRegion 等接口避免长期持有缓冲。复杂路径可用作用域清理包装，确保早退和 C++ 异常都释放，同时不让 C++ 异常越过 JNI 边界。

CheckJNI 可辅助发现错误线程的 JNIEnv、无效引用、部分签名 / 调用错误及不允许的异常状态操作；测试构建按平台方式启用，记录首个违规点。它不是 native UAF 检测器，也不能证明 close 与回调没有竞态。

5. 边界设计

减少细粒度跨 JNI 调用，批量传递必要数据；异步任务要同时管理 Java 引用、native 对象和线程生命周期。缓存类时需要有效 global reference，并考虑类加载器；线程附加本身不会自动获得应用所需的类加载器上下文。

参考：JNI 最佳实践与检查。

5.1 异步回调与 close 的竞争

假设 native 任务持有 callback 的 global reference，Java 页面退出时调用 close。仅在 close 中 DeleteGlobalRef / delete，可能与正在回调的线程竞争；只加一个 atomic closed 也无法保活已经释放的对象。下面是一种关闭请求允许已有任务收尾的设计协议，不是可直接复制的无锁实现。

OPEN：
  任务进入时，在同一锁协议下确认仍开放，取得拥有权并增加在途计数
  → 任务持有 native 状态，期间保证 callback global reference 有效

close 请求：
  OPEN → CLOSING；阻止新任务取得使用权，撤销外部句柄
  → 若在途计数已经为 0：取得唯一清理权，安排最终清理
  → 若在途计数大于 0：允许已有任务收尾，暂不删除引用 / 状态

任务退出：
  在同一锁协议下减少在途计数
  → 若已 CLOSING 且计数降到 0：取得唯一清理权，安排最终清理

最终清理：
  → 在具有有效 JNIEnv 的线程删除 global reference，释放 native 资源
  → CLOSED

任务取得拥有权之前必须通过可靠的句柄表 / 注册表等机制，不能先解引用已经可能销毁的裸地址再检查 closed。登记在途计数、发布 CLOSING、决定最终清理必须在一致的同步协议下完成，失败或取消路径也要归还使用权。重复 close 不能重复安排清理；清理执行者在锁内取得一次性清理权后，要持有状态的有效拥有权直到清理完成。没有任务在途时也必须主动清理，不能等待一个不会出现的“最后任务退出”。

调用 Java 回调时不要持有会被回调再次请求的内部锁。若需要“close 返回后再无回调”，就必须等待或异步通知在途任务排空；不能在回调线程中等待自己结束。释放 global reference 只处理 Java 持有关系，native 对象与线程仍按各自所有权清理。

验证至少覆盖：尚未开始即关闭、回调中关闭、多次关闭、任务取消、异常退出和类加载器重载。日志对齐任务开始 / 结束与引用创建 / 删除；用 CheckJNI 检查引用规则，native 访问错误另配合适用检测器。
