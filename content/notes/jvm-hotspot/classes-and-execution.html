从字节码到运行时状态

文件表示、运行时元数据与对象

源码中的类型、方法和字段先编码在文件里；加载后，运行时建立可访问的类型信息和解析状态；调用时再建立当前执行所需的帧。文件中的类描述、运行时的类信息、Class 对象和某个实例是不同层次。一个 class 文件通常表示一个类或接口，DEX 可汇集多个类定义及共享的索引表。

共同职责与两种表示

JVM 常量池含字面常量、类型和成员的符号信息；加载后的运行时常量池可维护解析结果。DEX 有分别索引字符串、类型、字段、方法的表。常量池不是“所有常量对象的一块堆”：字符串对象、驻留机制与这些表的职责需要分开。

例如 JVM 方法描述符 (ILjava/lang/String;)V表示显式参数 int、String，返回 void；实例方法的隐含 this 不写在描述符里。泛型 Signature 属性与供链接使用的描述符不是同一概念。JNI 查找成员也需要匹配的名字和描述符。

同一次加法怎样执行

以 static int plusOne(int x) { return x + 1; } 为例。下面是指令语义示意；DEX 用含两个虚拟寄存器的方法帧，最后一个 v1 接收参数，不承诺具体工具一定生成这个序列。

JVM：局部槽 0 = x，初始操作数栈为空
iload_0     栈 [x]
iconst_1    栈 [x, 1]
iadd        栈 [x + 1]
ireturn     返回栈顶值

DEX：v1 = x
add-int/lit8 v0, v1, #1
return v0

DEX 的 v0、v1 是字节码层的位置，不是 CPU 的 x0、x1。编译器可以折叠计算、内联调用并重新分配物理寄存器。两种模型都有调用帧，不能由“基于寄存器”推导 ART 没有栈。

参考：JVMS：class、描述符与 Code · DEX 格式 · DEX 指令与帧。

类加载器与类身份

同名为什么不一定是同一个类

对普通命名的类和接口，运行时类身份由二进制名称与定义它的类加载器共同决定。两个加载器分别定义 demo.Widget，得到的 Class 可以不同；即使字节完全相同，其实例也不能仅因名字相同就互相强转。数组类另按组件类型等规则创建，不能把每个数组都当成由加载器读取的独立文件。

定义加载器实际定义这个类型；发起加载器发起请求，可以委派其他加载器返回已有类型。共享接口若由父加载器定义，子加载器定义的实现可以实现该接口；若子加载器连接口也重复定义，就可能破坏原本期待的类型兼容。

委派是查找策略，边界是类型一致性

通常的 ClassLoader.loadClass 思路：
  查当前加载器是否已经加载
  → 委派父加载器 / 相应基础加载路径
  → 未找到时由自己的 findClass 查找并定义
  → 按请求完成必要的链接工作

这是常见父优先策略，不是所有加载器永远不可改变的执行顺序。自定义策略仍需遵守类型安全、加载约束与平台限制。线程上下文类加载器是供特定库选择加载来源的约定，并不自动替代所有类引用的解析加载器。

HotSpot/JDK 21 常见 bootstrap、platform、application 加载路径；Android 常见 BootClassLoader、PathClassLoader、DexClassLoader 等围绕 DEX 查找。它们不能用一套固定目录或内部字段概括。JNI 的 FindClass 又受调用上下文影响，见注册与查类案例。

复习问题：两个插件同名类强转失败，先查什么？

同时记录对象实际 Class、目标 Class 及各自加载器；检查共享接口是否重复打包 / 定义。比较类名或重新 new 一个加载器都不能证明类型一致。类缓存的持有链与卸载见元数据生命周期。

参考：JVMS：类身份与加载约束 · ClassLoader 的默认委派 · Android PathClassLoader。

链接、初始化与失败状态

先区分职责，再讨论发生时机

加载与链接不是执行静态代码块
职责主要工作
加载取得表示并建立类型
验证检查格式、类型和指令使用约束，确保满足相应运行时规则
准备建立静态字段存储及默认值等运行时状态；不执行普通静态初始化表达式
解析把符号引用关联到相应类型、字段、方法等，并检查访问与链接约束
初始化按规定设置常量值、协调依赖类型并执行需要的类初始化逻辑；JVM 对应 <clinit>

初始化前必须完成验证与准备，但解析可以提前或推迟到使用时；不要画成“全类所有符号必须一次解析完，再初始化”的唯一流水线。<clinit> 的类初始化与 <init> 的实例构造不同，一个类可以创建多个实例而不重复执行类初始化。

用可观察顺序理解主动使用

创建实例、调用类声明的静态方法、读写其非编译期常量静态字段等会触发相应初始化；使用子类名称访问继承的静态字段，关键是字段由哪个类声明。类字面量、创建组件类型的数组、读取编译期常量不会仅因此初始化该类。反射是否初始化取决于所用接口，例如 Class.forName 的 initialize 参数。

初始化类前要协调父类，以及规范要求初始化的、声明默认方法的相关父接口；不能推广成“所有接口都先初始化”。每个类的初始化协议处理竞争线程、递归请求和失败状态；成功完成初始化的同步保证，不意味着之后修改静态字段自动线程安全。

按第一次失败定位

ClassNotFoundException 常见于显式查找类失败；NoClassDefFoundError 也可能来自链接时找不到定义，或先前初始化失败后的再次使用。普通静态初始化抛出的非 Error 异常通常被包装成 ExceptionInInitializerError；失败类型会进入错误状态，不能依赖下次调用自动重试。先找最早的异常原因，再查后续报错。

初始化本身也可能因复杂的跨线程 / 跨类等待造成死锁或启动停顿。把耗时 I/O、回调和持锁等待放进静态初始化，影响的是首次使用的整条路径。ART 启动应单独观察这部分成本。

参考：JLS：初始化触发与顺序 · JVMS：初始化与错误状态。

方法解析、分派与异常

编译期选签名，运行时选适用目标

重载通常在源码编译阶段按表达式类型等规则选择签名；虚方法的重写分派则根据实际接收者选择实现。把符号引用解析为方法，与为某次调用选择目标不是同一步。类的虚表、接口分派表及入口缓存属于实现手段。

class Base { int work() { return 1; } }
class Derived extends Base { @Override int work() { return 2; } }
Base receiver = new Derived();
int result = receiver.work(); // 结果为 2；不因变量写作 Base 就调用 Base.work

在 JVM 字节码中，invokestatic 用于静态调用；invokevirtual / invokeinterface 支持相应动态分派；invokespecial 用于构造器及某些需特殊处理的调用。invokedynamic 通过引导方法链接调用点，不等于普通虚调用或“每次做反射”。DEX 有自己的 invoke 指令族；不能把 JVM 指令名直接当成 ART 本机入口。

反射按运行时的类型 / 成员对象发起访问，MethodHandle 表达可调用目标及类型化适配。它们仍受平台访问控制约束，开销受查找、适配、缓存和编译优化影响，不能说反射永远不能优化。普通分派的调用点缓存与去虚拟化见IC 与类型反馈。

Java throw 怎样找到处理器

  1. 在当前方法中，根据抛出位置和异常类型寻找适用处理器；JVM 的 Code 异常表描述受保护范围与处理目标。
  2. 找到时转到处理器所需状态；JVM 的处理器入口操作数栈中放异常对象引用，DEX 使用自己的处理器与 move-exception 约定。
  3. 当前帧无匹配处理器时向调用者传播；解释器和编译代码必须维持一致的语言行为。finally、资源关闭及同步释放由相应控制流与运行时协议实现。

机器帧可因内联少于逻辑调用层数，编译元数据仍须支持定位处理器。Java 异常不直接等于 C++ 的 __cxa_throw；JNI 待处理异常也不是自动在每次 native 指令后展开 C++ 栈。平台边界见JNI 异常清理。

参考：JVMS：调用与 athrow 指令 · Code 异常表 · DEX 调用与 move-exception。
