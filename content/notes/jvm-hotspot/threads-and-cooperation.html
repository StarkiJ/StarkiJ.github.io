共享状态与运行时协作

本部分解释共享状态规则，以及解释器、编译代码与 native 调用如何协作；先区分语言保证和实现元数据。

Java 内存模型、监视器与线程

内存区域与内存模型回答不同问题

堆、栈描述数据由谁保存；Java Memory Model（JMM）描述多线程读写允许观察到什么结果，以及编译器 / 处理器重排必须遵守的约束。happens-before 是保证可见性与先后关系的规则，不等于测到的墙钟时间。正确同步的程序可据此推理，不能靠“CPU 缓存迟早刷新”保证正确。

常用规则与不能推导的结论
机制建立的关系边界
程序顺序与传递性线程内动作及跨线程同步关系可以连成 happens-before 链不要求底层所有指令按源码顺序执行
volatile对变量的写与后续相应读建立同步关系，可用于发布之前的写入count++ 仍是复合操作；volatile 引用不让被引用对象的所有操作自动同步
synchronized同一 monitor 上的解锁与后续加锁建立同步，互斥保护临界区不同锁不自动保护同一不变量
Thread.start / join启动前的动作先于新线程动作；线程终止先于另一线程成功 join 后的动作启动线程不保证其后每次共享访问都安全
final 字段正确构造且未提前暴露 this 时有专门的初始化安全规则不意味着对象整体不可变；引用指向的可变内容后续仍需同步

Java volatile 与 C++ volatile 不能通用解释。C++ 的 volatile 不提供相同的线程同步保证。GC 引用屏障负责可达性或移动访问，也不能替代 JMM；具体实现可以复用底层原子指令，但职责不同。

发布对象之前的写入

推理链是 value=42 → volatile 写 ready → 读到该发布的 ready → 读取 value。删除 volatile 后，忙等不保证结束，也不能保证读到 42。onSpinWait 只是自旋提示，不建立这个同步关系。示例只展示发布规则；实际等待优先用锁、条件或适当的并发工具，避免持续占用 CPU。

安全发布可使用锁保护、volatile 引用、类初始化等适用机制。双重检查若使用可变共享引用，要同时说明其发布协议，不能只展示两次 if。构造器中注册 this 或启动可访问它的回调，会破坏“构造完成后才暴露”的前提。

互斥、等待与唤醒

对象 monitor 支持可重入互斥；实例 synchronized 方法使用接收者，静态 synchronized 方法使用对应 Class 对象。wait / notify / notifyAll 要持有同一对象的 monitor；wait 释放该 monitor，返回前重新取得它，其他已经持有的锁不因此全部释放。被唤醒不等于条件已经满足，也不等于立刻获得锁。

synchronized (lock) {
    while (!condition()) {
        lock.wait();       // 检查与等待在同一锁协议下；处理 InterruptedException
    }
    consume();             // 重新取得锁后再次确认条件
}

sleep 不释放所持有的 monitor；notify 发出唤醒后也不会立即释放当前线程的锁。循环检查同时处理虚假唤醒、多个等待者竞争以及条件再次变化。底层轻量锁、膨胀与等待队列属于具体 VM 和版本，不能把旧 HotSpot 的固定“锁升级四阶段”当作 Java / ART 共同保证。

语言状态、内核状态与安全点状态

Java Thread.State 包含 NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED。BLOCKED 特指等待进入 monitor；不等于所有 I/O 阻塞。RUNNABLE 也不保证此刻正在某个 CPU 上执行。OS 的就绪 / 睡眠状态和 VM 内部的托管 / native / 安全点状态是另外的观察层次。

本篇的例子使用平台线程。JDK 21 的虚拟线程及 Kotlin 协程涉及额外调度关系，不能把它们的数量直接当作内核线程数。通用等待机制见锁与 futex；GC 协调见安全点与根扫描。

解释、编译与 native 怎样协作

入口适配与执行状态

调用者与被调用者不一定使用同一种执行方式：解释器可调用编译代码，编译代码也可调用尚未编译的方法或 native 方法。运行时通过入口与适配代码转换参数位置、维护帧及线程状态，并处理必要的解析、检查与异常。更新方法入口主要影响后续进入方式，不能据此断定已经执行到一半的旧帧全部消失。

长循环可通过 OSR在受支持的位置转入编译执行；优化假设失效时可通过反优化恢复可继续执行的状态。它们需要执行位置和活值映射，不只是改一个函数指针。

看似都是“栈信息”，用途并不一样

以一次内联调用中的对象引用为例
信息回答的问题主要讲解位置
JVM StackMapTable字节码验证时，给定位置允许哪些局部值和操作数栈类型class 格式与验证；不是 GC 地址表
GC 引用位置图，如 HotSpot OopMap某个受控机器码位置哪些寄存器 / 槽是活引用GC 根扫描

CFI / 异常处理信息如何恢复上一机器帧，以及语言处理器 / 清理代码在哪里回溯与异常展开
调试映射机器地址对应哪个函数、源码行和内联位置符号化与调试

这些职责可能在实现中共享部分记录，但不能互换使用。编译器消除局部变量或内联方法后，源码中“有这个变量”不保证物理栈上有同名槽。ART 也需要相应协作信息，编码格式须查其分支；JNI 通过引用句柄和线程转换加入该协议。

复习问题：保存所有通用寄存器，是否足够支持 GC 和反优化？

还不够。保存位值没有说明哪些是引用、对应哪个逻辑变量、是否需要重新物化对象，以及恢复到哪个指令位置。运行时必须与编译器约定这些值的语义，而不只是寄存器数量。
