动态编译与运行时优化

本部分涉及托管方法的分派与执行状态；相关语义见方法解析与分派，机器状态基础见调用与栈帧。

运行期间的热点与类型信息可以指导编译决策。沿采集信息、生成优化代码、处理假设失效的顺序，连接前面的 IR 变换与可继续执行的运行时状态。

解释执行、AOT、JIT 与热点统计

AOT在目标程序本次执行前生成机器码；JIT在运行过程中按需编译，可使用运行时类型和热点信息。解释执行、低成本编译、优化编译可组成不同层级，平衡启动、峰值性能与编译资源。C1/C2 是 HotSpot 的特定分层术语，不是所有 JIT 的统一级别。

执行方式
方式收益成本
解释无需先为所有方法生成本机代码反复解释热点指令有成本
JIT按运行热点生成代码并利用运行信息占用应用运行期间的 CPU、代码缓存与元数据
AOT提前生成可复用机器码编译耗时、磁盘体积；可能编译并不热的方法

运行时还需要在解释帧、编译帧和 native 调用间转换。编译代码依赖相应检查、类状态和 GC 协作信息，不是与运行时脱离的一段裸机器码。

HotSpot C1 / C2：为什么分层

以 JDK 21 HotSpot 的编译级别为例，C1 是编译开销较低的编译器，可按级别产生不同数量的运行反馈；C2 花更多编译资源追求更强的优化。分层让热点代码较早脱离解释执行，同时继续积累调用与类型信息，供后续优化使用。级别是代码的编译状态，不是“一个方法一定按 0、1、2、3、4 各跑一遍”的固定流水线。

编译级别与主要职责
级别执行形式反馈与用途
0解释执行可收集热点信息，并决定是否提交编译任务
1C1 简单编译较快获得机器码，不承担完整的类型反馈收集
2C1 有限 profiling记录调用与回边计数等有限信息
3C1 完整 profiling除计数外记录方法数据中的更丰富反馈，为高层优化提供证据
4C2 完整优化；配置 JVMCI 时也可由其承担利用已有反馈进行更重的优化，增加编译 CPU、时间和代码缓存成本

实际升层由热点、编译队列、代码缓存、编译器是否可用及配置共同决定，可能跳级或停在较低级别；长循环还可能经 OSR 在循环中途切换。C2 依据类型反馈生成的快速路径仍要保证假设失效时可安全处理，可能走慢路径或反优化；这与“C2 机器码永远不退回解释”不同。反优化怎样恢复执行状态见OSR 与反优化。

面试追问：为什么不把所有方法一开始就交给 C2？

很多方法并不热，提前做重优化会花编译 CPU、延迟与代码缓存；初次执行也缺少有价值的类型和分支反馈。解释与 C1 先提供低成本执行和采样，运行时再把值得投入的方法交给 C2。是否收益更好仍取决于负载和配置。

参考：JDK 21 HotSpot CompLevel 定义 · JDK 21：分层编译与代码缓存。

AOT 编译怎样做优化

AOT 说明生成机器码的时机，不指定一套独有的优化算法。编译器仍可在 IR 上做常量传播、死代码删除、内联、循环优化和寄存器分配；每项变换的语义前提见优化的前提与代价。运行前已知的类型、调用关系和目标 ISA 可用于静态分析，但运行时才出现的接收者类型或分支频率不能凭空假定。

例如某虚调用有多个可能目标：若 AOT 编译时能证明目标唯一，可以直接调用或内联；若只有历史 Profile 显示某类型常见，可在支持相应协议的运行时生成“类型检查 → 热门目标快速路径 → 其他目标慢路径”，并保留假设失效后的正确执行方式。没有证明或反馈时应保留通用分派。由此可见，Profile-guided AOT仍是 AOT，利用过去运行的数据不等于在本次运行中 JIT 编译。

以 ART 为例，dex2oat 的 speed 倾向编译所有方法，speed-profile 依据 Profile 选择方法并优化相关类加载；已有类型反馈也可支持某些 AOT 调用点优化。要同时权衡编译耗时、磁盘中的机器码大小、启动时间、峰值执行速度和 Profile 的代表性。选择编译哪些方法与怎样优化单个方法是两个不同问题；具体 pass 和过滤器行为须限定 ART 版本。

面试追问：AOT 没有运行时信息，所以不能做内联吗？

不能这样说。目标在编译时可证明时可以静态内联；也可以用已有 Profile 做受检查的猜测性优化，前提是运行时提供相应的慢路径或状态恢复。没有可靠证据时不能把可能变化的目标无条件固定。

参考：Android：ART AOT 与 compiler filters · Android：Profile 与 AOT 调用点优化。

热点统计与编译调度

一种热点设计是在方法元数据中保存饱和调用计数、回边计数和编译状态；达到阈值后入队，避免重复编译。采样或线程本地计数可降低竞争；计数合并、过期、代码缓存容量和反优化也要纳入。无需每次调用都建立字符串键哈希表。

经典问题：热点统计应选择什么数据结构？

通常可把计数与状态放在方法关联元数据中，结合调用/回边计数或采样，降低查表和同步开销；编译队列要去重，计数可饱和。真实字段、阈值和队列实现需对照目标运行时分支。

经典问题：调低 JIT 阈值一定让启动更快吗？

不一定。较早生成机器码可减少热点解释成本，也会提前占用 CPU、内存和编译队列，可能与启动关键线程争抢资源。按冷/热启动、编译时间、执行节省和代码缓存占用做对照，不能只比较单个函数执行速度。

Profile 与代码缓存

经典问题：“JIT 预编译”通常需要怎样澄清？

如果指运行前依据已有 profile 生成机器码，那更接近 profile-guided AOT；如果指在运行中提前安排将使用的方法编译，则仍是运行时策略。应明确生成时间、输入信息和代码保存位置。

代码缓存回收处理可回收的 JIT 机器码及随代码保存的辅助信息；Java 堆 GC 处理对象可达性。代码、运行时类型反馈和持久化 profile 的存储与寿命必须分别看。以 JDK 21 HotSpot 为例，MethodData 中的方法反馈分配在 Metaspace；Code Cache 中的 profiled code heap 保存的是带 profiling 的编译代码，不能理解成存放全部 profile 数据的堆。

ART 有自己的 JIT 代码及 profiling 管理方式。回收一段机器码不等于删除全部类型反馈或磁盘 profile，也不等于清空 Java 堆；代码失效、类卸载和各类存储回收通过运行时协议协调。

参考：JDK 21 MethodData::allocate：反馈的元空间分配。

ART 的实际编译与 profile 流程见 ART 编译与 Android 应用启动。

参考：HotSpot：分层编译与代码缓存。

Inline cache、类型反馈与反优化

Inline cache（内联缓存，IC）是在调用点缓存接收者类型与调用目标的关系。同一个虚调用点往往反复遇到同一类对象；缓存命中时可缩短动态分派路径。这里的 inline 描述缓存贴近调用点，并不等于把被调用函数体展开。

调用点：receiver.work()
首次执行：尚无缓存 → 运行时解析 receiver 的类型与目标
单态路径（概念）：
    按语言要求处理 null
    if receiver.klass == cached_klass:
        call cached_target(receiver)
    else:
        进入 IC miss / 运行时分派路径

方法解析、普通分派与类身份见托管调用基础。缓存键必须足以识别运行时类型，例如可靠的 Klass 身份；同名类可能由不同类加载器定义，不能只比较类名字符串。虚表按类描述方法槽位，IC 则利用某一个调用点的类型规律，两者可以配合。

  • 未链接 / 未初始化：第一次调用尚需解析。
  • 单态（monomorphic）：调用点反复看到一种接收者类型，可使用类型检查加直接目标。
  • 多态内联缓存（PIC）：一般设计中可缓存少量“类型→目标”对，按 guard 逐一检查。
  • 超多态（megamorphic）：类型过多时，维护长检查链得不偿失，可退回通用虚表 / 接口表等分派。

上面是通用设计词汇，不是每个 HotSpot 调用点都必经四级状态。JDK 21 的 CompiledIC 主要表达 clean、monomorphic、megamorphic 等状态；JIT 根据 profile 生成多个类型 guard 的优化代码，与 CompiledIC 自身是否维护 PIC 数组是不同问题。

类型反馈怎样支持内联和反优化

JIT 看到单态热点后，可以生成“类型 guard + A.work 的内联代码 + 失败路径”。原 IC 快速调用仍存在一次调用，内联则消除了调用边界，并给后续常量传播、逃逸分析等提供机会。内联要平衡收益、代码膨胀和指令缓存压力。

当接收者出现新类型时，普通 IC miss 可以进入运行时解析并更新状态，不必每次都反优化。如果机器码依赖了更强假设，例如类层次分析认定某方法只有一个实现，则新类加载可能使依赖失效，触发失效处理或反优化。反优化需要用元数据恢复解释执行所需的局部变量、操作数栈和内联帧状态。

修改目标与缓存类型还必须满足并发发布协议，避免其他线程看到“新类型配旧目标”；代码修补也需遵守目标架构的指令可见性要求。这是运行时实现细节，不能直接用两次普通赋值替代。

面试追问：IC miss、缓存状态变化、反优化是同一件事吗？

不是。miss 表示当前接收者不满足该缓存快速路径；运行时可能解析后更新缓存，或者走通用分派。反优化则是退出不再适用的优化机器码、重建可继续执行的状态。guard 失败可以设计为慢调用，也可以设计为 uncommon trap，取决于编译决策。

面试追问：如何把 inline cache 与 SSA 连起来回答？

IC / profile 提供类型证据，JIT 生成 guard 把快速与慢速路径分开；两条路径返回的值在合并块可由 phi 汇合。进一步内联后，SSA 的定义—使用关系帮助传播常量与删除冗余计算。

OSR 与反优化：执行到一半怎样切换

方法入口与循环入口不是同一个状态

一个方法只调用一次，却在里面循环很久，仅统计方法调用次数可能漏掉热点。回边热度可触发OSR（On-Stack Replacement）编译：在运行时支持的位置，把正在执行的帧状态转为相应编译入口需要的状态，继续剩余工作，不重新执行方法开头。

long sum = 0;
for (int i = 0; i < n; i++) sum += i;

解释执行到某个受支持的循环入口：
  当前 i = k、sum = 前 k 项累加值、n 已知
  → 把活值交给针对该入口生成的代码
  → 编译代码从当前循环状态继续
不是：i = 0、sum = 0，再跑一遍。

普通编译入口接收方法参数；OSR 入口还依赖当前执行位置和已形成的局部状态。需要对应代码已准备好、线程可完成转换等条件，不能仅凭回边计数达到某个固定值就保证立即切换。JDK 21 HotSpot 与 ART 都有 OSR 相关路径，具体入口、限制和阈值各自定义。

反优化恢复的是语义状态

假设 outer 调用 inner，JIT 把 inner 内联，并消除了其中的 Pair 分配。机器上可能只剩 outer 的一帧和若干寄存器值。若某个优化依赖失效，需要恢复的却可能是 outer、inner 两层逻辑帧，以及仍会被后续代码使用的对象。

  1. 在规定位置确定失效原因与恢复点，避免把普通 IC miss 都当成反优化。
  2. 依据恢复元数据取得各逻辑帧的执行位置、局部值、表达式中间状态和必要的同步状态；来源可为寄存器、栈槽或常量。
  3. 对被消除但后续需要的对象重新物化，恢复字段与别名关系；两个逻辑变量原指向同一对象时不能恢复成两个独立副本。
  4. 构建目标执行状态，再从对应位置继续。哪些操作已完成、哪些还需执行，由恢复点及相应重执行规则确定，不能把已发生的写入或 I/O 随意重放。

因此，反优化不是简单“丢掉机器码再从方法第一行解释”。某方法的代码不再允许新调用进入，与它已没有任何活跃帧、可以回收存储，是不同条件；失效、在栈帧转换和代码回收需要协调。

HotSpot 的 ScopeDesc 等信息描述逻辑作用域、局部值与表达式状态，Deoptimization 负责恢复和物化。ART 有自己的帧与恢复格式。GC 只知道“哪个槽是引用”还不足以完成这一过程；对照几种元数据的职责。

参考：ART JIT 与 OSR · JDK 21 Deoptimization · JDK 21 ScopeDesc。

ART 的恢复元数据见HEnvironment。

用证据区分预热、编译与反优化

“第一次慢、后面快”可能来自类初始化、文件页与数据缓存、解释执行或 JIT。先分清一次进程启动与稳态吞吐，再将编译事件和业务耗时放到同一时间线上；不能用一次计时证明某个方法已内联或某对象已被标量替换。

观察、候选原因与补充证据
观察要区分的原因证据
多轮运行逐渐变快编译、初始化或缓存逐步就绪新进程与同进程分组，记录类加载 / 编译时间线及实际工作量
输入类型变多后变慢分派成本变化、优化依赖失效，或输入本身更昂贵匹配调用点、类型分布、编译 / 失效事件；不能只看一条 made not entrant
吞吐高但启动更差编译 CPU 与启动关键工作竞争编译线程 / 主线程调度、代码缓存、首轮延迟及稳态收益

HotSpot/JDK 21 可在受控测试中使用 -XX:+PrintCompilation观察编译记录，或用 JFR 关联编译、执行、分配等适用事件；日志中的 OSR 标记、编译级别和失效文字需按该版本格式解读。要证明具体优化还应检查适用的编译日志或生成代码，性能结果本身不是优化过程的证据。

一个类型变化实验可固定每轮输入数量和工作量，先主要调用实现 A，再引入实现 B，对齐记录类型切换和延迟。它是检验假设的设计，不保证特定 JIT 必然去优化；重复新进程试验并区分预热与测量。避免结果未使用导致死代码消除，也不要通过随意加 volatile 改变原问题。

严肃的 JVM 微基准可用 JMH 的独立进程、预热和结果消费机制；Android 启动场景则见编译状态对照。两者测试对象和环境不同，不直接比较一个毫秒数。
