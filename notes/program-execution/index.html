1. ELF、链接与装载

ELF可表示可重定位目标、可执行文件和共享库。除机器指令外，还可能包含只读/可写数据、符号、重定位、动态链接信息与调试信息。调试信息可被剥离或单独保存；并非每个文件都有全部内容。

两种组织视角
结构主要用途
Section：.text、.data、.bss 等链接与分析；.bss 表示需零初始化的存储，通常不占等量文件内容
Segment：由程序头描述装载器映射文件范围与设置内存权限；一段可包含多个 section

静态链接从目标和库中组合所需代码、处理符号与重定位。动态装载映射依赖库，由动态链接器处理相应符号和重定位；某些调用可通过 PLT/GOT 等结构间接解析。装载地址还可能受 ASLR 影响。

readelf -h -l -S app
readelf -Ws app
readelf -r app
nm -C app
objdump -d -C app

这些是 Linux/ELF 工具示例；Windows 常见 PE/COFF、macOS 常见 Mach-O，不能直接套用 ELF 文件结构。

参考：ELF 格式。

2. 指令、寄存器与内存

指令集 ISA规定可执行指令及其可见效果；微架构决定这些指令如何流水执行、预测和访问缓存。同为 AArch64 的不同处理器也可有不同流水线，不能把“五级流水线”当成所有 ARM/RISC-V 的固定实现。

CPU 执行 load 时按指令计算有效地址，经过地址转换与权限检查，从缓存或更低层存储取得数据，再写入寄存器。TLB 与缓存访问可能并行或重叠；它们不一定是严格串行的一条流程。

C++ 指针值用于定位目标；引用是语言层别名，可能被实现为地址，也可能被优化掉。解引用次数要看生成代码：成员偏移可直接合入寻址，而被优化成常量的对象可能没有实际访存。

经典问题：CPU 是直接从“引用变量”找到数据的吗？

CPU 不认识 C++ 引用语法，只执行生成的地址运算与加载指令。先解释引用绑定哪个对象，再看目标 ABI 和优化后的机器代码如何访问。

3. 大小端与数据表示

大小端描述多字节对象的字节顺序。以值 0x12345678 的 32 位整数为例，地址从低到高，小端为 78 56 34 12，大端为 12 34 56 78；它不改变数值本身，也不描述位在字符里的书写方向。

网络长度字段与磁盘格式应指定字节序，并使用显式编解码。不能把任意输入缓冲直接强转为结构体：还可能存在未对齐、填充、生命周期和类型访问问题。32/64 位也不能单独决定端序、long 大小或结构布局。

4. AArch64 寄存器与调用约定

ABI约定参数、返回值、寄存器保存责任、栈对齐和对象布局，使独立编译的代码能协作。以下采用 AAPCS64 的普通整数调用场景；AArch32、Windows x64、System V AMD64 等有各自规则。

AAPCS64 的常用寄存器角色
寄存器用途
x0–x7 / w0–w7常用整数/指针参数及结果寄存器；w 是对应寄存器的低 32 位视图
x8间接结果地址的特殊用途
x9–x15常用临时寄存器，调用者不能依赖调用后保留
x16–x17过程调用临时寄存器，可供链接桩使用
x18平台寄存器，使用约束依平台
x19–x28被调用者需要保存的通用寄存器
x29 / x30常作为 FP / LR；x29 按 ABI 保存，x30 保存返回地址
SP栈指针；接口处满足 16 字节对齐等约束
v0–v31浮点/SIMD 寄存器，传参与保存规则另行规定

AArch64 的 PC 不是可像 x0 那样直接使用的通用寄存器。BL 将返回位置记到 LR 并转移控制；BLR 经寄存器间接调用；RET 通常使用 LR 返回。条件分支、间接跳转、异常进入和异常返回也会改变控制流。

参考：Arm AAPCS64。

整数、浮点与聚合类型怎么传

按基础 AAPCS64，常规整数 / 指针参数使用 x0–x7，浮点 / SIMD 参数使用 v0–v7 的相应视图，两组参数寄存器分别分配。普通整数结果常在 x0，某些小聚合结果用 x0/x1；浮点结果用 v0 的相应视图。需间接返回的聚合对象由调用者准备存储，并通过 x8 传递结果地址，不能把 x8 说成第九个普通整数参数。

double mix(long a, double b, long c, double d);
// Linux LP64 的基础 AAPCS64 示例：a→x0，b→d0，c→x1，d→d1；结果→d0

long ninth(long a0, long a1, long a2, long a3, long a4,
           long a5, long a6, long a7, long a8);
// 前八个参数→x0..x7；a8 位于被调用者入口 SP 指向的栈参数区
// 若函数序言调整了 SP，访问 a8 时必须补上相应偏移。

不能只看 sizeof 决定所有结构体的传递：例如基础规则下由 1–4 个同类浮点成员组成的 HFA 可走浮点寄存器。C++ 非平凡对象及平台变体还有专门规则；可变参数、Apple / Windows ARM64、SVE 等需另查对应 ABI。本节不把普通定参函数的规则直接推广过去。

调用前后，哪些值能继续使用

caller-saved 表示调用后不保证保留；调用者若还要使用，就需保存到合适位置。callee-saved 表示被调用者若修改，就要恢复。x19–x29 需按约定保留；v8–v15 在基础约定中只保证低 64 位，不能假定完整 128 位 SIMD 值都保留。v0–v7 与 v16–v31 属调用可破坏范围。

SP 在公共接口及经 SP 访问内存时须满足 16 字节对齐要求；不能只减 8 字节压入一个值后就调用别的函数。写 wN 会清零对应 xN 的高 32 位；x18 的平台用途不能擅自占用。帧指针链是否存在受平台规则和优化选择影响，回溯可依赖展开表。

面试追问：我把一个跨调用的值留在 x9，调用结束再用，可以吗？

若没有额外保存或被调用目标的特殊保证，就不可以。x9 是 caller-saved，目标函数可覆盖它。可在调用前保存到栈，或分配到 callee-saved 寄存器；使用后者的函数也要保存和恢复它从自己调用者收到的原值。

5. 一次非叶函数调用

假设 int foo(int n) { return add(n, 1) + 1; }，add 未被内联。n 通过 w0 传入，第二个整数参数放 w1，整数结果从 w0 取得。下面是示意性汇编，不是编译器必须生成的固定序列。

foo:
    stp x29, x30, [sp, #-16]!  // 保存旧 FP/LR，SP 下移
    mov x29, sp
    mov w1, #1
    bl add                    // 覆盖 LR，跳到 add
    add w0, w0, #1           // 使用返回值
    ldp x29, x30, [sp], #16  // 恢复 FP/LR，SP 上移
    ret

栈帧可保存返回信息、需保留寄存器、局部对象、溢出到栈的值和栈上传参。并非所有参数都压栈，也不是每个局部变量都占一格栈内存。叶函数可不建立传统栈帧，内联和尾调用还可能消除一次调用层级。

普通非静态成员函数需要传递 this。在简单无特殊返回参数的场景，this 常占用首个指针参数位置；复杂返回值、thunk 和平台 ABI 可能改变细节。虚调用在无法去虚拟化时通常先读取虚表中的目标，再进行间接调用；虚表规则见 C++ 对象模型。

经典问题：为什么非叶函数常要保存 LR？

它调用别的函数时，BL 会改写 LR。若后续还要返回自己的调用者，就必须把原返回地址保存到合适位置；示例放在栈中。具体保存方式由编译器和 ABI 决定。

6. 调用栈回溯与 LLDB

回溯从当前 PC/SP 等寄存器出发，根据展开信息或有效帧链恢复上一层寄存器与返回地址，逐层重复。它不是简单把栈内“看起来像代码地址”的数字全部打印出来。

  1. 取得故障线程寄存器，确认 PC 所属模块和构建 ID。
  2. 用 DWARF CFI 等展开信息或目标平台机制恢复上一帧；符合约定时也可沿帧指针链回溯。
  3. 结合模块装载偏移和匹配的符号文件，把代码地址映射到函数、源码行和可能的内联帧。
  4. 若栈损坏、缺少符号或展开信息，检查寄存器和原始栈；不要把截断回溯当作完整调用关系。
thread backtrace all
register read pc sp fp lr
disassemble --frame
memory read --size 8 --format x --count 16 $sp
image lookup --address $pc

以上寄存器别名按 AArch64 LLDB 场景书写；其他目标需调整。读取内存前确认地址映射和可读范围，八字节显示也不意味着其中每一项都是指针。

经典问题：为什么优化后栈里少了某个函数？

可能被内联、尾调用消除，或缺少展开/调试信息。保留符号、核对同一构建，必要时用调试构建复现；不能只因回溯没有显示就断定没有执行。

参考：LLDB 命令参考。

7. C++ 异常展开：从 throw 到 catch

Stack unwinding（栈展开）利用保存状态和展开规则恢复上层帧。打印 backtrace 可只读取并重建虚拟上下文；C++ 异常传播则还要实际转移控制并运行清理代码。这里以 GCC / Clang 常见的 Itanium 风格 C++ EH + DWARF 展开模型为例，它也用于多种非 Itanium 架构；Windows SEH 和 AArch32 EHABI 有不同细节。

从 throw 到 catch：两阶段

  1. 抛出：构造异常对象；编译器通常调用 __cxa_throw，进入异常运行时和 _Unwind_RaiseException 等接口。
  2. 第一阶段——搜索：逐帧查询 personality routine，依据异常类型和该调用位置的语言相关信息寻找匹配处理器。搜索阶段不实际弹掉程序栈，也不执行这些帧的局部析构。
  3. 第二阶段——清理：从抛出点沿相同传播路径展开，把控制交给需要清理的 landing pad，销毁已完整构造、需要离开作用域的自动对象；清理后可通过 _Unwind_Resume 继续展开。
  4. 进入处理器：到达搜索阶段找到的处理器帧，执行 catch 的相应逻辑。重新抛出会继续异常传播。

“展开就是不断 pop 返回地址”漏掉了寄存器恢复和语言清理语义。personality routine负责语言相关的匹配 / 清理决策，通用 unwinder 负责帧状态恢复；编译器生成的 landing pad 执行实际清理动作。

CFI、CFA、LSDA 分别描述什么

参考：LLVM：异常处理与展开表。

DWARF CFI 描述给定 PC 处如何计算 CFA（规范帧地址）以及恢复寄存器；CFA 是展开使用的参考地址，通常由 SP 或 FP 加偏移得到，不等同于“当前 SP”。ELF 中异常展开信息常见于 .eh_frame，语言相关 LSDA 常见于 .gcc_except_table，后者关联调用位置、landing pad 和处理动作。调试符号负责函数名 / 行号等信息；删除调试符号不必然删除运行异常所需的展开表。

前面非叶函数示例在函数序言完成后，概念上可用 CFA = SP + 16，旧 x29 在 CFA−16，旧 x30 在 CFA−8；序言 / 尾声执行到一半时规则可能不同。缺少帧指针不自动意味着无法展开，关键是有适用且正确的展开信息。

参考：Itanium C++ ABI：搜索、清理和 personality 接口。

用析构顺序验证，不靠背术语

这验证 C++ 可观察的清理顺序，不能仅凭输出证明本机使用了哪一种 EH ABI。若构造函数尚未成功完成，失败对象自身的析构不会执行，但已成功构造的基类 / 成员会清理。仅有裸指针局部变量不会自动 delete 它指向的对象；要用 RAII 包装拥有关系。

面试追问：unwind 过程中析构函数再次抛异常会怎样？

若清理时调用的析构函数让第二个异常逃逸，运行时会调用 std::terminate；析构内部自行捕获处理是另一回事。异常逃出 noexcept 函数也会 terminate，不能承诺所有外层析构都已执行。未找到处理器时同样不能依赖“先析构整个栈再退出”。

面试追问：零成本异常真的没有成本吗？

通常指正常路径避免逐次注册处理器等开销，不代表二进制、缓存和优化没有代价。展开表与清理代码占空间，实际抛出还涉及异常对象、查表、类型匹配和展开；禁用异常编译也不能随意让异常穿越未准备好展开的边界。

参考：libstdc++：异常处理成本与禁用异常的边界。

JVM 相关追问要分清层次：Java 异常由虚拟机管理解释 / 编译帧及 Java 处理器，不能说每次 Java throw 都直接走 C++ __cxa_throw。GC 根扫描、反优化和 native 异常展开都需要机器状态元数据，但各自目的和协议不同。
