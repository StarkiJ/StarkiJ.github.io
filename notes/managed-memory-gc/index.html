阅读范围与实现边界

从运行时内存全景开始，沿对象创建、布局、引用与可达性，理解回收算法、并发标记、对象移动和内存排查。HotSpot 与 ART 的共同基础只讲一次，对象头、执行模型和分配路径的实现差异在对应知识点旁比较。

本文实例采用以下版本：JDK 21 HotSpot 的 G1 / 分代 ZGC与AOSP android-14.0.0_r1 的 ConcurrentCopying / Concurrent Mark Compact。实现细节不等同于 JVM 规范，也不自动适用于其他运行时、模式或版本。

JVM 规范描述抽象虚拟机，HotSpot 是具体实现，ART 则执行 DEX 字节码；共享 Java 语言与 API 概念，不意味着内存布局完全相同。只复习基础可读第一部分，屏障与移动见第二部分，G1、ART CC / CMC 的流程及平台排查见第三部分。地址与映射基础见虚拟地址与物理内存；解释、JIT 与 AOT 复用编译器笔记。

一、运行时内存、对象与回收基础

本部分从虚拟内存与驻留进入运行时内存、对象与回收；只复习共同基础可集中阅读本部分。

1. 运行时内存全景

一次方法调用需要保存执行状态，创建对象需要取得存储，访问字段需要知道类型与布局。HotSpot 与 ART 都要解决这些问题。先按内存承担什么职责、由谁持有、何时可以回收建立共同模型，再看具体实现使用哪些区域和数据结构。

从职责认识内存

JVM 数据区与 DEX 执行模型

栈帧保存一次调用所需的执行状态，GC 需要按当前执行位置识别其中的引用。JVM 的局部变量与操作数栈、DEX 的虚拟寄存器及运行时帧适配，统一见字节码与执行模型和执行状态与元数据；这里关注这些存储中的对象引用如何参与根扫描。

容量、使用量与物理占用

预留地址范围表示为后续使用留出虚拟地址；已提交容量表示运行时已提交使用的部分，并不等于所有页面都已驻留。已分配空间可能包含尚未回收的垃圾，存活量则要结合某轮存活判定理解。RSS 统计进程驻留页，PSS 按比例分摊共享页；比较它们时要保持采样时机和统计范围一致。

观察内存时至少分清：预留地址范围、已提交容量、已分配空间、回收后存活量、进程 RSS/PSS。对象失去引用、GC 回收对象存储、运行时把页面归还操作系统是不同事件。GC 后堆使用量下降，进程物理占用未必立即下降；虚拟地址连续也不要求物理页连续。地址与驻留基础见虚拟内存，分配器缓存见free 与页面归还。

2. 对象创建与分配路径

从创建请求到可用对象

把一次普通对象创建拆成几个职责：取得所需类型信息并满足类初始化要求，计算对象大小与对齐，取得存储，建立默认字段值和对象头，再执行构造逻辑。具体检查可能提前完成，零初始化也可能批量进行；这不是每次 new 都按同一条慢路径调用一遍的承诺。

分配存储与执行构造器是两件事。局部变量保存对象引用，也不表示对象存储就位于局部栈帧。优化器还可能消除不影响可观察行为的分配：JDK 21 HotSpot C2 的标量替换可把对象拆成独立值，不能简单背成“逃逸分析一定把对象搬到栈上”；推导与恢复条件见逃逸分析与标量替换。

指针递增、CAS 与 TLAB

连续空闲区可以用指针递增（bump pointer）分配：检查剩余空间，交付旧 top，再推进 top。若多个线程共享 top，必须用 CAS 等同步协议避免交付重叠区域；若空闲空间分散，分配器也可能查找空闲块。分配路径取决于当前空间组织，不能把所有对象创建都概括为一次 malloc。

CAS（Compare-And-Swap，比较并交换）把“比较当前值是否等于预期值，若相等则写入新值”作为一个原子操作。用它更新共享 top 时，竞争失败的线程需要重新读取和检查剩余空间。原子操作保护的是这次状态更新，不能保证高竞争下没有重试成本，也不保证整个分配慢路径无锁。

TLAB（Thread-Local Allocation Buffer）把一段堆空间交给某个分配线程使用。命中时由该线程推进自己的 top，减少每个小对象都争用共享分配状态的成本。这里“线程本地”修饰的是分配权：对象以后仍能被其他线程引用，也仍受 GC 管理。

3. 对象布局、引用与身份

理解对象布局时，先分出运行时管理信息、实例字段和对齐填充；数组还需要长度等信息。类型信息帮助运行时解释字段和方法，锁、身份哈希及 GC 又需要维护各自状态。具体信息可能位于对象头、类型元数据或外部表中，不保证全部常驻对象头。

对象身份、引用编码、对象地址和物理页不是同一个概念。压缩引用需要解码才能得到可用地址；类型指针用于查找类型，不是对象自己的地址。移动 GC 可改变地址，但语言层多个引用仍须指向同一个对象，见转发与身份。

直接引用与句柄体现不同的间接访问方式：句柄增加一层运行时管理的关联，直接引用也可能需要解码或屏障。JNI 的 jobject 应通过 JNI 接口使用，不能当作对象地址解引用；其 local / global 生命周期见JNI 引用。

4. 可达性、GC Roots 与引用类型

从根出发寻找对象

追踪式 GC从根集合沿对象引用寻找可达对象，再处理不可达对象。它依据可达关系，不依据“变量名还在不在”，也不要求对象引用图没有环。GC 线程之外执行应用代码的线程常称为 mutator。

根或根访问路径
场景为什么必须保留
线程当前栈帧、寄存器中的活引用方法后续还可能使用该对象
JNI local / global 强引用native 代码仍可能通过有效引用访问对象
运行时持有的类、线程和其他内部根运行时自身仍需要这些对象
已加载且可达的类的静态字段通过类对象和相关运行时根可继续到达字段指向的对象

具体根集合由运行时实现与线程状态决定；弱引用需要特殊处理，不等价于普通强根。移动 GC 还需识别并修正引用，不能简单扫描任意整数并把“像地址”的值都移动。

经典问题：两个对象互相引用，GC 是否一定回收不了？

追踪式 GC 可以回收整个不可达环。只要没有从根到达这个环的强可达路径，就不因互相引用而保留。引用计数通过增减计数跟踪持有关系，单纯的强引用计数无法自行识别不可达环；二者的存活判断依据不同。

强、软、弱、虚引用

要问的是对象当前通过什么路径可达。同一个对象同时被普通变量与 WeakReference 引用时，只要普通变量仍形成活的强可达路径，弱引用就不会使该对象被提前回收。

Java 引用语义：HotSpot 与 ART 可共用的基础
种类对存活的影响使用边界
强引用仍然强可达的对象必须保留“对象之间存在强引用”不等于“从根强可达”；无用但持续可达会形成托管内存泄漏
SoftReference仅软可达时，GC 可响应内存需求清除软引用不能把它当作具有固定容量和淘汰时机的缓存；具体回收策略随实现变化
WeakReference不会阻止仅弱可达对象进入后续回收处理不是“每次 GC 必定清掉所有弱引用”；使用 get() 的结果时检查 null，并用局部强引用保存本次结果
PhantomReference用于跟踪相应可达性变化，配合 ReferenceQueue 处理通知get() 始终返回 null；入队不能证明对象存储已归还操作系统

ReferenceQueue 通知与实际资源清理需要应用自己的处理逻辑。保留被注册的 Reference 对象；队列不会仅因注册动作而替应用保活它。GC 管理堆存储，文件、连接、native 缓冲等资源仍应优先显式关闭，例如使用 AutoCloseable / try-with-resources。

JDK 21 中 finalize 已弃用并计划移除，不能作为可靠的资源释放时机。Cleaner 可承接部分兜底清理，但执行时机不确定，清理动作也不能反过来强持有被清理对象。Android 上相关 API 的可用版本要另行核对；不要把 HotSpot 的实现队列与线程安排当作两种运行时的共同协议。

参考：Java 引用与队列语义 · Android java.lang.ref · Cleaner 的生命周期要求 · finalize 的弃用说明。

类、反射与元数据生命周期

类也涉及生命周期：类加载器、Class 对象、实例，以及缓存中的 Method / Field 等反射对象可能组成持有链。长期缓存这些对象可能间接保留类加载器及其元数据。排查时沿真实引用链取证，不能仅凭“实例数量归零”认定类已经卸载；卸载支持与时机依运行时、收集器和类的种类而定。

反射允许在运行时取得类型与成员信息，反射对象本身也要纳入上述持有关系。成员访问仍受相应平台的访问控制约束；本节关注生命周期，类身份、加载和初始化统一见托管运行时基础，本节保留持有链与卸载视角。

参考：JLS：类与接口卸载 · Java 反射访问控制。

6. 分代、收集范围与记忆集

分代假说与对象晋升

分代利用对象寿命的经验规律：许多对象很快变得无用，已经存活较久的对象往往还会继续存活。于是可以更频繁地回收新分配对象所在范围，让长寿对象少参与昂贵的重复扫描。这是针对负载的优化依据，不是每个程序都必然满足的定律。

以传统分代布局作例子：新对象进入 Eden，年轻代回收把需要保留的对象复制到 Survivor 或晋升到老年代；后续回收可交换 Survivor 的角色。年龄是经历存活判定的计数，不是墙钟时间。晋升还受目标空间、年龄策略及对象大小等条件影响，不保证所有对象都先经过固定次数 Survivor。

G1 以 region 承载 Eden、Survivor、Old 等角色，同一代不必在地址上连续；具体流程见G1 实例。ART 的分代模式按其收集器协议划定年轻收集范围，不能直接套用固定 Eden:S0:S1 比例，也不能仅凭 RegionSpace 名称推导出与 G1 相同的分代规则。

根 → 老对象 A → 年轻对象 B
本轮只回收年轻范围：
  若只检查根直接指向的年轻对象，就可能漏掉 B
  还需要找到收集范围外指向范围内的引用

记忆集（remembered set）记录收集范围外指向范围内的引用信息，避免局部回收时重新遍历所有外部对象。卡表可作为粗粒度记录手段；它与记忆集不必是同一结构。标脏、重扫及并发协作统一见卡表与写屏障。

Young GC 只回收选定的年轻范围，但仍需根和跨代引用信息。Full GC 涉及更广收集范围；某实现仍会利用卡表扫描免收集空间或并发修改，不应简单说“Full 一定不用卡表”。GC 可因分配压力、目标堆占用、显式请求或运行时策略触发，最耗时阶段可能是根/卡扫描、对象扫描或复制等，要读阶段计时。

经典问题：扩大堆后，GC 必然更少且更快吗？

频率可能下降，但一次收集的活对象和扫描范围可能变大，物理压力也可能增加。应一起比较每秒 GC 次数、暂停分位数、总 CPU、复制字节、回收收益和 RSS/PSS；Young 与 Full 不存在固定耗时倍数。

参考：G1 分代布局与收集范围 · G1 记忆集 · ART 卡表。

二、并发标记与对象移动

本部分以前一部分的根、回收范围和记忆集为基础；先明确回收要维护的关系，再看并发修改与对象移动。

应用修改引用图、GC 标记和对象搬迁可能交错发生。下面分别讨论保持可达性、取得可靠根集合、访问正确对象和发布唯一副本的条件；HotSpot 的实现示例随对应机制说明。

7. 三色标记与并发漏标

颜色记录扫描进度，不是对象当前的生死

三色是逻辑状态，不要求对象头真有三个颜色值。白色表示尚未发现；灰色表示已发现但引用尚未扫描完；黑色表示已扫描完。可用标记位图和工作队列表达：已标记但仍待扫描的是灰色，已处理的是黑色。

初始化：对象视为白；从根发现的对象染灰、入队
循环：取一个灰对象，发现其白色后继并染灰、入队
      扫描完该对象后，将它视为黑色
终止：工作队列及线程缓冲中的待处理工作均已收敛
回收：本轮收集范围内仍白、且无特殊保留规则的对象

在图不变化的模型中，从根可达的节点会逐步被发现。强三色不变量是不存在黑对象直接指向白对象的边；白对象仍可由灰色前沿保护。下面的并发交错会破坏这一保证：

初态：根 → A（黑），根 → B（灰），B.ref → C（白）
应用：A.ref = B.ref    // 新增 A（黑）→ C（白）
应用：B.ref = null     // 删除灰色前沿通向 C 的最后一条路径
GC：  扫描 B，只看到 null；不会重扫已黑的 A
结果：C 仍白，却能从根经 A 到达，若回收便发生漏标

这是没有相应屏障保护、黑对象不再重扫的模型。关键是两个变化组合：黑到白的新边出现，且灰色前沿发现该白对象的路径被切断。仅出现一条黑到白的边不一定漏标；若 C 仍能被其他待扫描路径发现，就可能被保住。不同并发算法维护的不变量不同，SATB 也不要求始终没有黑到白边。

复习问题：如何修复上面的交错？

可暂停应用，固定引用图后扫描；也可在引用修改时记录必要信息，让并发标记恢复发现 C 的能力。必须连同根变化、分配期间的新对象和终止协议一起处理，不能只说“多加一个标记位”。

参考：Dijkstra 等：并发垃圾收集与颜色不变量。

浮动垃圾：对象后来不可达，本轮仍然保留

浮动垃圾指并发回收期间已经变得不可达，却仍按本轮存活信息保留、未在本轮回收的对象。原因在于应用继续修改引用，而本轮标记并不持续撤销已建立的存活判断。标记对象时它完全可能仍然可达，因此不能把原因概括为“GC 标错了”或“多标导致对象变成垃圾”。

假设 A.ref 是通向 B 的唯一强可达路径，且无特殊保留规则：
t0：根 → A → B，B 可达
t1：GC 已发现并扫描 B，B 为黑色；此时的标记正确
t2：应用令 A.ref = null，且没有其他根或引用保留 B；B 变得不可达
t3：本轮仍保留 B 的存活标记，不回收它；B 成为浮动垃圾
后续：覆盖 B 所在范围、重新判定可达性的收集才有机会回收它

若把本轮保留集合与回收结束时的实际可达集合比较，可把多保留的部分称作“多标”，但这是结果描述，不是浮动垃圾的独立成因。漏标则是仍需保留的活对象没有被正确保护；若因此回收，会破坏内存安全。浮动垃圾也不同于“业务不用、却一直被强引用链保留”的托管内存泄漏。

SATB 会保留标记开始时可达、随后失去引用的对象，即使它在失去引用前还没来得及被扫描。浮动垃圾也并非 SATB 独有：采用增量更新的 CMS 同样可能保留已标记、后来不可达的对象。不能仅靠更换这两种屏障策略就保证本轮回收所有新产生的垃圾。

参考：Oracle：CMS 的浮动垃圾与增量更新 · JDK 21 G1：SATB 保留起始存活对象。

8. STW、安全点与根扫描

STW（Stop-The-World）表示在一段协调窗口内暂停执行应用托管代码的线程；GC 工作线程仍可并行执行。并行描述多个工作线程一起做事，并发描述 GC 与应用的执行在时间上重叠。并行 GC 完全可能处于 STW。

HotSpot 在安全点等受控状态获取可靠的机器状态。编译代码的 OopMap描述特定程序位置的哪些寄存器或栈槽保存对象引用；不是把所有像地址的整数都当成对象。暂停请求到达后，各线程还要到达或被判定处于安全状态，因此“请求暂停”不等于“立即开始 GC 工作”。native 线程可以通过线程状态协议被视为安全，但返回托管执行前仍要遵守协调规则。

教材中的安全区域（Safe Region）可理解为一段无需继续执行托管代码、其引用状态仍可按协议处理的区间。阻塞或 sleep 线程不会因为没有抵达下一个轮询点就必然阻止 GC；关键是运行时能确认它的状态，并在重新进入托管执行前完成协调。不能把所有 JNI 调用都当成无需约束的安全区；ART 的线程根切换实例见ConcurrentCopying。

STW 可用于建立根快照、完成标记收敛或切换关键阶段；具体工作随收集器变化。G1 有并发标记，但 Young / Mixed 的疏散复制与引用更新在暂停中进行，Remark 也需要暂停。不能把“有并发标记”推导为“对象搬迁同样并发”。

观察一次延迟时分开看：
到达安全状态所需时间 → 安全点内的 GC / VM 操作时间 → 恢复应用
另看整轮 GC 墙钟时间、累计 CPU、分配停顿与应用尾延迟
复习问题：有读屏障是否就能完全消除 STW？

不能据此保证。读屏障主要让应用安全地使用引用，根处理、阶段切换和工作收敛仍需要协议。有些工作能改成并发扫描或线程握手，但必须说明具体收集器和版本；更短暂停也可能付出屏障、CPU 和预留空间成本。

参考：JDK 21 G1：并发标记与暂停疏散。

屏障解决的不同问题
机制记录或检查什么在漏标例子中的作用
SATB（起始快照）写前屏障覆盖引用前，记录旧引用；标记线程处理缓冲覆盖 B.ref 前保留 C，使起始快照中的存活关系仍可被追踪

SATB 的逻辑是保存标记起始时的可达快照，实际可保守地多留对象；它不要求任何时刻都严格满足“没有黑到白边”。本轮开始后分配的对象也有专门保护规则。卡表屏障与 SATB 屏障可以出现在同一次写入周围，但服务于不同目的。

写引用(slot, new):                   // SATB 概念伪代码
    old = *slot
    若本轮标记需要：把 old 记入线程缓冲
    *slot = new
    若需跨区域追踪：记录 slot 所在区域

读引用(slot):                        // 并发移动的概念伪代码
    old = *slot
    若 old 为空或状态已满足要求：返回可用引用
    current = 运行时解析或协助迁移(old)
    尝试有条件地将 slot 中的 old 修复为 current
    返回 current

上述仅表达职责，省略内存序、标记队列并发、弱引用、阶段状态和机器码优化，不能直接实现为普通 C++ 并发读写。修复槽通常需要比较交换等协议，避免把应用同时写入的新值覆盖掉。快速路径让多数正常引用低成本通过；慢路径才处理需要修复的情况。

读屏障不是所有移动 GC 的必需配置。例如 G1 在疏散暂停中移动对象并更新引用，应用恢复后使用已更新的引用；ZGC、ART CC 则通过各自的屏障和阶段协议，让应用与对象移动并发执行。上面的读引用伪代码只表达某类并发移动方案，不能套到所有收集器。

GC 屏障与 CPU 内存屏障不同。前者维护对象图或引用有效性；后者约束内存访问排序和可见性。GC 屏障内部可能使用原子操作或排序指令，但一个 acquire load 不会自动找到搬迁后的对象。

复习问题：ZGC 是不是只有读屏障？

不能这样概括。JDK 21 的分代 ZGC 同时有 load 与 store 屏障：普通强引用 load 路径负责取得可用的对象地址，store 路径参与标记及代际引用维护；弱引用等访问还有专门处理。非分代 ZGC 的职责分配不同，回答时必须限定模式和版本。

9.1 卡表：把引用修改变成可重扫的范围

卡表把一段堆地址划成固定大小的 card，用小型表项记录相应范围是否需要处理。例如对象 A 执行 A.child = B，写后屏障可把 A 所在的 card标脏；它记录可能含有新引用的位置，不是给 B 贴上“活对象”标签。

示意：假设一张 card 覆盖 512 字节（仅为算例）
card_index = (对象 A 的地址 - 堆起点) / 512
A.child = B
card_table[card_index] = dirty

后续扫描该 card 覆盖的对象 / 引用槽，再判断目标是否需要处理。
多个字段共用一张 card，所以标脏是保守记录。

它有两类常见用途：局部回收找入边，例如只收年轻代时重新检查老年代脏卡；并发标记补查修改，例如重扫标记期间发生过引用写入的对象范围。卡表是记录手段，具体算法决定何时标脏、处理后如何清理，以及与并发写入怎样协调；不能把所有卡表都限定为“老年代到新生代”。

Remembered set 表达需记住的跨区域引用信息，可能由脏卡细化生成，也可能采用其他表示；不一定就是卡表本身。SATB 缓冲记录旧引用，脏卡记录需重查的源范围，信息不同。ART 的常规字段写屏障以非空引用写入为条件之一，调用卡表的 MarkCard(dst)；CC 与下文 CMC 如何消费这些信息须分别看阶段协议。

参考：Android 14：字段写屏障 · ART 卡表。

10. 对象移动、转发与身份

假设对象 O 从 0x1000 复制到 0x9000，堆字段、栈槽或寄存器仍可能暂时保存旧引用。转发信息表达“旧对象位置 → 权威新位置”，让这些引用最终指向同一个对象。实现可以借用旧对象头、设置额外间接指针或建立旁路转发表；不能一概说“转发地址永远存在 Mark Word”。

复制前：p ─┐
          ├→ O @ 0x1000
        q ─┘
复制后：转发表 0x1000 → 0x9000（O 的权威副本）
        p 已更新 → 0x9000
        q 仍为旧引用 → 经屏障解析 → 0x9000
  1. 唯一性：GC 线程和应用线程可能同时尝试迁移同一对象。发布转发结果需要原子协议，使观察者收敛到唯一新地址；允许投机复制的设计还必须处理竞争失败的副本。
  2. 可见性与写入：新地址可供解引用前，副本初始化必须满足发布协议。应用的字段写入也须与搬迁协调，否则写在旧副本上的更新可能丢失；并非有一条转发记录就自动正确。
  3. 身份与元数据：多个别名仍要指向同一对象，身份哈希、锁等状态也必须保留或转移。地址变化不应改变语言层的对象身份。
  4. 回收时机：旧存储与转发元数据的寿命未必相同。只有旧引用已被更新，或仍能由可靠元数据安全解析时，才可按协议复用旧区域；不能在无保护下把旧地址重新解释成另一个对象。
复习问题：两个线程复制同一个对象，为什么不能各用自己的副本？

那会把一个对象分裂成两个身份：通过 p 的写入可能无法通过 q 观察到。需要原子决定权威副本；未获胜者转向已发布的新地址，而不是仅保证两份初始内容相同。

11. HotSpot G1 的区域与回收周期

区域角色与回收集合

以 JDK 21 HotSpot G1为例，堆由等大的 region 组成，分别承担 Eden、Survivor、Old 或空闲空间等角色。一次暂停选定的回收集合称为 collection set；记忆集帮助找到集合外的入边，疏散把集合中的活对象复制到目标区域。区域属于某一代，不要求整代在地址上连续。

大对象可走 Humongous 区域路径，在老年代取得连续的 region。此时即使总空闲量不少，也可能受连续区域不足与末尾浪费影响。不能把“G1 按 region 管理”理解为任何对象都可以拆开塞进任意空闲小块。

把标记、屏障与疏散连成一轮

  1. 年轻代收集：Normal Young 暂停回收年轻区域，复制存活对象并按策略晋升，老年代占用逐步变化。
  2. Concurrent Start：达到并发周期的启动条件后，在一次年轻代暂停中启动标记工作。
  3. 并发标记：与应用一起运行，使用前文的 SATB 机制保留起始存活信息；期间仍可能发生普通年轻代暂停。
  4. Remark / Cleanup：用暂停完成标记收敛和相关处理，并确定后续区域回收所需状态；二者之间还有并发工作，不能把整段统称为一次暂停。
  5. 混合收集：进入空间回收阶段后，在多次 Mixed 暂停中回收年轻区域及选定的老年代区域，随后回到以年轻代收集为主的阶段。

这是常见周期主线，具体执行可因回收收益等条件跳过后续工作。并发标记判断哪些对象需要保留；Young / Mixed 的对象疏散和引用更新仍在暂停内完成。SATB 与卡表屏障分别服务标记和区域引用追踪，不能互相替代。

若疏散目标空间不足，会出现 evacuation failure；若后续分配与回收仍无法维持运行，可能退回 Full GC，仍不足才可能报告 OOM。一次疏散失败不等于立刻 OOM。排查时联合观察老年代增长、Humongous 区域、并发周期是否赶得上分配，以及各暂停阶段耗时。

G1 的暂停时间是预测目标，不能保证每次都小于某个毫秒数，也不承诺固定吞吐率。固定年轻代比例可能限制它调节暂停工作量的能力；调优应从日志与负载出发。

参考：G1 区域与周期 · G1 暂停、疏散失败与诊断。

Image / Zygote 等空间启动映像、预加载与共享相关，收集中的处理方式依空间属性

在 AOSP android-14.0.0_r1 中，ShouldAllocLargeObject 同时检查大小阈值，以及对象是否为原始类型数组或 String。因此“任意超过 4 KB 的对象都进入 LOS”不成立；阈值也不是所有设备固定常量。降低阈值可能减少其他空间压力，却增加独立大块分配、碎片和映射管理成本。

复制预留空间用于容纳迁移中的活对象。逻辑堆上限、RegionSpace 映射容量、疏散预留和实际物理占用不能互相替代；经典半空间模型的二倍存储直觉不能直接当作所有 ART 配置的固定比例。

为什么区分 RegionSpace 与 LargeObjectSpace

RegionSpace 让分配与回收以区域组织：线程可从区域取得 TLAB，用指针推进完成常见小对象分配；收集器按区域状态和存活情况选择迁移与复用。空闲区域易于整批回收，代价是区域管理、尾部浪费以及复制期间的目标空间需求。这里的 region 是 GC 管理单位，不是操作系统的一页。

对大型数组，复制存活载荷的带宽成本可能很高；LOS 用不同的分配与回收策略，减少反复搬动大块数据的必要。它并非没有成本：仍需追踪存活和释放，可能需要映射管理或连续空闲块，也未必能靠压缩消除碎片。

该版本把原始类型数组和 String 纳入候选，与其主要载荷无需按普通对象引用数组逐项扫描、以及 LOS 的卡表覆盖边界有关。不能由此推导“LOS 对象完全没有对象头引用”，也不能把对象引用数组一律送入 LOS。RegionSpace 本身仍支持大对象区域及尾部区域；对象大、RegionSpace 的大对象表示、进入独立 LOS是三个不同判断。

该版本 HeapReference 内部保存 Atomic<uint32_t>，PtrCompression 负责与实际对象指针转换，并可处理引用 poisoning。它不是普通 native 指针大小，也不是 JNI jobject；扩大可寻址对象范围可能涉及引用编码、空间布局和访问路径，不能只改一个容量数字。

参考：Android 14 分配判断 · HeapReference 与转换 · RegionSpace。

13. ART ConcurrentCopying 的阶段安排

以 AOSP android-14.0.0_r1 的 ConcurrentCopying 为具体例子，RunPhases 的主线如下。不同配置会选择不同分支，不能把 CC 概括成“全程暂停复制”。

  1. InitializePhase 准备本轮状态；特定分代全堆场景先执行 MarkingPhase，计算存活情况。
  2. 启用相应读屏障入口、处理需要的卡信息，再通过 FlipThreadRoots 协调线程根与空间状态切换。
  3. CopyingPhase 与应用并发推进：复制需迁移的活对象，扫描引用、处理标记工作；读屏障帮助访问获得正确对象。
  4. ReclaimPhase 回收可释放区域，FinishPhase 收尾并更新统计。验证选项可能额外引入暂停。

这里的读屏障承担前文所述的引用访问协作职责；算法定义和 CPU 内存屏障的区别见屏障机制。具体检查、复制和标记条件须对照该版本源码。

Baker 读屏障：从持有者状态取得可用引用

以此版本的 Baker 字段读路径为例，读取 A.child 时检查的是持有字段的 A 的读屏障状态。普通路径直接得到引用；若 A 为灰色，则进入 Mark 慢路径，必要时复制目标、查询转发结果或参与标记，返回当前可用的对象引用。根读取有自己的状态检查，不能把字段读伪代码套到所有根。

字段读的概念流程（省略内存序与并发发布细节）：
  检查 holder 的读屏障状态
  ref = holder.field
  若 holder 为灰色：ref = Mark(ref)
  返回 ref

Mark 内部按空间、标记和转发状态处理，
不是每次读取都复制一次，也不是每次都查全局哈希表。

真实实现用状态读取与引用读取间的排序协议保证正确性，部分路径还会有条件地修复原引用槽。对象搬迁前后的别名要收敛到同一权威副本；复制竞争中的发布与失败副本处理见 ConcurrentCopying::Copy。选用 table-lookup 读屏障时快速检查不同，不能与 Baker 条件混写。

读屏障与卡表写屏障分别负责什么

CC 的读屏障参与保证当前读到的引用符合移动与标记协议；卡表写屏障记录引用图发生修改的源对象范围，供区域或代际扫描使用。例如老对象新增指向年轻对象的字段，仅让读取者取得新地址，并不能替代下一轮局部收集需要的入边记录。两者配合根切换、工作队列与终止协议，才构成完整收集器。

参考：Baker、table-lookup 与根读屏障。

经典问题：并发复制时为什么仍可能暂停？

切换线程根、同步关键状态等步骤需要与应用线程协调。大量复制可并发执行，但这不意味着无暂停；区分 GC 总耗时、暂停时长和应用受到的 CPU/屏障开销。

14. ART CMC：以页面访问协调并发压缩

这里的 CMC（Concurrent Mark Compact）指 AOSP android-14.0.0_r1 的 MarkCompact 实现。先标记活对象并规划压缩后的位置，再在应用运行期间逐页准备可访问的内容。移动空间来自 BumpPointerSpace；不能把 CC 的 RegionSpace 疏散过程直接改名为 CMC，也不能仅凭版本号推断某台设备实际选用它。

从标记到压缩：哪些阶段需要协调

  1. 初始化与并发标记：建立本轮状态，从根追踪对象；通过卡信息等处理并发修改，并预清理待重扫范围。
  2. 标记暂停：补充根与标记工作，撤销线程本地分配缓冲，建立后续新分配对象的处理边界。暂停后应用仍可继续分配，必须把这批 black allocation 纳入协议。
  3. 回收与压缩准备：处理可回收的非移动空间等工作，按存活信息计算移动对象的新位置和页面处理所需元数据。
  4. 压缩切换与线程根协调：更新根，安排旧内容保留和目标地址范围的映射，建立页面访问的拦截与处理条件；这一转换不能任由应用观察半完成状态。
  5. 并发压缩与收尾：后台推进页面整理，按访问需要完成尚未准备的页面，更新其中的对象引用；待工作及故障处理收敛后，撤销临时状态并释放可回收资源。

这是源码阶段的职责概括，实际顺序以 RunPhases、MarkingPause、CompactionPause 和 CompactionPhase 为准。功能不可用时存在 fallback 分支，部分压缩工作转入暂停；“并发压缩”不承诺任何配置下都无暂停。

userfaultfd 在 CMC 中解决什么问题

userfaultfd 让用户态为注册的地址范围接收和处理特定类型的页故障。在常见事件处理模型中，访问线程等待；处理线程通过文件描述符取得故障地址，准备好内容后用 ioctl 让该页可访问，访问线程再继续。它不是每次内存访问都调用的系统调用，也不是简单地“所有写入都触发写保护”。

简化的 CMC 页面场景：
旧内容仍可供收集器读取，根已按压缩计划调整
  应用访问目标页 P，P 尚未准备完成
    → 触发受管理的页故障
    → 收集器从旧内容构造 P，调整 P 中需要更新的引用
    → 按当前模式安装 / 放行完整的 P
    → 应用继续访问
  后台线程也可提前完成其他页面，避免等到访问时才处理

missing 模式可用 UFFDIO_COPY 提供内容，minor 模式可在处理已有页面后用 UFFDIO_CONTINUE 放行；具体支持范围取决于内核和映射类型。该 ART 分支还区分工作线程处理、SIGBUS 协作等路径，不能把上面的教学流程当成唯一实现。页故障基础复用操作系统中的访存流程，这里关注它如何服务对象压缩。

参考：Linux：userfaultfd 的注册、通知与页面完成 · Android 14 MarkCompact：阶段、映射准备与并发压缩。

区分泄漏、峰值与容量不足

托管对象泄漏通常是“业务已经不需要，引用链仍让它可达”。例如长寿缓存一直保留请求结果，或异步任务一直持有已退出的页面。GC 正确地保留了可达对象，问题在持有关系；这与 native 中丢失指针却未释放存储的泄漏表现不同。

  1. 先确认是 Java 堆分配失败、native 分配失败、地址空间/碎片问题，还是系统杀进程；保留日志和构建信息。
  2. 记录失败申请大小、存活量、堆目标/上限、GC 前后变化及进程内存分类。
  3. 对比多轮相同业务的 heap dump，沿 GC Roots 引用链查不必要的持有；native 增长另查分配调用栈。
  4. 应用侧减少峰值同时存活数据、按需加载、缩小图片/缓存、及时取消任务；修复引用链后用同负载复测。

若相同业务往返后，回收后的存活量持续上升，优先查长期持有；若只有并发峰值时分配失败、峰值后能恢复，优先查同时存活的数据规模；若稳定负载始终超过容量，再评估资源预算。单次占用高不能独自证明泄漏，回收前后采样也要保证口径可比。

HPROF 是堆转储格式之一，可用于分析托管对象和引用。dump 本身有开销，且不覆盖所有 native、映射或图形资源；“Java 堆不涨”不能排除进程内存问题。

从大小排名走到支配关系

Shallow size是对象自身占用；retained size是在相应引用处理规则下，该对象不可达时可随之变得不可达的对象集合大小。一个很小的容器可能保留大量数组，而一个大数组未必能因删除某一条引用就回收。

若从根到 Y 的所有保留路径都经过 X，则 X 支配 Y。堆分析的 dominator tree 用于汇总保留关系，但树边不一定是原始对象的直接字段引用；它也不是编译器 CFG 的支配树，虽然用到了相似的图论定义。

根 → Cache → Entry → byte[]
若数组只有这条保留路径，Cache 可支配数组。

另一个根 → Worker ─────────→ byte[]
加入这条路径后，移除 Cache 仍不能使数组不可达。

先用数量 / retained size 排名选候选，再查看通向根的真实引用路径与业务生命周期。分析器是否排除弱 / 软引用、dump 采集时机和活对象处理方式都会影响解释，不能把对象浅大小相加就当成进程 RSS。

先确认 Page 在业务上已结束，再查 owner 字段赋值处、listener 的创建和注册调用栈，以及退出、取消和异常分支的清理代码。heap dump 展示采样时的对象图，通常不能单独还原历史分配调用栈；需要分配记录、日志或可重复调试补齐“何时、由谁创建”。

修复应让拥有注册关系的组件在适当生命周期释放它，例如保存注册句柄并在退出时关闭，处理重复注册、异常和仍在执行的回调。仅把某个局部变量设为 null，不能解除 Registry 中的强引用；直接改成弱引用也可能让本该存活的回调过早消失。

复测使用相同次数的进入 / 退出，等待任务取消与清理完成，在可比采样条件下比较已退出页面数量、根路径和回收后存活量。若仍有第二条路径保留 Page，解除第一条路径不等于问题已经解决。

两个增长案例：长期持有与并发峰值

以下是排查示意，不是实测数据。案例一：每次进入页面注册 listener，退出后忘记从长寿 Registry 移除；listener 捕获页面，页面保留图像缓冲。重复相同进出操作后，观察回收后的页面数量和保留量，沿 Registry → listener → page 取证。修复注册 / 注销与取消协议后，重复同样负载，并给异步清理足够的完成条件；只有内存下降而没有确认这条关系被解除，还不足以证明原因。

案例二：多个请求同时解码大图，处理结束后存活量能回到基线，但并发时分配失败。记录同时存活任务数、输入尺寸、失败申请与 GC 后可用量，检查是否是容量或连续空间压力。通过限制并发、分块处理或减少解码尺寸降低峰值，再检查延迟与吞吐代价。此时仅寻找永久持有链可能查错方向。

若托管堆稳定而 RSS 增长，转看 native 分配、映射、图形资源或分配器保留，不应强行套入上面两个 Java 堆案例。

16. GC 与编译器、ABI 的协作

要点回顾：三色标记用白、灰、黑表达发现和扫描状态，颜色不等于对象当前是否可达。应用修改引用，既可能让尚需保留的对象逃过扫描，也可能让本轮已保留的对象变成浮动垃圾；前者必须由正确的标记协议防止，后者可留待后续收集。STW 阻止应用在协调窗口内修改对象图，并发阶段则依靠相应屏障与根处理协议。移动对象后，G1 在疏散暂停中更新引用，ZGC / ART CC 则使用各自的读屏障等机制协调并发访问；不能把读屏障视为所有移动 GC 的共同步骤。

复习问题：GC 为什么需要编译器和 ABI 配合？

GC 需要知道机器状态里哪些值是引用；编译器生成安全点信息并插入所选收集器需要的屏障，调用约定又规定值如何跨调用保存。异常展开需要恢复上一帧，但 DWARF CFI 描述恢复规则，OopMap 描述对象引用位置，二者不是同一份信息。

复习问题：malloc 的指针为什么通常不能这样搬？

普通 native 调用者可以复制、隐藏裸指针，分配器没有完整根集合和编译器屏障协作，不能擅自移动已交付的活块。realloc 可以返回新地址，但必须由调用者更新使用方式；详见malloc 专题。
