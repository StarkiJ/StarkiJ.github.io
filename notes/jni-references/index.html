1. 调用边界与线程

JNI是托管代码与 native 代码交互的接口。Java/Kotlin 声明 native 方法并加载相应库；运行时通过名称匹配或 RegisterNatives 找到 native 实现。普通实例 native 方法接收 JNIEnv* 和 jobject，普通静态方法接收 JNIEnv* 和 jclass，再接收显式参数。特殊优化调用约定另有约束。

JavaVM用于取得线程的运行时接口；JNIEnv与当前线程关联，不能从一个线程缓存后交给另一线程使用。native 创建的线程需要先附加到 VM，使用自己的 JNIEnv，并在自己负责附加的线程退出前 detach。

经典问题：把主线程的 JNIEnv 放进全局变量，工作线程继续使用可以吗？

不可以。缓存 JavaVM，在工作线程调用 GetEnv；若尚未附加再 AttachCurrentThread。JNIEnv 和 local reference 都不能因此跨线程复用。

参考：Android JNI：线程与接口。

2. Local、Global 与 Weak Global

引用种类
引用有效期 / 回收影响释放
local reference属于线程与本地引用帧；普通 native 调用返回时自动清理，存在期间保持相应强可达性可提前 DeleteLocalRef；循环中可配合 Push/PopLocalFrame
global reference跨调用有效并强持有对象；跨线程使用时仍需当前线程的 JNIEnv 和业务同步DeleteGlobalRef
weak global reference句柄存在不阻止目标被 GC；使用前须提升并检查DeleteWeakGlobalRef

jobject 是运行时管理的引用句柄，不应作为普通 C++ 对象地址解引用。两个句柄可能指向同一个 Java 对象却有不同值，判断对象身份用 IsSameObject。jmethodID/jfieldID 是成员标识，不是 local/global 对象引用。

jobject strong = env->NewLocalRef(weak);
if (strong != nullptr) {
    // 使用 strong；不能先检查 weak 未空，再直接依赖 weak
    env->DeleteLocalRef(strong);
} else {
    // 目标可能已回收；还需按接口规则检查是否存在待处理异常
}
经典问题：native 线程一直运行，local reference 会自动很快回收吗？

不能这样假设。附加的 native 线程若没有不断返回的 Java→native 调用帧，局部引用可能持续保留到显式删除、弹出本地帧或线程 detach。循环创建对象应主动控制局部引用数量。

3. 创建对象与访问成员

设计规范：引用、方法绑定与对象访问。

  1. 取得目标类：由参数传入、GetObjectClass，或在正确类加载器上下文中 FindClass。
  2. 按名字与签名取得构造器/方法/字段 ID，区分 static 与实例接口。
  3. 用 NewObject 分配并调用指定构造器；访问字段用 Get/Set<Type>Field，调用方法用匹配的 Call<Type>Method。
  4. 检查空返回和待处理 Java 异常；清理自己持有的引用与缓冲，再返回或按约定处理错误。
示例：从 native 构造一个 Integer 
#include <jni.h>
// 对应 Java: package demo; class Native { static native Integer box(int n); }
extern "C" JNIEXPORT jobject JNICALL
Java_demo_Native_box(JNIEnv* env, jclass, jint value) {
    jclass type = env->FindClass("java/lang/Integer");
    if (!type) return nullptr; // 保留待处理的 Java 异常
    jmethodID ctor = env->GetMethodID(type, "<init>", "(I)V");
    if (!ctor) { env->DeleteLocalRef(type); return nullptr; }
    jobject result = env->NewObject(type, ctor, value);
    env->DeleteLocalRef(type);
    return result; // 允许把有效 local ref 作为此次 native 调用结果返回
}

这是需接入 Android/JNI 工程的函数示例，不是独立 main 程序。NewObject 得到 local reference；返回给 Java 是合法路径。AllocObject 则不调用普通构造器，不能无条件代替 NewObject。调用实例、静态或显式非虚方法要选择对应 API。

经典问题：有待处理 Java 异常时，还能继续任意调用 JNI 吗？

不能。许多 JNI 操作此时不允许调用；应检查异常，执行允许的清理操作并返回，或明确清除并处理。也不要让未处理的 C++ 异常穿过 JNI 边界。

参考：JNI 函数规范。

4. GC 与 native 缓冲

GC 追踪有效 JNI 强引用，并通过运行时引用机制维持对象移动后的可访问性。native 保存的任意裸地址不因此成为 GC Root。GetStringUTFChars、Get<PrimitiveType>ArrayElements 等接口可能提供副本或受约束的直接访问，必须与对应 Release 配对。

数组 Release 的 mode 决定是否回写和是否释放副本；JNI_COMMIT 不是最终释放，仍需完成对应释放。Critical 接口期间应尽快结束，遵守不能任意阻塞或执行其他 JNI 调用等约束。GetStringUTFChars 使用 Modified UTF-8，不能把所有 JNI 字符串接口都当作普通 UTF-8。

常见泄漏或持有问题
原因修复方向
NewGlobalRef 无匹配删除为持有者定义明确关闭时机；用当前有效 JNIEnv 清理
local reference 在长循环积累及时删除或使用本地帧
字符/数组缓冲未 Release建立成对作用域清理，覆盖异常与提前返回
native 自己 new/malloc 后未释放由 C++ 所有权与 RAII 负责，Java GC 不自动接管
经典问题：Java 对象已经没有 Java 变量引用，为什么还活着？

可能仍被 JNI global reference、线程、静态字段、回调或其他根路径持有。查看引用链和 JNI heap 视图；不要仅根据某个方法已经返回判断可回收。

5. 边界设计

减少细粒度跨 JNI 调用，批量传递必要数据；异步任务要同时管理 Java 引用、native 对象和线程生命周期。缓存类时需要有效 global reference，并考虑类加载器；线程附加本身不会自动获得应用所需的类加载器上下文。

Java 的 StringBuffer 为常见方法提供同步，而 StringBuilder 不提供这层同步；即使单个方法受保护，“先检查再修改”这样的多步业务操作也可能需要外部同步。这与 C++ string 的线程安全规则需分别理解。

参考：JNI 最佳实践与检查 · StringBuffer API。
