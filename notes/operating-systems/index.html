1. 进程、线程与调度

1.1 进程资源与线程共享

进程是资源与地址空间的组织单位；线程是进程内的一条执行流。Linux 将可调度实体表示为任务，同一进程中的线程可在不同 CPU 上同时运行。用户态协程是否被内核单独调度，取决于它如何映射到内核线程。

同一进程内的常见共享关系
共享各线程独立
虚拟地址空间：代码、全局数据、堆、映射寄存器上下文、执行位置、线程栈、线程局部存储
文件描述符表等进程资源线程 ID、信号屏蔽字、调度相关属性

“每个线程有自己的栈”是分配与执行习惯，不是隔离边界：只要得到地址，其他线程也可能访问该栈中的对象，仍须满足生命周期与同步规则。

1.2 上下文切换与调度成本

上下文切换保存当前任务的寄存器与调度状态，恢复另一个任务。切换进程还可能涉及地址空间切换；成本也受缓存/TLB、内核实现和硬件影响。阻塞任务不持续占用 CPU；就绪任务等待调度。

经典问题：加一个监控线程是否没有成本？

有栈和管理结构的内存成本，也有唤醒、调度、采样和锁竞争成本。周期较长且工作很少时可能较低，但需测量 CPU、延迟和内存，而不能仅根据线程数量判断。

参考：POSIX 线程共享属性。

1.3 系统调用：进入内核不等于切换线程

系统调用是用户程序请求内核服务的受控入口。以 Linux arm64 为例，libc 包装函数按系统调用 ABI 放置参数，用 svc #0触发同步异常；内核保存必要的用户状态，按调用号分派、校验参数与权限，完成服务后通过异常返回恢复用户执行。普通 bl / ret调用只改变函数控制流，不能因此取得内核权限。

系统调用 ABI 与普通函数 ABI 分别定义
内容Linux arm64 约定
调用号与进入指令w8 保存调用号，执行 svc #0；具体号码来自目标系统头文件
最多六个系统调用参数x0–x5；不同于普通 AAPCS64 的整数参数规则
主要返回值x0；常见错误以负 errno 返回，libc 包装再转换为 -1 并设置 errno
// Linux arm64 的 .S 片段，调用号由目标头文件提供
#include <asm/unistd.h>
get_pid_raw:
    mov w8, #__NR_getpid
    svc #0                  // 进入内核；返回后从下一条指令继续
    ret                     // 再返回本函数的调用者

这个片段演示无参数的 getpid，不是完整的通用 syscall 包装器。内核态切换可以一直由同一个线程执行；只有发生阻塞、抢占等调度事件时才可能换线程。系统调用也可能睡眠后再返回，不能承诺它总在一次连续 CPU 时间内完成。普通访存触发的缺页异常可以进入内核，却不是程序主动执行的 syscall。

库接口和系统调用不是一一对应：malloc 常先复用用户态空闲块；某些时间查询可通过 vDSO 完成，避免实际陷入内核。排查时区分“调用了库函数”和“确实执行了系统调用”。普通参数传递与寄存器保存规则见AArch64 函数调用。

参考：Linux syscall ABI · vDSO 与用户态服务入口。

2. 虚拟内存与堆栈

2.1 地址映射与驻留内存

虚拟地址是进程使用的地址；页表记录虚拟页到物理页或其他状态的映射与权限，MMU 执行地址转换，TLB 缓存常用转换。虚拟地址空间中可有代码、数据、堆、栈、共享库、文件映射和未映射空洞。

保留一段地址、建立映射、分配物理页、成为驻留页是不同事件。匿名映射可以按需触页；文件映射可从文件恢复内容；相同物理页也可能被多个进程映射。因此虚拟空间大小、已分配对象大小和 RSS 不相等。

2.2 缺页、权限与访问故障

访问时的常见情况
页或访问状态可能处理
有效且驻留、权限满足正常读写
合法映射但尚未准备物理页缺页异常后分配页、装入文件页或处理交换等，再重试
写入写时复制页复制需要私有化的页并更新映射，再继续
未映射或权限不允许内核通常向线程送 SIGSEGV；部分映射错误可能是 SIGBUS
经典问题：没有物理页就一定崩溃吗？

不一定。合法的按需分配、文件页装入或写时复制都可通过缺页处理完成。只有访问无法按映射与权限规则满足时才进入故障路径；“缺页”本身不是错误结论。

页权限检查主要限制映射的访问方式，不能识别同一可写页内的所有对象越界或释放后访问。更细粒度的标签检查见ARM64 MTE：标签与访问检查。

2.3 一次访存：地址转换、缓存与缺页

以用户线程的一条普通 load 为例：指令根据寄存器和偏移形成虚拟地址，硬件取得地址转换与权限信息，并通过数据缓存或更低层存储取得数据。以下是职责关系，不是所有处理器必须顺序执行的流水线；地址转换和缓存查找可能部分重叠。

指令形成虚拟地址
  ├─ TLB 命中：取得缓存的转换及访问属性
  └─ TLB 未命中：AArch64 硬件遍历页表，取得有效转换时可填入 TLB

地址转换与权限检查（TLB 命中仍须满足权限）
  ├─ 满足：继续取得数据
  └─ 无法满足：触发异常，进入内核
        ├─ 合法按需分配 / 文件页 / COW 等：准备页面，更新页表
        │     按要求维护转换缓存，返回后重试访问
        └─ 无法满足访问：按故障类型处理，可能送出信号

转换与权限满足后取得数据
  ├─ 数据缓存命中：从缓存取得数据
  └─ 未命中：由缓存层次 / 一致性协议从更低层或内存取得
访问完成：load 的结果成为指令后续计算可使用的值

假设采用 4 KiB 页，虚拟地址 0x12345678 的页内偏移为 0x678。若对应虚拟页映射到物理页框 0xABC，其物理地址就是 0xABC678。这是地址换算示意：实际页大小、页表层级、大页与缓存组织依平台。缓存以 cache line 为单位管理数据，页以页表映射粒度管理地址，二者不是同一种分块。

不要把三种现象都叫作缺页
现象缺什么通常由谁推进
TLB miss缓存中没有所需的地址转换AArch64 页表遍历硬件；页表有效时不必进入内核
cache miss当前缓存层没有所需数据行缓存与内存系统；不因此自动产生缺页异常
page fault / 访问异常当前页表状态不能直接满足访问内核检查映射、权限及页面状态，决定修复还是报错

内核管理的虚拟内存区域记录“这一段地址允许怎样使用”，页表记录当前访问所需的映射状态。因此合法区域暂时没有可用页表项不等于非法地址。TLB 命中也可能因缓存的权限不允许此次写入而产生访问异常；写 COW 页就是内核可能修复的一类情况。处理需要 I/O 或等待资源时，线程可能被挂起；缺页并不都意味着读取磁盘。

store 同样需要地址转换与写权限，还会经过写缓冲、缓存和一致性协议等机制；指令完成不等于数据已经写到 DRAM，更不等于已经持久化到文件。这里解释普通内存的职责路径，设备内存、特殊指令和具体微架构另有访问约束。

经典问题：普通读内存需要每次执行系统调用吗？

不需要。转换和权限已满足时，硬件直接完成访问；只有需要内核介入的访问异常才转入内核处理。TLB miss、缓存 miss 本身也不等于一次系统调用。

参考：Linux 页表与缺页处理 · 页表修改与 cache/TLB 维护。

2.4 mmap：建立映射之后发生什么

mmap把一个地址范围与匿名内存或文件内容关联，并设置访问保护。它返回虚拟地址，失败返回 MAP_FAILED；建立映射不保证已为所有字节准备独占的物理页。访问过程复用上面的地址转换和缺页路径。

来源与共享方式是两个维度
选择含义注意点
匿名 / 文件匿名映射初始内容为零；文件映射对应指定文件范围匿名零页可按需准备；文件映射也不等于立刻读入整个文件
MAP_PRIVATE对映射的修改按私有写时复制语义处理写入不通过该映射回写原文件，也不据此更新其他映射
MAP_SHARED修改可由映射同一底层区域的其他进程观察并发读写仍需同步；文件持久化时机还需相应同步与文件系统保证
PROT_READ / WRITE / EXEC请求读取、写入、执行等保护属性映射和文件权限等必须允许；改变保护不等于改变语言层对象生命周期
匿名私有映射示意（Linux，伪代码；不是本机实测）：
page_size = sysconf(_SC_PAGESIZE)
p = mmap(NULL, 2 * page_size, PROT_READ | PROT_WRITE,
         MAP_PRIVATE | MAP_ANONYMOUS, -1, 0)
检查 p != MAP_FAILED
写入 p[0]                 → 为相应页满足写访问，可能触发按需分配
写入 p[page_size]         → 访问另一页，实际提交方式依配置
munmap(p, 2 * page_size)  → 解除映射，所有旧地址别名停止使用

通常让内核选择地址；随意使用 MAP_FIXED 可能覆盖已有映射。文件偏移须满足页对齐要求，解除映射的起始地址也有对齐约束，页大小应查询平台。文件映射建立后可以关闭原文件描述符，映射不会因此自动消失；越过文件有效范围访问则可能产生 SIGBUS，不能把 mmap 当作无限扩展的字节数组。

malloc 管理细粒度块，可能复用已映射空间，也可能向系统申请新映射。free 交还给分配器，munmap 则解除进程映射；两者的操作对象和成本不同，详见原生分配层次。

参考：mmap / munmap · 文件映射同步。

2.5 线程栈与动态分配

线程栈通常承担调用帧和未被优化消除的局部存储；动态分配器管理可复用内存块，并按需向系统申请映射或扩展相关区域。new 一般先申请存储再构造对象，不等于每次都调用内核。free/delete 释放到分配器后，页可能暂时仍保留。

对象释放、分配器保留和页面归还分别讨论，见原生内存的层次与free 与页面归还；GC 堆上限问题见扩堆与 OOM。

参考：mmap 与页映射 · 内存统计。

3. 进程创建与写时复制

进程创建将执行流与资源和地址空间联系起来。下面以 Linux 的 fork 为例。

fork为子进程建立独立地址空间。Linux 通常用写时复制共享父子原有私有页，写入时再私有化；只读数据无需立即复制。MAP_SHARED 映射另按共享语义处理。多线程进程 fork 后子进程只有调用者线程，却可能继承其他线程持有的锁状态，后续操作有严格限制。

4. 进程间通信

4.1 通信机制与适用边界

IPC 机制
方式数据如何传递适用与边界
管道 / FIFO内核缓冲区中的字节流常用于流式连接；消息边界需协议

5. 锁、futex 与死锁

5.1 互斥锁与 futex

互斥锁让同一时刻只有一个执行流进入受保护区；它还建立必要的同步关系。Linux 上常见实现先在用户态用原子操作竞争，竞争严重时通过 futex 等待/唤醒，避免一直忙等。futex 是基于用户内存字的等待机制，不直接等于完整 mutex。

5.2 等待条件与唤醒

等待操作需要将“值仍符合等待条件”的检查与进入睡眠协调起来，避免在检查和睡眠之间错过唤醒。条件变量的业务条件仍要在锁内用循环检查。

5.3 死锁条件与处理

死锁四条件：互斥、占有并等待、不可抢占、循环等待。工程中常用全局加锁顺序、一次协调获取多个锁、缩小持锁范围；超时只提供失败出口，不能自动保证状态正确。自旋锁适合极短且持有者能很快运行的临界区，长等待更适合阻塞。

经典问题：两个线程分别先锁 A/B，再锁 B/A，为什么会卡住？

它们可能各持有一把锁并等待对方形成环。统一先 A 后 B，或使用适用的多锁协调接口破坏循环等待；不要在持锁时等待必须由另一持锁线程推进的任务。

本节解释等待与唤醒机制；C++ 中如何使用锁、条件变量及内存序，见并发与同步；Java 的共享状态规则见JMM 与 monitor。

参考：futex 机制。

6. 异常、信号与故障

6.1 异常与信号处理路径

CPU 异常先进入内核处理；无法恢复的用户访问错误可转为信号。信号也可由进程显式发送或由定时器等事件产生。处理方式包括默认动作、忽略或安装处理器；SIGKILL/SIGSTOP 不能捕获或忽略。

6.2 处理器约束与语言边界

信号处理器会打断正常执行，只能使用适用的异步信号安全操作；随意分配内存、获取普通锁或调用复杂日志接口可能再次出错。C++ 异常与 Linux 信号是不同机制，不能指望普通 try/catch 捕获所有段错误。

经典问题：空指针调用没有崩溃，是否说明合法？

语言规则先于系统表现。空指针上的非静态成员调用可能已经是 C++ 未定义行为；编译器生成的代码是否真的触发页访问，只影响这次是否出现信号，不改变合法性。

参考：Linux 信号。
