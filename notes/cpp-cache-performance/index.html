1. 连续存储与访问步长

int a[R][C] 是 R 个长度为 C 的数组连续排列；a[i][j] 相对起点的字节偏移是 (i * C + j) * sizeof(int)。行内相邻元素连续，跨行步长为一整行。

假设 int 为 4 字节、C = 1024
访问顺序内层相邻访问间隔访问特点
先行后列：i 外、j 内4 字节连续读取，通常利于预取和向量化
先列后行：j 外、i 内4096 字节跨页访问，可能增加缓存与 TLB 压力

缓存行是 CPU 缓存传输和一致性管理的重要粒度。若缓存行为 64 字节，一行可容纳 16 个这样的 int；一次加载后顺序读取可利用同一行其余元素。行大小、缓存容量、组相联和预取器均依处理器而异。

经典问题：按行遍历一定更快、一定快 16 倍吗？

通常更有利，但不存在固定倍数。小数组可能已在缓存中；编译器可能调整循环；大步长还受预取、TLB、缓存冲突影响。16 个 int/缓存行描述空间利用率，不能直接换算整体运行时间。

2. 可运行的对照实验

下面使用一维 vector 表示同样的行优先矩阵，避开大数组占用线程栈的问题；用 64 位累加防止求和溢出。初始化不计入时间，先校验结果并预热，再随机交替两种访问顺序，输出最小值、中位数、最大值和校验和。

下载源码（kernels.cpp）。使用 C++17 编译；断言测试请勿定义 NDEBUG。

两种遍历的独立实现 
#include <cstddef>
#include <cstdint>
std::int64_t rows(const int* a, std::size_t n) {
    std::int64_t sum = 0;
    for (std::size_t i=0; i<n; ++i)
        for (std::size_t j=0; j<n; ++j) sum += a[i*n+j];
    return sum;
}
std::int64_t columns(const int* a, std::size_t n) {
    std::int64_t sum = 0;
    for (std::size_t j=0; j<n; ++j)
        for (std::size_t i=0; i<n; ++i) sum += a[i*n+j];
    return sum;
}

计时、顺序打乱与结果校验 
#include <algorithm>
#include <array>
#include <cassert>
#include <chrono>
#include <cstddef>
#include <cstdint>
#include <iostream>
#include <random>
#include <stdexcept>
#include <string>
#include <vector>
std::int64_t rows(const int*, std::size_t);
std::int64_t columns(const int*, std::size_t);
int main(int argc, char** argv) {
    const auto n = argc>1 ? std::stoul(argv[1]) : 1024ul;
    if (n<32 || n>8192) throw std::out_of_range("n must be 32..8192");
    std::mt19937 random(42);
    std::vector<int> a(n*n);
    std::int64_t expected = 0;
    for (auto& x : a) { x=static_cast<int>(random()%1024); expected+=x; }
    assert(rows(a.data(),n)==expected && columns(a.data(),n)==expected);
    using Fn=std::int64_t(*)(const int*,std::size_t);
    std::array<Fn,2> fn{rows,columns};
    std::array<std::vector<double>,2> time;
    std::int64_t checksum=0;
    for (int round=0; round<10; ++round) {
        std::array<int,2> order{0,1};
        std::shuffle(order.begin(),order.end(),random);
        for (int id : order) {
            const auto start=std::chrono::steady_clock::now();
            const auto result=fn[id](a.data(),n);
            const auto end=std::chrono::steady_clock::now();
            assert(result==expected);
            checksum+=result;
            time[id].push_back(std::chrono::duration<double,std::milli>(end-start).count());
        }
    }
    for (int id=0; id<2; ++id) {
        auto& t=time[id]; std::sort(t.begin(),t.end());
        std::cout << (id==0 ? "rows" : "columns") << " ms min/median/max: "
                  << t.front() << ' ' << (t[4]+t[5])/2 << ' ' << t.back() << '\n';
    }
    std::cout << "checksum: " << checksum << '\n';
}
g++ -std=c++17 -O3 -fno-lto -c kernels.cpp -o kernels.o
g++ -std=c++17 -O3 -fno-lto benchmark.cpp kernels.o -o cache-bench
./cache-bench 1024

两份源码分别编译且关闭 LTO，计时文件看不到遍历函数体；结果参与断言和最终输出，避免测试只剩空循环。仍应检查优化后的汇编，确认实际测量的是预期访问模式。可另用 Google Benchmark 的 DoNotOptimize/ClobberMemory；这些工具也不能替代对生成代码的检查。

参考：Google Benchmark：防止无效优化。

3. 结果解释与观测指标

  • 同时记录 CPU、操作系统、编译器版本、优化选项、矩阵规模和数据类型；改变规模观察何时超出各级缓存。
  • 本例测预热后的重复访问；冷缓存、首次触页和初始化应另设实验，不要混合比较。
  • 在 Linux 上可用 perf stat 观察 cycles、instructions、cache-misses、page-faults；TLB 与各级缓存事件名称须查 perf list，硬件/权限可能不支持。
  • 按两种内核分别采集计数器才能归因；对整个混合测试运行 perf，只能得到合计。时间差还可能来自向量化和内存带宽，不能只用一个 cache-misses 值定论。

参考：perf stat。

4. 粒子系统的数据布局

两种布局
形式适合场景代价
AoS：vector<Particle>单次访问一个粒子的多数属性只更新位置时也可能加载颜色、名称等冷数据
SoA：x[] / y[] / vx[] / vy[]批量处理少数同类属性，便于 SIMD各数组长度与索引必须一致；操作单粒子更多间接访问

优化先减少热循环不需要读取的数据：把位置/速度与调试名称等冷数据分开；批量更新并避免逐粒子堆分配。多线程按连续区间分块，避免频繁写同一缓存行造成伪共享。数据布局变化后要重新检查删除和稳定 ID 的映射。

经典问题：是否应该把所有对象都改成 SoA？

看热点访问方式。若逻辑经常同时读取单个对象的全部字段，AoS 可能更直接且局部性足够；若只对大量位置做同一计算，SoA 更有优势。用相同工作量和正确性校验比较。
