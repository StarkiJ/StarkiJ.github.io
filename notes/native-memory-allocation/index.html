1. malloc、new、虚拟内存各负责什么

malloc 是用户态分配接口，一次调用通常先复用分配器管理的空闲块，不是每次都向内核申请一段物理内存。本文先讲通用机制，再用 Linux / glibc 2.39 的分配器作为具体例子；jemalloc、TCMalloc、Android Scudo 或其他版本有不同结构。

从对象到物理页
层次职责常见误解
C++ new 表达式取得存储并初始化对象；普通失败路径抛异常，可重载分配函数new 不保证直接调用 malloc；placement new 不另取存储
malloc / free按字节交付和回收可用存储，不运行 C++ 构造 / 析构malloc 的大小不等于分配器实际占用；free 不保证降低 RSS
用户态分配器对齐、大小分组、缓存、切分、合并与并发控制arena、tcache 不是操作系统概念
操作系统虚拟地址映射、页权限、按需建立物理页等地址连续不要求物理页连续；申请成功不等于所有页已驻留

常规对象使用 new/delete、数组使用 new[]/delete[]，malloc 对应 free，不能随意混配。对齐要求超出普通 malloc 保证时，要选择适合平台的对齐分配接口。托管堆内的对象分配还可能走 TLAB 指针递增路径，不等于每创建一个 Java 对象就调用一次 native malloc。

2. 一次分配经过哪些路径

首先检查请求大小及溢出，再把用户大小换算为满足对齐和元数据要求的 chunk 大小。大小类别降低查找成本，也会产生内部碎片。以下是 glibc 2.39 常见路径的概念顺序，实际分支还会受到大小、缓存状态、线程和配置影响：

malloc(n)
  → 检查大小、规范化为内部 chunk 大小
  → 符合条件且 tcache 有块：从当前线程缓存取出
  → 进入 arena 路径：尝试适用的空闲结构并按需补充缓存
  → 找到合适块：可能切分，剩余块继续由分配器管理
  → 使用 top chunk（arena 尾部的可扩展空闲块）
  → 仍不足：按条件扩展 arena 或单独 mmap
  → 成功返回用户区域；失败返回空指针
glibc 常见结构
结构作用代价或边界
tcache每线程、按大小分组缓存部分空闲块，使命中路径避免 arena 锁有容量和适用大小限制；每线程缓存会留住内存
arena包含锁、bins、top 等状态的分配域，管理一个或多个堆区域多 arena 降低争用，也可能增加碎片；不等于每线程一个 arena
fastbins缓存部分小块，快速路径通常暂不合并相邻块后续可能触发集中合并，不等于立即变成连续大块
unsorted / small / large bins暂存或按大小组织空闲块，支持复用与查找切分、归类及合并取决于具体路径，不能只背一条固定链
单独 mmap 的块满足条件时独立映射，释放时可解除映射系统调用及页级管理有成本，阈值和策略不是普适常数

glibc 的主 arena 可通过 brk 扩展，其他 arena 的堆空间也可来自 mmap；不能把“用了 mmap”直接等同于“一定是独立大块分配”。mmap_threshold 在默认策略下可动态调整，显式配置会改变行为；“大于 128 KB 必走 mmap”不是可靠的通用答案。

参考：glibc 2.39 malloc.c：分配与空闲结构。

参考：glibc 2.39：arena、tcache 与 mmap 调整项。

3. free 怎么知道大小，为什么不立刻还内存

free 接收原始用户指针，分配器根据其布局找回 chunk 元数据，从而确定块大小、状态与所属管理结构。glibc 使用 chunk 头部及相邻块状态信息支持检查和合并，但这不赋予用户访问 p[-1] 的权限；头部布局、最小块和保护机制均属于实现细节。

  1. free(nullptr) 无操作；其他参数必须是仍有效且允许释放的分配起始指针。
  2. 符合缓存条件的块可进入线程 tcache；某些小块进入 fastbins，暂缓合并。
  3. 进入普通合并路径时，根据相邻空闲块状态合并，并放入相应结构或合入 top。
  4. 独立 mmap 块通常通过解除映射释放；arena 管理的空闲存储可保留供后续复用，满足条件时再 trim 或归还页。

free 后指针变量的位值不会自动清零，但对应存储已不再允许原调用者使用。继续读写是 use-after-free；重复 free、释放偏移后的内部指针或破坏元数据均可能产生未定义行为。

面试追问：释放了 1 GB，RSS 为什么没明显下降？

可能已经逻辑释放，但空闲块仍留在 tcache / arena，或被活块隔开而难以归还整页。先分开观察业务存活量、分配器保留量与操作系统驻留量；仅看 RSS 无法断言泄漏，也不能因调用过 free 就排除泄漏。

参考：malloc_trim：满足条件时归还空闲页。

4. 碎片、并发与 realloc

内部碎片是交付块因大小分组、对齐而超过请求；外部碎片是空闲空间分散，难以拼出所需连续虚拟地址块。分配器元数据本身也占空间。线程缓存和多 arena 改善争用，却可能让空闲存储滞留在局部，不能只从一次分配的耗时判断整体收益。

普通 malloc 通常无法移动仍在使用的块，因为不知道应用保存了多少裸指针及其副本。池、句柄和托管运行时通过额外约束才有机会整理；可对照 GC 的转发与引用修复。

realloc可能原地扩缩，也可能分配新块、复制保留范围并释放旧块。对于非零的新大小，失败返回空指针而旧块仍有效，因此不要直接用返回值覆盖唯一旧指针。成功后都以返回的指针作为有效分配地址；之前指针及内部借用的使用需重新建立。零大小的规则随语言标准和实现有差异，业务代码最好显式 free 并单独处理。

void* next = std::realloc(buffer, new_size); // 前提：new_size > 0
if (next != nullptr) {
    buffer = next;                         // 重新建立后续内部指针
} else {
    // 原 buffer 仍由调用者拥有，可保留、稍后重试或释放
}
面试追问：怎样定位 malloc 引起的性能问题？

观察大小分布、分配次数、线程数、跨线程释放与峰值同时存活量；用剖析区分缓存命中、锁竞争、系统调用及缺页。固定负载比较吞吐、尾延迟和 RSS；仅做单线程 malloc/free 紧循环，往往只测到了缓存快路径。

参考：realloc 契约及多线程分配背景。

5. 面试回答与排查入口

一分钟回答：malloc 先在用户态把大小规范化，优先复用线程缓存或 arena 内的空闲块，必要时切分、合并或向操作系统扩展映射。free 通过元数据识别块，把它交回分配器，不保证马上归还物理页。性能来自缓存和分组，也付出碎片和保留内存的代价。具体 bins、阈值和锁策略要限定分配器与版本。

追问路线：虚拟内存与缺页 → 泄漏与非法访问定位 → 稳定句柄 → 移动 GC。面试时能画出“用户请求、chunk、arena、虚拟页”四层关系，比只背 brk / mmap 两个名字更完整。
