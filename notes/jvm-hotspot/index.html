阅读范围与实现边界

JVM 与 HotSpot 先把程序表示变成可用的类型与方法，再协调执行、线程与内存管理。本篇沿字节码、类身份、初始化、调用、同步、编译和 HotSpot GC 展开；对象如何分配与回收见托管内存，LLVM IR 和通用编译分析见LLVM 编译器。

共同语义以 Java SE 21 的语言与虚拟机规范为参照，HotSpot 示例限定 JDK 21；Android 对照采用 ART / Android 14 的常规应用场景。ART 使用 DEX，不能直接套用 class 文件、HotSpot 元数据或全部 Java SE API。JDK 虚拟线程也不等同于 Android 平台线程或 Kotlin 协程。

程序表示、类型与执行

本部分解释程序表示、类型身份和调用语义；对象分配与回收机制另见 GC 篇。

从字节码到运行时状态

文件表示、运行时元数据与对象

源码中的类型、方法和字段先编码在文件里；加载后，运行时建立可访问的类型信息和解析状态；调用时再建立当前执行所需的帧。文件中的类描述、运行时的类信息、Class 对象和某个实例是不同层次。一个 class 文件通常表示一个类或接口，DEX 可汇集多个类定义及共享的索引表。

共同职责与两种表示
职责JVM class / 字节码DEX / ART
描述类型与成员类名、父类、字段、方法、描述符和属性类型、字段、方法等索引及类定义
保存方法体Code 属性中的指令、异常表等；native / abstract 方法没有普通 Code 方法体有实现的方法通过 code_item 等结构描述指令与异常处理
表达计算局部变量表与操作数栈方法帧中的虚拟寄存器
进入机器执行解释器执行表示的语义，或由编译代码实现；逻辑帧不必与机器帧一一对应

JVM 常量池含字面常量、类型和成员的符号信息；加载后的运行时常量池可维护解析结果。DEX 有分别索引字符串、类型、字段、方法的表。常量池不是“所有常量对象的一块堆”：字符串对象、驻留机制与这些表的职责需要分开。

例如 JVM 方法描述符 (ILjava/lang/String;)V表示显式参数 int、String，返回 void；实例方法的隐含 this 不写在描述符里。泛型 Signature 属性与供链接使用的描述符不是同一概念。JNI 查找成员也需要匹配的名字和描述符。

同一次加法怎样执行

以 static int plusOne(int x) { return x + 1; } 为例。下面是指令语义示意；DEX 用含两个虚拟寄存器的方法帧，最后一个 v1 接收参数，不承诺具体工具一定生成这个序列。

JVM：局部槽 0 = x，初始操作数栈为空
iload_0     栈 [x]
iconst_1    栈 [x, 1]
iadd        栈 [x + 1]
ireturn     返回栈顶值

DEX：v1 = x
add-int/lit8 v0, v1, #1
return v0

DEX 的 v0、v1 是字节码层的位置，不是 CPU 的 x0、x1。编译器可以折叠计算、内联调用并重新分配物理寄存器。两种模型都有调用帧，不能由“基于寄存器”推导 ART 没有栈。

参考：JVMS：class、描述符与 Code · DEX 格式 · DEX 指令与帧。

类加载器与类身份

同名为什么不一定是同一个类

对普通命名的类和接口，运行时类身份由二进制名称与定义它的类加载器共同决定。两个加载器分别定义 demo.Widget，得到的 Class 可以不同；即使字节完全相同，其实例也不能仅因名字相同就互相强转。数组类另按组件类型等规则创建，不能把每个数组都当成由加载器读取的独立文件。

定义加载器实际定义这个类型；发起加载器发起请求，可以委派其他加载器返回已有类型。共享接口若由父加载器定义，子加载器定义的实现可以实现该接口；若子加载器连接口也重复定义，就可能破坏原本期待的类型兼容。

委派是查找策略，边界是类型一致性

通常的 ClassLoader.loadClass 思路：
  查当前加载器是否已经加载
  → 委派父加载器 / 相应基础加载路径
  → 未找到时由自己的 findClass 查找并定义
  → 按请求完成必要的链接工作

这是常见父优先策略，不是所有加载器永远不可改变的执行顺序。自定义策略仍需遵守类型安全、加载约束与平台限制。线程上下文类加载器是供特定库选择加载来源的约定，并不自动替代所有类引用的解析加载器。

HotSpot/JDK 21 常见 bootstrap、platform、application 加载路径；Android 常见 BootClassLoader、PathClassLoader、DexClassLoader 等围绕 DEX 查找。它们不能用一套固定目录或内部字段概括。JNI 的 FindClass 又受调用上下文影响，见注册与查类案例。

复习问题：两个插件同名类强转失败，先查什么？

同时记录对象实际 Class、目标 Class 及各自加载器；检查共享接口是否重复打包 / 定义。比较类名或重新 new 一个加载器都不能证明类型一致。类缓存的持有链与卸载见元数据生命周期。

参考：JVMS：类身份与加载约束 · ClassLoader 的默认委派 · Android PathClassLoader。

链接、初始化与失败状态

先区分职责，再讨论发生时机

加载与链接不是执行静态代码块
职责主要工作
加载取得表示并建立类型
验证检查格式、类型和指令使用约束，确保满足相应运行时规则
准备建立静态字段存储及默认值等运行时状态；不执行普通静态初始化表达式
解析把符号引用关联到相应类型、字段、方法等，并检查访问与链接约束
初始化按规定设置常量值、协调依赖类型并执行需要的类初始化逻辑；JVM 对应 <clinit>

初始化前必须完成验证与准备，但解析可以提前或推迟到使用时；不要画成“全类所有符号必须一次解析完，再初始化”的唯一流水线。<clinit> 的类初始化与 <init> 的实例构造不同，一个类可以创建多个实例而不重复执行类初始化。

用可观察顺序理解主动使用

创建实例、调用类声明的静态方法、读写其非编译期常量静态字段等会触发相应初始化；使用子类名称访问继承的静态字段，关键是字段由哪个类声明。类字面量、创建组件类型的数组、读取编译期常量不会仅因此初始化该类。反射是否初始化取决于所用接口，例如 Class.forName 的 initialize 参数。

初始化类前要协调父类，以及规范要求初始化的、声明默认方法的相关父接口；不能推广成“所有接口都先初始化”。每个类的初始化协议处理竞争线程、递归请求和失败状态；成功完成初始化的同步保证，不意味着之后修改静态字段自动线程安全。

按第一次失败定位

ClassNotFoundException 常见于显式查找类失败；NoClassDefFoundError 也可能来自链接时找不到定义，或先前初始化失败后的再次使用。普通静态初始化抛出的非 Error 异常通常被包装成 ExceptionInInitializerError；失败类型会进入错误状态，不能依赖下次调用自动重试。先找最早的异常原因，再查后续报错。

初始化本身也可能因复杂的跨线程 / 跨类等待造成死锁或启动停顿。把耗时 I/O、回调和持锁等待放进静态初始化，影响的是首次使用的整条路径。ART 启动应单独观察这部分成本。

参考：JLS：初始化触发与顺序 · JVMS：初始化与错误状态。

方法解析、分派与异常

编译期选签名，运行时选适用目标

重载通常在源码编译阶段按表达式类型等规则选择签名；虚方法的重写分派则根据实际接收者选择实现。把符号引用解析为方法，与为某次调用选择目标不是同一步。类的虚表、接口分派表及入口缓存属于实现手段。

class Base { int work() { return 1; } }
class Derived extends Base { @Override int work() { return 2; } }
Base receiver = new Derived();
int result = receiver.work(); // 结果为 2；不因变量写作 Base 就调用 Base.work

在 JVM 字节码中，invokestatic 用于静态调用；invokevirtual / invokeinterface 支持相应动态分派；invokespecial 用于构造器及某些需特殊处理的调用。invokedynamic 通过引导方法链接调用点，不等于普通虚调用或“每次做反射”。DEX 有自己的 invoke 指令族；不能把 JVM 指令名直接当成 ART 本机入口。

反射按运行时的类型 / 成员对象发起访问，MethodHandle 表达可调用目标及类型化适配。它们仍受平台访问控制约束，开销受查找、适配、缓存和编译优化影响，不能说反射永远不能优化。普通分派的调用点缓存与去虚拟化见IC 与类型反馈。

Java throw 怎样找到处理器

  1. 在当前方法中，根据抛出位置和异常类型寻找适用处理器；JVM 的 Code 异常表描述受保护范围与处理目标。
  2. 找到时转到处理器所需状态；JVM 的处理器入口操作数栈中放异常对象引用，DEX 使用自己的处理器与 move-exception 约定。
  3. 当前帧无匹配处理器时向调用者传播；解释器和编译代码必须维持一致的语言行为。finally、资源关闭及同步释放由相应控制流与运行时协议实现。

机器帧可因内联少于逻辑调用层数，编译元数据仍须支持定位处理器。Java 异常不直接等于 C++ 的 __cxa_throw；JNI 待处理异常也不是自动在每次 native 指令后展开 C++ 栈。平台边界见JNI 异常清理。

参考：JVMS：调用与 athrow 指令 · Code 异常表 · DEX 调用与 move-exception。

共享状态与运行时协作

本部分解释共享状态规则，以及解释器、编译代码与 native 调用如何协作；先区分语言保证和实现元数据。

Java 内存模型、监视器与线程

内存区域与内存模型回答不同问题

堆、栈描述数据由谁保存；Java Memory Model（JMM）描述多线程读写允许观察到什么结果，以及编译器 / 处理器重排必须遵守的约束。happens-before 是保证可见性与先后关系的规则，不等于测到的墙钟时间。正确同步的程序可据此推理，不能靠“CPU 缓存迟早刷新”保证正确。

常用规则与不能推导的结论
机制建立的关系边界
程序顺序与传递性线程内动作及跨线程同步关系可以连成 happens-before 链不要求底层所有指令按源码顺序执行
volatile对变量的写与后续相应读建立同步关系，可用于发布之前的写入count++ 仍是复合操作；volatile 引用不让被引用对象的所有操作自动同步
synchronized同一 monitor 上的解锁与后续加锁建立同步，互斥保护临界区不同锁不自动保护同一不变量
Thread.start / join启动前的动作先于新线程动作；线程终止先于另一线程成功 join 后的动作启动线程不保证其后每次共享访问都安全
final 字段正确构造且未提前暴露 this 时有专门的初始化安全规则不意味着对象整体不可变；引用指向的可变内容后续仍需同步

Java volatile 与 C++ volatile 不能通用解释。C++ 的 volatile 不提供相同的线程同步保证。GC 引用屏障负责可达性或移动访问，也不能替代 JMM；具体实现可以复用底层原子指令，但职责不同。

发布对象之前的写入

推理链是 value=42 → volatile 写 ready → 读到该发布的 ready → 读取 value。删除 volatile 后，忙等不保证结束，也不能保证读到 42。onSpinWait 只是自旋提示，不建立这个同步关系。示例只展示发布规则；实际等待优先用锁、条件或适当的并发工具，避免持续占用 CPU。

安全发布可使用锁保护、volatile 引用、类初始化等适用机制。双重检查若使用可变共享引用，要同时说明其发布协议，不能只展示两次 if。构造器中注册 this 或启动可访问它的回调，会破坏“构造完成后才暴露”的前提。

互斥、等待与唤醒

对象 monitor 支持可重入互斥；实例 synchronized 方法使用接收者，静态 synchronized 方法使用对应 Class 对象。wait / notify / notifyAll 要持有同一对象的 monitor；wait 释放该 monitor，返回前重新取得它，其他已经持有的锁不因此全部释放。被唤醒不等于条件已经满足，也不等于立刻获得锁。

synchronized (lock) {
    while (!condition()) {
        lock.wait();       // 检查与等待在同一锁协议下；处理 InterruptedException
    }
    consume();             // 重新取得锁后再次确认条件
}

sleep 不释放所持有的 monitor；notify 发出唤醒后也不会立即释放当前线程的锁。循环检查同时处理虚假唤醒、多个等待者竞争以及条件再次变化。底层轻量锁、膨胀与等待队列属于具体 VM 和版本，不能把旧 HotSpot 的固定“锁升级四阶段”当作 Java / ART 共同保证。

语言状态、内核状态与安全点状态

Java Thread.State 包含 NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED。BLOCKED 特指等待进入 monitor；不等于所有 I/O 阻塞。RUNNABLE 也不保证此刻正在某个 CPU 上执行。OS 的就绪 / 睡眠状态和 VM 内部的托管 / native / 安全点状态是另外的观察层次。

本篇的例子使用平台线程。JDK 21 的虚拟线程及 Kotlin 协程涉及额外调度关系，不能把它们的数量直接当作内核线程数。通用等待机制见锁与 futex；GC 协调见安全点与根扫描。

参考：JLS：线程、锁与内存模型 · Object.wait · Android 线程状态 · Thread 与 onSpinWait。

解释、编译与 native 怎样协作

入口适配与执行状态

调用者与被调用者不一定使用同一种执行方式：解释器可调用编译代码，编译代码也可调用尚未编译的方法或 native 方法。运行时通过入口与适配代码转换参数位置、维护帧及线程状态，并处理必要的解析、检查与异常。更新方法入口主要影响后续进入方式，不能据此断定已经执行到一半的旧帧全部消失。

长循环可通过 OSR在受支持的位置转入编译执行；优化假设失效时可通过反优化恢复可继续执行的状态。它们需要执行位置和活值映射，不只是改一个函数指针。

看似都是“栈信息”，用途并不一样

以一次内联调用中的对象引用为例
信息回答的问题主要讲解位置
JVM StackMapTable字节码验证时，给定位置允许哪些局部值和操作数栈类型class 格式与验证；不是 GC 地址表
GC 引用位置图，如 HotSpot OopMap某个受控机器码位置哪些寄存器 / 槽是活引用GC 根扫描
反优化恢复信息内联了几个逻辑调用；执行位置、局部值和待恢复对象是什么编译器状态恢复
CFI / 异常处理信息如何恢复上一机器帧，以及语言处理器 / 清理代码在哪里回溯与异常展开
调试映射机器地址对应哪个函数、源码行和内联位置符号化与调试

这些职责可能在实现中共享部分记录，但不能互换使用。编译器消除局部变量或内联方法后，源码中“有这个变量”不保证物理栈上有同名槽。ART 也需要相应协作信息，编码格式须查其分支；JNI 通过引用句柄和线程转换加入该协议。

复习问题：保存所有通用寄存器，是否足够支持 GC 和反优化？

还不够。保存位值没有说明哪些是引用、对应哪个逻辑变量、是否需要重新物化对象，以及恢复到哪个指令位置。运行时必须与编译器约定这些值的语义，而不只是寄存器数量。

参考：StackMapTable · HotSpot ScopeDesc · HotSpot OopMap。

动态编译与运行时优化

本部分涉及托管方法的分派与执行状态；相关语义见方法解析与分派，机器状态基础见调用与栈帧。

运行期间的热点与类型信息可以指导编译决策。沿采集信息、生成优化代码、处理假设失效的顺序，连接前面的 IR 变换与可继续执行的运行时状态。

解释执行、AOT、JIT 与热点统计

AOT在目标程序本次执行前生成机器码；JIT在运行过程中按需编译，可使用运行时类型和热点信息。解释执行、低成本编译、优化编译可组成不同层级，平衡启动、峰值性能与编译资源。C1/C2 是 HotSpot 的特定分层术语，不是所有 JIT 的统一级别。

执行方式
方式收益成本
解释无需先为所有方法生成本机代码反复解释热点指令有成本
JIT按运行热点生成代码并利用运行信息占用应用运行期间的 CPU、代码缓存与元数据
AOT提前生成可复用机器码编译耗时、磁盘体积；可能编译并不热的方法

运行时还需要在解释帧、编译帧和 native 调用间转换。编译代码依赖相应检查、类状态和 GC 协作信息，不是与运行时脱离的一段裸机器码。

HotSpot C1 / C2：为什么分层

以 JDK 21 HotSpot 的编译级别为例，C1 是编译开销较低的编译器，可按级别产生不同数量的运行反馈；C2 花更多编译资源追求更强的优化。分层让热点代码较早脱离解释执行，同时继续积累调用与类型信息，供后续优化使用。级别是代码的编译状态，不是“一个方法一定按 0、1、2、3、4 各跑一遍”的固定流水线。

编译级别与主要职责
级别执行形式反馈与用途
0解释执行可收集热点信息，并决定是否提交编译任务
1C1 简单编译较快获得机器码，不承担完整的类型反馈收集
2C1 有限 profiling记录调用与回边计数等有限信息
3C1 完整 profiling除计数外记录方法数据中的更丰富反馈，为高层优化提供证据
4C2 完整优化；配置 JVMCI 时也可由其承担利用已有反馈进行更重的优化，增加编译 CPU、时间和代码缓存成本

实际升层由热点、编译队列、代码缓存、编译器是否可用及配置共同决定，可能跳级或停在较低级别；长循环还可能经 OSR 在循环中途切换。C2 依据类型反馈生成的快速路径仍要保证假设失效时可安全处理，可能走慢路径或反优化；这与“C2 机器码永远不退回解释”不同。反优化怎样恢复执行状态见OSR 与反优化。

面试追问：为什么不把所有方法一开始就交给 C2？

很多方法并不热，提前做重优化会花编译 CPU、延迟与代码缓存；初次执行也缺少有价值的类型和分支反馈。解释与 C1 先提供低成本执行和采样，运行时再把值得投入的方法交给 C2。是否收益更好仍取决于负载和配置。

参考：JDK 21 HotSpot CompLevel 定义 · JDK 21：分层编译与代码缓存。

AOT 编译怎样做优化

AOT 说明生成机器码的时机，不指定一套独有的优化算法。编译器仍可在 IR 上做常量传播、死代码删除、内联、循环优化和寄存器分配；每项变换的语义前提见优化的前提与代价。运行前已知的类型、调用关系和目标 ISA 可用于静态分析，但运行时才出现的接收者类型或分支频率不能凭空假定。

例如某虚调用有多个可能目标：若 AOT 编译时能证明目标唯一，可以直接调用或内联；若只有历史 Profile 显示某类型常见，可在支持相应协议的运行时生成“类型检查 → 热门目标快速路径 → 其他目标慢路径”，并保留假设失效后的正确执行方式。没有证明或反馈时应保留通用分派。由此可见，Profile-guided AOT仍是 AOT，利用过去运行的数据不等于在本次运行中 JIT 编译。

以 ART 为例，dex2oat 的 speed 倾向编译所有方法，speed-profile 依据 Profile 选择方法并优化相关类加载；已有类型反馈也可支持某些 AOT 调用点优化。要同时权衡编译耗时、磁盘中的机器码大小、启动时间、峰值执行速度和 Profile 的代表性。选择编译哪些方法与怎样优化单个方法是两个不同问题；具体 pass 和过滤器行为须限定 ART 版本。

面试追问：AOT 没有运行时信息，所以不能做内联吗？

不能这样说。目标在编译时可证明时可以静态内联；也可以用已有 Profile 做受检查的猜测性优化，前提是运行时提供相应的慢路径或状态恢复。没有可靠证据时不能把可能变化的目标无条件固定。

参考：Android：ART AOT 与 compiler filters · Android：Profile 与 AOT 调用点优化。

热点统计与编译调度

一种热点设计是在方法元数据中保存饱和调用计数、回边计数和编译状态；达到阈值后入队，避免重复编译。采样或线程本地计数可降低竞争；计数合并、过期、代码缓存容量和反优化也要纳入。无需每次调用都建立字符串键哈希表。

经典问题：热点统计应选择什么数据结构？

通常可把计数与状态放在方法关联元数据中，结合调用/回边计数或采样，降低查表和同步开销；编译队列要去重，计数可饱和。真实字段、阈值和队列实现需对照目标运行时分支。

经典问题：调低 JIT 阈值一定让启动更快吗？

不一定。较早生成机器码可减少热点解释成本，也会提前占用 CPU、内存和编译队列，可能与启动关键线程争抢资源。按冷/热启动、编译时间、执行节省和代码缓存占用做对照，不能只比较单个函数执行速度。

Profile 与代码缓存

经典问题：“JIT 预编译”通常需要怎样澄清？

如果指运行前依据已有 profile 生成机器码，那更接近 profile-guided AOT；如果指在运行中提前安排将使用的方法编译，则仍是运行时策略。应明确生成时间、输入信息和代码保存位置。

代码缓存回收处理可回收的 JIT 机器码及随代码保存的辅助信息；Java 堆 GC 处理对象可达性。代码、运行时类型反馈和持久化 profile 的存储与寿命必须分别看。以 JDK 21 HotSpot 为例，MethodData 中的方法反馈分配在 Metaspace；Code Cache 中的 profiled code heap 保存的是带 profiling 的编译代码，不能理解成存放全部 profile 数据的堆。

ART 有自己的 JIT 代码及 profiling 管理方式。回收一段机器码不等于删除全部类型反馈或磁盘 profile，也不等于清空 Java 堆；代码失效、类卸载和各类存储回收通过运行时协议协调。

参考：JDK 21 MethodData::allocate：反馈的元空间分配。

ART 的实际编译与 profile 流程见 ART 编译与 Android 应用启动。

参考：HotSpot：分层编译与代码缓存。

Inline cache、类型反馈与反优化

Inline cache（内联缓存，IC）是在调用点缓存接收者类型与调用目标的关系。同一个虚调用点往往反复遇到同一类对象；缓存命中时可缩短动态分派路径。这里的 inline 描述缓存贴近调用点，并不等于把被调用函数体展开。

调用点：receiver.work()
首次执行：尚无缓存 → 运行时解析 receiver 的类型与目标
单态路径（概念）：
    按语言要求处理 null
    if receiver.klass == cached_klass:
        call cached_target(receiver)
    else:
        进入 IC miss / 运行时分派路径

方法解析、普通分派与类身份见托管调用基础。缓存键必须足以识别运行时类型，例如可靠的 Klass 身份；同名类可能由不同类加载器定义，不能只比较类名字符串。虚表按类描述方法槽位，IC 则利用某一个调用点的类型规律，两者可以配合。

  • 未链接 / 未初始化：第一次调用尚需解析。
  • 单态（monomorphic）：调用点反复看到一种接收者类型，可使用类型检查加直接目标。
  • 多态内联缓存（PIC）：一般设计中可缓存少量“类型→目标”对，按 guard 逐一检查。
  • 超多态（megamorphic）：类型过多时，维护长检查链得不偿失，可退回通用虚表 / 接口表等分派。

上面是通用设计词汇，不是每个 HotSpot 调用点都必经四级状态。JDK 21 的 CompiledIC 主要表达 clean、monomorphic、megamorphic 等状态；JIT 根据 profile 生成多个类型 guard 的优化代码，与 CompiledIC 自身是否维护 PIC 数组是不同问题。

类型反馈怎样支持内联和反优化

JIT 看到单态热点后，可以生成“类型 guard + A.work 的内联代码 + 失败路径”。原 IC 快速调用仍存在一次调用，内联则消除了调用边界，并给后续常量传播、逃逸分析等提供机会。内联要平衡收益、代码膨胀和指令缓存压力。

当接收者出现新类型时，普通 IC miss 可以进入运行时解析并更新状态，不必每次都反优化。如果机器码依赖了更强假设，例如类层次分析认定某方法只有一个实现，则新类加载可能使依赖失效，触发失效处理或反优化。反优化需要用元数据恢复解释执行所需的局部变量、操作数栈和内联帧状态。

修改目标与缓存类型还必须满足并发发布协议，避免其他线程看到“新类型配旧目标”；代码修补也需遵守目标架构的指令可见性要求。这是运行时实现细节，不能直接用两次普通赋值替代。

面试追问：IC miss、缓存状态变化、反优化是同一件事吗？

不是。miss 表示当前接收者不满足该缓存快速路径；运行时可能解析后更新缓存，或者走通用分派。反优化则是退出不再适用的优化机器码、重建可继续执行的状态。guard 失败可以设计为慢调用，也可以设计为 uncommon trap，取决于编译决策。

面试追问：如何把 inline cache 与 SSA 连起来回答？

IC / profile 提供类型证据，JIT 生成 guard 把快速与慢速路径分开；两条路径返回的值在合并块可由 phi 汇合。进一步内联后，SSA 的定义—使用关系帮助传播常量与删除冗余计算。

参考：JDK 21 CompiledIC：状态与调用点约定。

参考：JDK 21 CompiledIC：状态转换与目标更新。

OSR 与反优化：执行到一半怎样切换

方法入口与循环入口不是同一个状态

一个方法只调用一次，却在里面循环很久，仅统计方法调用次数可能漏掉热点。回边热度可触发OSR（On-Stack Replacement）编译：在运行时支持的位置，把正在执行的帧状态转为相应编译入口需要的状态，继续剩余工作，不重新执行方法开头。

long sum = 0;
for (int i = 0; i < n; i++) sum += i;

解释执行到某个受支持的循环入口：
  当前 i = k、sum = 前 k 项累加值、n 已知
  → 把活值交给针对该入口生成的代码
  → 编译代码从当前循环状态继续
不是：i = 0、sum = 0，再跑一遍。

普通编译入口接收方法参数；OSR 入口还依赖当前执行位置和已形成的局部状态。需要对应代码已准备好、线程可完成转换等条件，不能仅凭回边计数达到某个固定值就保证立即切换。JDK 21 HotSpot 与 ART 都有 OSR 相关路径，具体入口、限制和阈值各自定义。

反优化恢复的是语义状态

假设 outer 调用 inner，JIT 把 inner 内联，并消除了其中的 Pair 分配。机器上可能只剩 outer 的一帧和若干寄存器值。若某个优化依赖失效，需要恢复的却可能是 outer、inner 两层逻辑帧，以及仍会被后续代码使用的对象。

  1. 在规定位置确定失效原因与恢复点，避免把普通 IC miss 都当成反优化。
  2. 依据恢复元数据取得各逻辑帧的执行位置、局部值、表达式中间状态和必要的同步状态；来源可为寄存器、栈槽或常量。
  3. 对被消除但后续需要的对象重新物化，恢复字段与别名关系；两个逻辑变量原指向同一对象时不能恢复成两个独立副本。
  4. 构建目标执行状态，再从对应位置继续。哪些操作已完成、哪些还需执行，由恢复点及相应重执行规则确定，不能把已发生的写入或 I/O 随意重放。

因此，反优化不是简单“丢掉机器码再从方法第一行解释”。某方法的代码不再允许新调用进入，与它已没有任何活跃帧、可以回收存储，是不同条件；失效、在栈帧转换和代码回收需要协调。

HotSpot 的 ScopeDesc 等信息描述逻辑作用域、局部值与表达式状态，Deoptimization 负责恢复和物化。ART 有自己的帧与恢复格式。GC 只知道“哪个槽是引用”还不足以完成这一过程；对照几种元数据的职责。

参考：ART JIT 与 OSR · JDK 21 Deoptimization · JDK 21 ScopeDesc。

ART 的恢复元数据见HEnvironment。

用证据区分预热、编译与反优化

“第一次慢、后面快”可能来自类初始化、文件页与数据缓存、解释执行或 JIT。先分清一次进程启动与稳态吞吐，再将编译事件和业务耗时放到同一时间线上；不能用一次计时证明某个方法已内联或某对象已被标量替换。

观察、候选原因与补充证据
观察要区分的原因证据
多轮运行逐渐变快编译、初始化或缓存逐步就绪新进程与同进程分组，记录类加载 / 编译时间线及实际工作量
输入类型变多后变慢分派成本变化、优化依赖失效，或输入本身更昂贵匹配调用点、类型分布、编译 / 失效事件；不能只看一条 made not entrant

HotSpot/JDK 21 可在受控测试中使用 -XX:+PrintCompilation观察编译记录，或用 JFR 关联编译、执行、分配等适用事件；日志中的 OSR 标记、编译级别和失效文字需按该版本格式解读。要证明具体优化还应检查适用的编译日志或生成代码，性能结果本身不是优化过程的证据。

一个类型变化实验可固定每轮输入数量和工作量，先主要调用实现 A，再引入实现 B，对齐记录类型切换和延迟。它是检验假设的设计，不保证特定 JIT 必然去优化；重复新进程试验并区分预热与测量。避免结果未使用导致死代码消除，也不要通过随意加 volatile 改变原问题。

严肃的 JVM 微基准可用 JMH 的独立进程、预热和结果消费机制；Android 启动场景则见编译状态对照。两者测试对象和环境不同，不直接比较一个毫秒数。

HotSpot 对象优化

逃逸、标量替换与锁消除

static final class Pair {
    final int x, y;
    Pair(int x, int y) { this.x = x; this.y = y; }
}
static int sum(int a, int b) {
    Pair p = new Pair(a, b);
    return p.x + p.y;
}

若编译器能看到相关构造与使用、确认不需要保留可观察的对象身份，可把 p.x / p.y 化为独立值，最终只计算 a+b。逃逸分析提供是否逃出方法 / 线程等信息，标量替换是可能采用的变换；分析成功也不保证每种代码形态都能消除分配。写入静态容器、传入无法分析的调用或观察身份，都可能影响决策。

JDK 21 HotSpot C2 的这一优化不能一概表述为“对象从堆搬到栈”。若同步只作用于无法被其他线程访问的对象，编译器也可能消除相应锁操作；正确性依赖分析与语言语义。优化帧还可能需要在反优化时重新物化对象。GC 篇保留分配职责，这里负责解释为何分配会消失。

参考：MemorySSA 与内存依赖 · 目标 lowering、活跃性与代码生成 · HotSpot 逃逸分析与标量替换。

HotSpot 垃圾回收实现

GC Roots、并发标记、屏障和转发的共同机制见垃圾回收基础。

HotSpot G1 的区域与回收周期

区域角色与回收集合

以 JDK 21 HotSpot G1为例，堆由等大的 region 组成，分别承担 Eden、Survivor、Old 或空闲空间等角色。一次暂停选定的回收集合称为 collection set；记忆集帮助找到集合外的入边，疏散把集合中的活对象复制到目标区域。区域属于某一代，不要求整代在地址上连续。

大对象可走 Humongous 区域路径，在老年代取得连续的 region。此时即使总空闲量不少，也可能受连续区域不足与末尾浪费影响。不能把“G1 按 region 管理”理解为任何对象都可以拆开塞进任意空闲小块。

把标记、屏障与疏散连成一轮

  1. 年轻代收集：Normal Young 暂停回收年轻区域，复制存活对象并按策略晋升，老年代占用逐步变化。
  2. Concurrent Start：达到并发周期的启动条件后，在一次年轻代暂停中启动标记工作。
  3. 并发标记：与应用一起运行，使用前文的 SATB 机制保留起始存活信息；期间仍可能发生普通年轻代暂停。
  4. Remark / Cleanup：用暂停完成标记收敛和相关处理，并确定后续区域回收所需状态；二者之间还有并发工作，不能把整段统称为一次暂停。
  5. 混合收集：进入空间回收阶段后，在多次 Mixed 暂停中回收年轻区域及选定的老年代区域，随后回到以年轻代收集为主的阶段。

这是常见周期主线，具体执行可因回收收益等条件跳过后续工作。并发标记判断哪些对象需要保留；Young / Mixed 的对象疏散和引用更新仍在暂停内完成。SATB 与卡表屏障分别服务标记和区域引用追踪，不能互相替代。

若疏散目标空间不足，会出现 evacuation failure；若后续分配与回收仍无法维持运行，可能退回 Full GC，仍不足才可能报告 OOM。一次疏散失败不等于立刻 OOM。排查时联合观察老年代增长、Humongous 区域、并发周期是否赶得上分配，以及各暂停阶段耗时。

G1 的暂停时间是预测目标，不能保证每次都小于某个毫秒数，也不承诺固定吞吐率。固定年轻代比例可能限制它调节暂停工作量的能力；调优应从日志与负载出发。

参考：G1 区域与周期 · G1 暂停、疏散失败与诊断。

比较收集器时看哪些差异

按工作安排理解收集器
实例主要安排理解重点
HotSpot Serial / Parallel主要收集工作在暂停中完成，分别采用单线程 / 多线程工作方式并行能缩短部分工作耗时，但不等于与应用并发
HotSpot G1并发标记、暂停疏散，分批选择区域回收暂停预测、跨区域引用、疏散预留与回收收益
JDK 21 分代 ZGC通过 load / store 屏障支持并发标记与重定位等工作降低暂停需要引用访问协议，并付出 CPU、屏障和空间成本
Android 14 ART CC协调线程根切换后，并发复制与扫描分配空间、读屏障及根切换协议共同保证访问正确性

历史上的 CMS 用并发标记与清扫减少暂停，但要处理浮动垃圾、预留空间和碎片；它已在 JDK 14 移除，适合作为机制演进案例。收集器名称不能代替版本、模式和负载条件。
