1. 逻辑标签与分配标签

MTE（Memory Tagging Extension）是 Arm 的内存标记机制。在支持并启用检查的内存访问中，CPU 比较指针中的逻辑标签与目标内存颗粒的分配标签；不一致时产生标签检查故障。

经典 MTE 使用 4 位标签，每个 16 字节对齐的颗粒对应一个分配标签。逻辑标签位于地址表示中的指定高位，分配标签由硬件支持的标签存储维护，不是简单往每个对象结构体末尾加一个成员。地址转换与标签检查各有职责。

带标签指针：地址 A + 逻辑标签 5
内存颗粒 A：分配标签 5  → 标签匹配
内存颗粒 B：分配标签 9  → 用标签 5 的指针访问时不匹配
  1. 分配器选择标签，为相关颗粒设置分配标签，并返回带逻辑标签的指针。
  2. 程序通过该指针访问，硬件在适用条件下校验标签。
  3. 释放或复用存储时按策略改变标签，使旧指针更可能与新存储不匹配。

参考：Linux AArch64 MTE。

2. 能发现什么，不能发现什么

检测范围取决于实际启用范围与标签差异
情况判断
越界跨到不同标签颗粒可触发不匹配
释放后使用，原颗粒已换成不同标签可触发不匹配
同一 16 字节颗粒内的小越界标签可能仍一致，无法按真实对象边界识别
不同对象或复用后碰巧标签相同可能漏检；标签数量有限
未标记的分配/映射、未启用检查不应假定被保护
内存泄漏、业务状态错误、一般数据竞争不由 MTE 完整检测

随机标签的检出概率依标签集合和分配策略而变，不能把某个概率当作全部错误的覆盖率。堆、栈、全局对象是否标记也取决于分配器、编译插桩和平台配置。

经典问题：启用 MTE 之后，是否就没有悬垂指针？

悬垂指针仍可能产生。MTE 增加发现不匹配访问的能力，不会自动修正对象生命周期，也不能保证每次复用都得到不同标签。仍需所有权与边界设计。

参考：Android MTE 与分配策略。

3. SYNC 与 ASYNC

故障报告模式
模式报告位置与信息取舍
SYNC在触发访问处同步报告，适合定位故障指令定位精度较高，运行开销依硬件/实现
ASYNC先记录故障状态，在之后的适当时机报告通常有较低开销，但报告时 PC 不一定是首次错误指令

Linux 同步标签故障使用 SIGSEGV 的 SEGV_MTESERR，异步使用 SEGV_MTEAERR；同步可提供出错地址，异步报告的地址/时序信息有限。Android tombstone 中是否包含分配、释放栈还取决于模式与分配器记录，不能承诺所有报告都有三条完整栈。

经典问题：拿到 ASYNC 崩溃栈，是否直接修改栈顶函数？

不能直接归因。先确认故障模式与信号代码，用相同场景尝试 SYNC、保留符号并结合分配/释放记录定位。异步报告处可能只是系统发现待报告故障的位置。

参考：Linux 标签故障报告。

4. 覆盖与性能实验

  1. 确认硬件、系统、进程、分配器和目标内存类别均支持并启用 MTE；应用可按官方指南配置 manifest 的 memtagMode。
  2. 分别构造跨标签颗粒的越界和释放后访问作为故意错误样例，同时准备无错误对照。错误样例不能按普通 C++ 输出断言。
  3. 保留一组预期盲区：颗粒内越界、未覆盖区域；统计多次运行，不把一次未报错当作配置正确的证据。
  4. 对照关闭、SYNC、ASYNC 下相同业务负载的吞吐、延迟分位数、启动时间、RSS 与 CPU；记录设备与系统版本。

定位记录应包含模式、故障地址、读写类型、访问大小、PC/模块、匹配符号，以及可取得的分配释放栈。修复后用原触发路径验证，再做压力与边界检查；检测器配置不是修复本身。

参考：Android 应用启用 MTE。

5. Hook 与诊断边界

Hook在调用或执行路径中插入观察/替换逻辑，例如拦截分配接口采集调用栈。符号级 hook 只能覆盖经过该符号的路径；直接调用、内联、自定义分配器等可能绕过它，不能据此宣称全覆盖。

监测代码要处理重入、线程安全、递归分配与自身开销，并保存原调用语义。判断价值看能否定位实际错误、覆盖哪些路径和增加多少成本；MTE 的硬件访问检查与 hook 的软件观察点是不同层次。
