1. 可达性与 GC Roots

追踪式 GC从根集合沿对象引用寻找可达对象，再处理不可达对象。它依据可达关系，不依据“变量名还在不在”，也不要求对象引用图没有环。GC 线程之外执行应用代码的线程常称为 mutator。

根或根访问路径
场景为什么必须保留
线程当前栈帧、寄存器中的活引用方法后续还可能使用该对象
JNI local / global 强引用native 代码仍可能通过有效引用访问对象
运行时持有的类、线程和其他内部根运行时自身仍需要这些对象
已加载且可达的类的静态字段通过类对象和相关运行时根可继续到达字段指向的对象

具体根集合由运行时实现与线程状态决定；弱引用需要特殊处理，不等价于普通强根。移动 GC 还需识别并修正引用，不能简单扫描任意整数并把“像地址”的值都移动。

经典问题：两个对象互相引用，GC 是否一定回收不了？

追踪式 GC 可以回收整个不可达环。只要没有从根到达这个环的强可达路径，就不因互相引用而保留；引用计数系统中的强引用环是另一种机制的问题。

2. 回收算法与并发复制

算法侧重点
方式机制典型代价
标记清扫标记活对象，回收未标记对象可能留下外部碎片
标记整理标记后移动活对象并更新引用整理与引用更新成本
复制将选定区域的活对象搬到目标区域，回收旧区域需目标空间；成本与活对象量相关
分代按对象存活特征划分收集范围维护跨代引用；不能漏掉老对象指向年轻对象的边

以 AOSP android-14.0.0_r1 的 ConcurrentCopying 为具体例子，RunPhases 的主线如下。不同配置会选择不同分支，不能把 CC 概括成“全程暂停复制”。

  1. InitializePhase 准备本轮状态；特定分代全堆场景先执行 MarkingPhase，计算存活情况。
  2. 启用相应读屏障入口、处理需要的卡信息，再通过 FlipThreadRoots 协调线程根与空间状态切换。
  3. CopyingPhase 与应用并发推进：复制需迁移的活对象，扫描引用、处理标记工作；读屏障帮助访问获得正确对象。
  4. ReclaimPhase 回收可释放区域，FinishPhase 收尾并更新统计。验证选项可能额外引入暂停。

读屏障是在读取对象引用时执行的附加逻辑。并发移动期间，应用可能读到旧地址；屏障根据对象/空间状态找到、复制或标记目标并提供正确引用。它不是操作系统的内存屏障，也不等于 C++ atomic 的内存序。

经典问题：并发复制时为什么仍可能暂停？

切换线程根、同步关键状态等步骤需要与应用线程协调。大量复制可并发执行，但这不意味着无暂停；区分 GC 总耗时、暂停时长和应用受到的 CPU/屏障开销。

参考：Android 14 CC 源码 · ART GC 调试文档。

若复习 JVM 面试中的三色标记、STW、转发地址与屏障，见 三色漏标反例及 并发移动与转发。那里区分通用原理、G1 与分代 ZGC；本节仍限定 Android 14 ART 的实现。

3. Young、Full 与卡表

卡表把一段堆划成较粗粒度的 card；写屏障在相关引用写入后标记卡，后续只扫描受影响范围。它记录的是“这片区域需要检查”，通常不是每条精确引用。

Young GC 只回收选定的年轻范围，但老对象可能指向年轻对象，因此仍需根和跨代引用信息。Full GC 涉及更广收集范围；某实现仍会利用卡表扫描免收集空间或并发修改，不应简单说“Full 一定不用卡表”。

GC 可因分配压力、目标堆占用、显式请求或运行时策略触发。是否转为更全面收集取决于版本、分配结果和回收收益。最耗时阶段可能是根/卡扫描、对象扫描、复制等，要读阶段计时；Young 与 Full 不存在固定耗时倍数。

经典问题：扩大堆后，GC 必然更少且更快吗？

频率可能下降，但一次收集的活对象和扫描范围可能变大，物理压力也可能增加。应一起比较每秒 GC 次数、暂停分位数、总 CPU、复制字节、回收收益和 RSS/PSS。

4. 堆空间与引用表示

常见空间角色，具体配置依版本
空间用途与机制
RegionSpace按区域管理对象，支持 TLAB 分配与选定区域的迁移；区域还可表达大对象及其尾部区域
LargeObjectSpace专门管理符合条件的大对象；通常避免搬动大块对象，分配和回收策略不同
NonMovingSpace承担要求或选择不移动的分配；不移动不等于不做可达性判断和回收
Image / Zygote 等空间启动映像、预加载与共享相关，收集中的处理方式依空间属性

在 Android 14 上述 tag 中，ShouldAllocLargeObject 同时检查大小阈值，以及对象是否为原始类型数组或 String。因此“任意超过 4 KB 的对象都进入 LOS”不成立；阈值也不是所有设备固定常量。降低阈值可能减少其他空间压力，却增加独立大块分配、碎片和映射管理成本。

复制预留空间用于容纳迁移中的活对象。逻辑堆上限、RegionSpace 映射容量、疏散预留和实际物理占用不能互相替代；经典半空间模型的二倍存储直觉不能直接当作所有 ART 配置的固定比例。

该版本 HeapReference 内部保存 Atomic<uint32_t>，PtrCompression 负责与实际对象指针转换，并可处理引用 poisoning。它不是普通 native 指针大小，也不是 JNI jobject；扩大可寻址对象范围可能涉及引用编码、空间布局和访问路径，不能只改一个容量数字。

参考：Android 14 分配判断 · HeapReference 与转换 · RegionSpace。

5. OOM 与应用侧排查

Java OutOfMemoryError是运行时无法满足相应分配请求的错误；Linux/Android 因全局或进程内存压力终止进程，是另一条路径。抛 OOM 不等于在该指令处必定立刻被系统杀死，但捕获异常也不自动恢复可用内存或业务状态。

  1. 先确认是 Java 堆分配失败、native 分配失败、地址空间/碎片问题，还是系统杀进程；保留日志和构建信息。
  2. 记录失败申请大小、存活量、堆目标/上限、GC 前后变化及进程内存分类。
  3. 对比多轮相同业务的 heap dump，沿 GC Roots 引用链查不必要的持有；native 增长另查分配调用栈。
  4. 应用侧减少峰值同时存活数据、按需加载、缩小图片/缓存、及时取消任务；修复引用链后用同负载复测。

HPROF 是堆转储格式之一，可用于分析托管对象和引用。dump 本身有开销，且不覆盖所有 native、映射或图形资源；“Java 堆不涨”不能排除进程内存问题。

经典问题：具体扩堆上限和 ART 统计函数能否背一个通用答案？

不能。要核对目标分支、指针/引用表示、配置、空间约束和实际改动。平台项目可沿 JNI 注册、native 实现到 Heap/collector 统计接口追踪；应用公开 API 与内部函数不是同一接口合同。

参考：Android 内存概览 · 捕获 heap dump。
