一、IR、优化与代码生成

本部分主要用到机器调用与寄存器约束；CFG 与 SSA 在本部分定义，托管类加载不是通用编译原理的统一前置。

先把程序表达成便于分析的控制流与数据流，再讨论变换的正确性和目标机器约束。词法、语法与语义分析在这里作为流程概览，重点是 IR、SSA 和代码生成。

1. 编译阶段与中间表示

从源码到机器码
阶段输入 → 输出主要任务
词法分析字符 → token识别标识符、关键字、字面量等
语法分析token → AST按文法建立结构，报告语法错误
语义分析AST → 带类型/绑定信息的表示名字查找、类型检查、作用域与转换
IR 生成与优化高层结构 → 中间表示显式表达控制流、数据依赖与内存操作
代码生成IR → 目标指令指令选择、寄存器分配、调度与目标约束
汇编与链接汇编/目标文件 → 可执行程序或库编码指令、解析符号与重定位

AST保留源程序语法结构；IR为分析和变换提供规则更统一的表示。同一编译器可以有多层 IR，从接近语言语义逐步降低到机器指令。汇编器主要完成目标指令编码；解释器直接执行某种表示的语义，不必先生成本机代码。

record/结构体需要字段类型、偏移、大小与对齐规则；类继承还涉及基类子对象、访问与动态分派。先确定语言语义，再按 ABI 降低到布局和地址操作，不能仅把每个字段按字节相加。

2. 基本块与控制流图

基本块是一段从入口顺序执行到结尾转移的指令序列；中间没有控制流跳入。CFG以基本块为节点，以可能的控制流转移为边。

  1. 在线性三地址码中，把第一条指令、跳转目标和转移指令后的新指令标为块首。
  2. 相邻块首之间构成基本块；以跳转、条件分支、返回等确定终结。
  3. 按各终结指令建立后继边，构造前驱列表；异常控制流也要按 IR 模型纳入。

条件分支通常有两个后继，返回没有普通后继。不能仅按花括号切块：短路逻辑、循环与异常处理都可能产生额外边。

从 CFG 计算支配与活跃性

对可达块，入口只被自己支配；其他块的支配集合可初始化为全部可达块，再反复计算 Dom(B) = {B} ∪ ∩ Dom(P)，P 为 B 的前驱，直到不再变化。菱形 CFG 的两条分支互不支配，合并块的共同支配者可以只有入口与自己。

entry → left  → merge
      → right → merge

Dom(left)  = {entry, left}
Dom(right) = {entry, right}
Dom(merge) = {entry, merge}

源变量 v 分别在 left / right 定义，merge 使用：
  需要把各路径值汇合，后面的 SSA 例子用 phi 表达。

活跃性问的是“这个值以后是否还会在被覆盖前使用”。在非 SSA 的块级模型中，可迭代计算 OUT[B] = ∪ IN[S]、IN[B] = USE[B] ∪ (OUT[B] − DEF[B])；USE 指块内先使用后定义的值，S 为后继。SSA 的 phi 输入使用发生在前驱边上，不能把所有输入都当作合并块同时需要的普通使用。

支配帮助判断某定义是否覆盖所有到达路径；活跃性帮助决定哪些值必须保留、哪些值能共用寄存器。两种分析都不直接证明内存没有别名。

3. SSA 与 phi

SSA（静态单赋值）要求每个 SSA 值只有一个定义。源变量反复赋值时使用不同版本；控制流合并处用 phi 根据实际前驱选择对应版本。它不是同时执行所有分支，也不是求平均。

define i32 @choose(i1 %cond, i32 %x) {
entry:
  br i1 %cond, label %yes, label %no
yes:
  %a = add i32 %x, 1
  br label %merge
no:
  %b = sub i32 %x, 1
  br label %merge
merge:
  %result = phi i32 [ %a, %yes ], [ %b, %no ]
  ret i32 %result
}

支配：从入口到 B 的每条路径都经过 A，则 A 支配 B。支配边界描述某定义可能与其他路径定义相遇的合并位置。经典 SSA 构建先计算支配关系，在迭代支配边界放置 phi，再沿支配树用版本栈重命名定义与使用；可结合活跃性省掉无用 phi。

经典问题：SSA 是否表示内存永远只写一次？

不是。SSA 约束 IR 值名的定义；store 仍可反复修改内存。对内存的依赖分析需别名分析或 MemorySSA 等额外表示，不能把不同 load 的结果直接视为恒等。

参考：LLVM phi 语义 · LLVM MemorySSA。

循环里的 phi：静态一次定义，动态反复执行

循环头有入口边和回边，phi 合并初始值与上一轮结果。以下函数累加 0..n-1，演示 phi 的控制流语义；示例输入前提为 n 非负且数学结果能放入有符号 i32。这是便于演算的数值范围，不是 ABI 调用约定；代码中的普通 add 未附加 nsw / nuw，溢出时按位宽回绕。

define i32 @sum_to(i32 %n) {
entry:
  br label %loop
loop:
  %i = phi i32 [ 0, %entry ], [ %next, %body ]
  %sum = phi i32 [ 0, %entry ], [ %updated, %body ]
  %more = icmp slt i32 %i, %n
  br i1 %more, label %body, label %exit
body:
  %updated = add i32 %sum, %i
  %next = add i32 %i, 1
  br label %loop
exit:
  ret i32 %sum
}

n=3 时，进入循环头的 (i, sum) 依次为 (0,0) → (1,0) → (2,1) → (3,3)，最后返回 3。%i 只有一处静态定义，但该定义可以动态执行多次；“循环变量会变化，所以不能是 SSA”混淆了静态程序与动态执行。

在 LLVM IR 中，phi 必须集中在基本块开头，输入成对标明值与前驱；输入值的使用发生在对应边上。因此 %updated 只需在 body→loop 的边上可用，不需要在 entry→loop 的边上也有定义。同一块的多个 phi 同时选择对应边的输入。

phi、select 与优化收益

phi 按实际进入的前驱选值；select 按显式布尔条件从已可用的操作数中选值。把分支改成 select 时，不能随便把原本只在一个分支执行的可能抛异常、越界或有副作用的计算提升到公共路径。phi 通常在后端转成边上的复制或经寄存器合并消失，不要求 CPU 有名为 phi 的指令。

SSA 使定义—使用关系明确：沿值的唯一来源做常量传播，按使用关系删除死值，检查支配与别名后复用计算。它不会自动解决别名、内存依赖或正确性问题；“SSA 就等于更少寄存器”也不成立，寄存器压力还要看活跃区间。

面试追问：面试要求手工构建 SSA，按什么顺序？

先画 CFG 并标入口、回边与合并块；算支配关系，在需要汇合多个定义的迭代支配边界放 phi；沿支配树重命名定义与使用，给每条前驱边填入对应版本；最后去掉无用或输入相同的 phi。循环头的回边输入不要漏填。

3.1 ART HGraph：把 CFG 与 SSA 落到编译器对象

HGraph 是 ART optimizing 编译器的图表示，不是 DEX 文件格式，也不是 LLVM IR 的别名。以 AOSP android-14.0.0_r1 为例，它组织一个编译单元的基本块、控制流与分析信息；HBasicBlock 保存前驱、后继以及指令，HInstruction 表达运算及其输入和使用关系，HPhi 表达合流值。图在构建、SSA 转换、优化和目标降低过程中逐步变化。

源方法：int choose(boolean c, int x) {
          int y;
          if (c) y = x + 1; else y = x - 1;
          return y;
        }

示意 HGraph（省略入口、退出及具体节点编号）：
B0：参数 c、x；HIf(c)       → B1 / B2
B1：a = HAdd(x, 1)        → B3
B2：b = HSub(x, 1)        → B3
B3：y = HPhi(a, b)；HReturn(y)

控制流边：B0→B1、B0→B2、B1→B3、B2→B3
数据依赖：HAdd/HSub 使用 x；HPhi 使用各前驱提供的值

这是关系图示，不是某次编译的逐字 dump；实际图还受空检查、异常边、常量节点和优化结果影响。阅读 dump 时先看块间路径，再看每个值的定义和使用，最后检查变换是否保持支配、phi 输入与异常语义；只按节点的显示顺序阅读会漏掉图关系。

可以顺着 HGraphBuilder → SSA 与优化 pass → 位置约束 / 寄存器分配 → CodeGenerator 追踪。需要异常或反优化状态的指令还可带 HEnvironment，它与普通输入边的职责不同，见编译期环境与运行时恢复。AOT / JIT 何时触发这条编译流程，放在ART 编译与启动中讨论。

参考：ART HGraph、HBasicBlock、HInstruction、HPhi · optimizing 编译流程。

4. phi 消除与寄存器分配

降低 SSA 时，可把 v = phi(a from A, b from B) 变成在边 A→合并块上执行 v←a、边 B→合并块上执行 v←b。若前驱有多个后继而目标有多个前驱，直接把复制放任一块可能在错误路径执行，应按需要拆分临界边。

同一条边上的多项复制具有并行语义。交换 a、b 不能依次执行 a←b、b←a，否则第二步读到已覆盖值；可用临时 t：t←a、a←b、b←t。寄存器合并可以消掉一部分复制。

虚拟寄存器是编译器表示中的值位置，不受硬件寄存器数量直接限制。分配器按活跃区间与干涉关系映射到物理寄存器；位置不足时 spill 到栈并插入 load/store。调用约定、寄存器类别和保存成本也属于约束。

线性扫描：按活跃区间起点分配

经典 linear scan 把程序位置线性编号，按区间起点遍历，维护按结束位置排列的 active 集合。处理新区间前释放已结束区间的寄存器；有空位就分配，没有空位则选择 spill。下面采用“比较结束位置，优先移出结束最晚的区间”的教学策略；真实实现可按使用位置拆分区间、处理空洞并估算溢出成本。

两个同类寄存器 R1、R2；半开区间 [start, end)：
a = [0, 8)    b = [1, 3)    c = [2, 6)    d = [6, 9)
位置 2 同时活跃 a、b、c，两个寄存器无法容纳三个值。
位置 6 的 c 已结束，因此 c 与 d 不干涉。
按起点扫描与选择溢出
到达位置处理分配后状态
0：a 开始取空闲 R1a→R1
1：b 开始取空闲 R2a→R1，b→R2
2：c 开始a 在 8 结束，比 c 的 6 更晚；选择 a 溢出c→R1，b→R2；a 的值须保存到栈
6：d 开始b、c 已结束，释放其寄存器d 可取 R1；a 后续使用需 reload

这个表是在手算区间的分配决定。实际生成代码时要在覆盖寄存器前保存仍需使用的值，并在使用前重载；重载产生的短临时区间也要满足指令约束。分裂区间的实现可保留 a 的前段寄存器位置，整段溢出的简化实现则重写其定义与使用；不能只把分配表中的 a 改成“栈”就认为机器码已经正确。

参考：Poletto、Sarkar：Linear Scan Register Allocation。

图着色：不能共用寄存器的值连边

干涉图的节点代表待分配的值，边表示两值不能占用同一个寄存器。用 K 个颜色代表 K 个可用同类寄存器：相邻节点必须不同色。对上面的区间，边为 a—b、a—c、a—d、b—c；其中 a、b、c 构成三角形，所以 K=2 时不可能全部留在寄存器中。

  1. Simplify：反复删除度数小于 K 的节点并压栈。先删 d，它只有邻居 a。
  2. 选择候选：剩余三角形没有度数小于 2 的节点。为与前例对照，这里选 a 为潜在 spill 候选，暂时移除；真实选择还应看使用频率、循环和代价。
  3. 继续简化：剩下 b—c，可依次压栈 b、c。
  4. Select：逆序恢复：给 c 分 R1，b 分 R2；恢复 a 时两个颜色都被邻居占用，确实需要 spill。d 恢复后可分 R1。
  5. 重写与重试：为 a 加入必要的栈存取，重新分析新增短区间与干涉，再完成分配。

“度数大于等于 K”本身不证明必须 spill：某些图仍可着色，乐观着色允许候选在恢复时找到颜色。本例必须溢出的证据是三角形需要三个颜色。复制合并还能减少 move，但若合并引入过多干涉，也可能增加溢出；实际算法要处理预着色寄存器、寄存器类别及目标指令限制。

线性扫描通常较容易控制编译开销，图着色显式处理全局干涉；不能把名称直接等同于“一个总快、另一个生成代码总好”。Android 14 ART 的分配器工厂具有 linear-scan 与 graph-color 策略，实际选择须追踪编译选项，不能背成“JIT 必用前者、AOT 必用后者”。

参考：Appel：带预着色节点的分配示例 · ART 寄存器分配策略。

经典问题：把所有 phi 换成合并块开头的普通 move 可以吗？

不可以。合并块必须知道来自哪个前驱才能选择输入；无条件顺序执行所有 move 会取错值。复制必须放到对应路径，并处理并行复制冲突。

参考：LLVM 代码生成。

从值运算到目标指令

目标 lowering 还要处理硬件支持的类型、指令寻址和调用约束，之后才能分配寄存器、安排指令顺序。调度可重排独立工作以隐藏延迟，但必须保留数据依赖、内存顺序与必要的异常语义。

Java：static int tripleSum(int a, int b) { return (a + b) * 3; }

等价的 i32 值运算（不附加“不会溢出”的标记）：
  t = add a, b
  r = mul t, 3
  return r

一种按基础 AAPCS64 传参的 AArch64 运算示例：
  add w0, w0, w1
  add w0, w0, w0, lsl #1
  ret

第二条指令把 t 与 2t 相加；这里都保留低 32 位，符合该 Java int 运算的回绕语义。本示例另约定按基础 AAPCS64 在 w0/w1 接收 a/b，并从 w0 返回结果；它展示运算如何降低到机器指令，不代表 HotSpot 或 ART 实际编译该 Java 方法时使用这套入口。VM 的托管调用约定与 native ABI 需要通过适配代码衔接。

a 最后一次使用后 w0 可承载 t，再承载返回值。指令选择消除了显式乘法，不代表所有处理器上它一定更快；这里只验证运算语义与所指定的位置安排。

参考：JDK 21 AArch64：Java 与 C 调用约定及适配。

跨调用活值为什么需要保存

概念 IR：
  t = a + b
  r = call opaque()
  return t + r

一种 AAPCS64 保存方案（省略展开指令等汇编元数据）：
  stp x19, x30, [sp, #-16]!
  add w19, w0, w1
  bl opaque
  add w0, w19, w0
  ldp x19, x30, [sp], #16
  ret

t 跨调用仍活跃，不能只留在允许 opaque 覆盖的 w9。这里让 w19 保存 t，同时保留调用者原来的 x19 与返回位置，栈仍满足对齐。也可选择 spill 槽，在调用后 reload；寄存器不足时要综合活跃区间、寄存器类别、调用频率和保存成本。spill 是值的位置变化，不是创建新的语言层对象。

5. 优化的前提与代价

常见优化
优化变换必须确认的前提
常量传播 / 折叠用已知值替代计算值确实确定，遵守目标语义与溢出规则
死代码删除删除不影响可观察行为的计算无需要保留的副作用、异常或 volatile 访问
公共子表达式消除复用已有计算结果操作数相同，相关内存未被可能的别名写入改变
循环不变量外提把不随迭代变化的计算移到循环外依赖、异常与执行条件允许移动
内联 / 去虚拟化展开调用或确定调用目标目标可确定，收益超过代码膨胀与编译成本
向量化一次处理多个数据元素依赖、别名、对齐与浮点语义允许

优化后的快慢需结合真实输入与热点衡量。浮点结合律通常不能像实数一样任意重排；C++ UB 也会影响编译器可以采用的推理，不能用“硬件会回绕”代替语言规则。

有两个相同 load，为什么不一定能合并

前提：p / q 有效，访问普通非 volatile 内存
a = load p
store q, 9
b = load p
return a + b

若 p 与 q 指向同一位置，第二次读取应看见 9；把 b 无条件替换成 a 会改变结果。只有证明写入不影响 p、没有其他相关干扰等条件，才可能复用。MemorySSA 用 MemoryDef、MemoryUse、MemoryPhi 表达内存依赖候选关系；结合别名分析查可能覆盖的写入，不是把每个内存字节变成永不修改的 SSA 变量。

类似地，循环不变量外提不仅看操作数不变。循环可能执行零次时，把原本位于循环里的可能故障的 load 或有副作用的调用移到入口，可能凭空增加一次访问。需要证明可安全提前执行，或保留必要的执行条件。

逃逸、标量替换与锁消除

static final class Pair {
    final int x, y;
    Pair(int x, int y) { this.x = x; this.y = y; }
}
static int sum(int a, int b) {
    Pair p = new Pair(a, b);
    return p.x + p.y;
}

若编译器能看到相关构造与使用、确认不需要保留可观察的对象身份，可把 p.x / p.y 化为独立值，最终只计算 a+b。逃逸分析提供是否逃出方法 / 线程等信息，标量替换是可能采用的变换；分析成功也不保证每种代码形态都能消除分配。写入静态容器、传入无法分析的调用或观察身份，都可能影响决策。

JDK 21 HotSpot C2 的这一优化不能一概表述为“对象从堆搬到栈”。若同步只作用于无法被其他线程访问的对象，编译器也可能消除相应锁操作；正确性依赖分析与语言语义。优化帧还可能需要在反优化时重新物化对象。GC 篇保留分配职责，这里负责解释为何分配会消失。

参考：MemorySSA 与内存依赖 · 目标 lowering、活跃性与代码生成 · HotSpot 逃逸分析与标量替换。

6. 解释执行、AOT、JIT 与热点统计

AOT在目标程序本次执行前生成机器码；JIT在运行过程中按需编译，可使用运行时类型和热点信息。解释执行、低成本编译、优化编译可组成不同层级，平衡启动、峰值性能与编译资源。C1/C2 是 HotSpot 的特定分层术语，不是所有 JIT 的统一级别。

执行方式
方式收益成本
解释无需先为所有方法生成本机代码反复解释热点指令有成本
JIT按运行热点生成代码并利用运行信息占用应用运行期间的 CPU、代码缓存与元数据
AOT提前生成可复用机器码编译耗时、磁盘体积；可能编译并不热的方法

运行时还需要在解释帧、编译帧和 native 调用间转换。编译代码依赖相应检查、类状态和 GC 协作信息，不是与运行时脱离的一段裸机器码。

HotSpot C1 / C2：为什么分层

以 JDK 21 HotSpot 的编译级别为例，C1 是编译开销较低的编译器，可按级别产生不同数量的运行反馈；C2 花更多编译资源追求更强的优化。分层让热点代码较早脱离解释执行，同时继续积累调用与类型信息，供后续优化使用。级别是代码的编译状态，不是“一个方法一定按 0、1、2、3、4 各跑一遍”的固定流水线。

编译级别与主要职责
级别执行形式反馈与用途
0解释执行可收集热点信息，并决定是否提交编译任务
1C1 简单编译较快获得机器码，不承担完整的类型反馈收集
2C1 有限 profiling记录调用与回边计数等有限信息
3C1 完整 profiling除计数外记录方法数据中的更丰富反馈，为高层优化提供证据
4C2 完整优化；配置 JVMCI 时也可由其承担利用已有反馈进行更重的优化，增加编译 CPU、时间和代码缓存成本

实际升层由热点、编译队列、代码缓存、编译器是否可用及配置共同决定，可能跳级或停在较低级别；长循环还可能经 OSR 在循环中途切换。C2 依据类型反馈生成的快速路径仍要保证假设失效时可安全处理，可能走慢路径或反优化；这与“C2 机器码永远不退回解释”不同。反优化怎样恢复执行状态见OSR 与反优化。

面试追问：为什么不把所有方法一开始就交给 C2？

很多方法并不热，提前做重优化会花编译 CPU、延迟与代码缓存；初次执行也缺少有价值的类型和分支反馈。解释与 C1 先提供低成本执行和采样，运行时再把值得投入的方法交给 C2。是否收益更好仍取决于负载和配置。

参考：JDK 21 HotSpot CompLevel 定义 · JDK 21：分层编译与代码缓存。

AOT 编译怎样做优化

AOT 说明生成机器码的时机，不指定一套独有的优化算法。编译器仍可在 IR 上做常量传播、死代码删除、内联、循环优化和寄存器分配；每项变换的语义前提见优化的前提与代价。运行前已知的类型、调用关系和目标 ISA 可用于静态分析，但运行时才出现的接收者类型或分支频率不能凭空假定。

例如某虚调用有多个可能目标：若 AOT 编译时能证明目标唯一，可以直接调用或内联；若只有历史 Profile 显示某类型常见，可在支持相应协议的运行时生成“类型检查 → 热门目标快速路径 → 其他目标慢路径”，并保留假设失效后的正确执行方式。没有证明或反馈时应保留通用分派。由此可见，Profile-guided AOT仍是 AOT，利用过去运行的数据不等于在本次运行中 JIT 编译。

以 ART 为例，dex2oat 的 speed 倾向编译所有方法，speed-profile 依据 Profile 选择方法并优化相关类加载；已有类型反馈也可支持某些 AOT 调用点优化。要同时权衡编译耗时、磁盘中的机器码大小、启动时间、峰值执行速度和 Profile 的代表性。选择编译哪些方法与怎样优化单个方法是两个不同问题；具体 pass 和过滤器行为须限定 ART 版本。

面试追问：AOT 没有运行时信息，所以不能做内联吗？

不能这样说。目标在编译时可证明时可以静态内联；也可以用已有 Profile 做受检查的猜测性优化，前提是运行时提供相应的慢路径或状态恢复。没有可靠证据时不能把可能变化的目标无条件固定。

参考：Android：ART AOT 与 compiler filters · Android：Profile 与 AOT 调用点优化。

热点统计与编译调度

一种热点设计是在方法元数据中保存饱和调用计数、回边计数和编译状态；达到阈值后入队，避免重复编译。采样或线程本地计数可降低竞争；计数合并、过期、代码缓存容量和反优化也要纳入。无需每次调用都建立字符串键哈希表。

经典问题：热点统计应选择什么数据结构？

通常可把计数与状态放在方法关联元数据中，结合调用/回边计数或采样，降低查表和同步开销；编译队列要去重，计数可饱和。真实字段、阈值和队列实现需对照目标运行时分支。

经典问题：调低 JIT 阈值一定让启动更快吗？

不一定。较早生成机器码可减少热点解释成本，也会提前占用 CPU、内存和编译队列，可能与启动关键线程争抢资源。按冷/热启动、编译时间、执行节省和代码缓存占用做对照，不能只比较单个函数执行速度。

Profile 与代码缓存

经典问题：“JIT 预编译”通常需要怎样澄清？

如果指运行前依据已有 profile 生成机器码，那更接近 profile-guided AOT；如果指在运行中提前安排将使用的方法编译，则仍是运行时策略。应明确生成时间、输入信息和代码保存位置。

代码缓存回收处理可回收的 JIT 机器码及随代码保存的辅助信息；Java 堆 GC 处理对象可达性。代码、运行时类型反馈和持久化 profile 的存储与寿命必须分别看。以 JDK 21 HotSpot 为例，MethodData 中的方法反馈分配在 Metaspace；Code Cache 中的 profiled code heap 保存的是带 profiling 的编译代码，不能理解成存放全部 profile 数据的堆。

ART 有自己的 JIT 代码及 profiling 管理方式。回收一段机器码不等于删除全部类型反馈或磁盘 profile，也不等于清空 Java 堆；代码失效、类卸载和各类存储回收通过运行时协议协调。

参考：JDK 21 MethodData::allocate：反馈的元空间分配。

ART 的实际编译与 profile 流程见 ART 编译与 Android 应用启动。

参考：HotSpot：分层编译与代码缓存。

7. Inline cache、类型反馈与反优化

Inline cache（内联缓存，IC）是在调用点缓存接收者类型与调用目标的关系。同一个虚调用点往往反复遇到同一类对象；缓存命中时可缩短动态分派路径。这里的 inline 描述缓存贴近调用点，并不等于把被调用函数体展开。

调用点：receiver.work()
首次执行：尚无缓存 → 运行时解析 receiver 的类型与目标
单态路径（概念）：
    按语言要求处理 null
    if receiver.klass == cached_klass:
        call cached_target(receiver)
    else:
        进入 IC miss / 运行时分派路径

方法解析、普通分派与类身份见托管调用基础。缓存键必须足以识别运行时类型，例如可靠的 Klass 身份；同名类可能由不同类加载器定义，不能只比较类名字符串。虚表按类描述方法槽位，IC 则利用某一个调用点的类型规律，两者可以配合。

  • 未链接 / 未初始化：第一次调用尚需解析。
  • 单态（monomorphic）：调用点反复看到一种接收者类型，可使用类型检查加直接目标。
  • 多态内联缓存（PIC）：一般设计中可缓存少量“类型→目标”对，按 guard 逐一检查。
  • 超多态（megamorphic）：类型过多时，维护长检查链得不偿失，可退回通用虚表 / 接口表等分派。

上面是通用设计词汇，不是每个 HotSpot 调用点都必经四级状态。JDK 21 的 CompiledIC 主要表达 clean、monomorphic、megamorphic 等状态；JIT 根据 profile 生成多个类型 guard 的优化代码，与 CompiledIC 自身是否维护 PIC 数组是不同问题。

类型反馈怎样支持内联和反优化

JIT 看到单态热点后，可以生成“类型 guard + A.work 的内联代码 + 失败路径”。原 IC 快速调用仍存在一次调用，内联则消除了调用边界，并给后续常量传播、逃逸分析等提供机会。内联要平衡收益、代码膨胀和指令缓存压力。

当接收者出现新类型时，普通 IC miss 可以进入运行时解析并更新状态，不必每次都反优化。如果机器码依赖了更强假设，例如类层次分析认定某方法只有一个实现，则新类加载可能使依赖失效，触发失效处理或反优化。反优化需要用元数据恢复解释执行所需的局部变量、操作数栈和内联帧状态。

修改目标与缓存类型还必须满足并发发布协议，避免其他线程看到“新类型配旧目标”；代码修补也需遵守目标架构的指令可见性要求。这是运行时实现细节，不能直接用两次普通赋值替代。

面试追问：IC miss、缓存状态变化、反优化是同一件事吗？

不是。miss 表示当前接收者不满足该缓存快速路径；运行时可能解析后更新缓存，或者走通用分派。反优化则是退出不再适用的优化机器码、重建可继续执行的状态。guard 失败可以设计为慢调用，也可以设计为 uncommon trap，取决于编译决策。

面试追问：如何把 inline cache 与 SSA 连起来回答？

IC / profile 提供类型证据，JIT 生成 guard 把快速与慢速路径分开；两条路径返回的值在合并块可由 phi 汇合。进一步内联后，SSA 的定义—使用关系帮助传播常量与删除冗余计算。

参考：JDK 21 CompiledIC：状态与调用点约定。

参考：JDK 21 CompiledIC：状态转换与目标更新。

8. OSR 与反优化：执行到一半怎样切换

方法入口与循环入口不是同一个状态

一个方法只调用一次，却在里面循环很久，仅统计方法调用次数可能漏掉热点。回边热度可触发OSR（On-Stack Replacement）编译：在运行时支持的位置，把正在执行的帧状态转为相应编译入口需要的状态，继续剩余工作，不重新执行方法开头。

long sum = 0;
for (int i = 0; i < n; i++) sum += i;

解释执行到某个受支持的循环入口：
  当前 i = k、sum = 前 k 项累加值、n 已知
  → 把活值交给针对该入口生成的代码
  → 编译代码从当前循环状态继续
不是：i = 0、sum = 0，再跑一遍。

普通编译入口接收方法参数；OSR 入口还依赖当前执行位置和已形成的局部状态。需要对应代码已准备好、线程可完成转换等条件，不能仅凭回边计数达到某个固定值就保证立即切换。JDK 21 HotSpot 与 ART 都有 OSR 相关路径，具体入口、限制和阈值各自定义。

反优化恢复的是语义状态

假设 outer 调用 inner，JIT 把 inner 内联，并消除了其中的 Pair 分配。机器上可能只剩 outer 的一帧和若干寄存器值。若某个优化依赖失效，需要恢复的却可能是 outer、inner 两层逻辑帧，以及仍会被后续代码使用的对象。

  1. 在规定位置确定失效原因与恢复点，避免把普通 IC miss 都当成反优化。
  2. 依据恢复元数据取得各逻辑帧的执行位置、局部值、表达式中间状态和必要的同步状态；来源可为寄存器、栈槽或常量。
  3. 对被消除但后续需要的对象重新物化，恢复字段与别名关系；两个逻辑变量原指向同一对象时不能恢复成两个独立副本。
  4. 构建目标执行状态，再从对应位置继续。哪些操作已完成、哪些还需执行，由恢复点及相应重执行规则确定，不能把已发生的写入或 I/O 随意重放。

因此，反优化不是简单“丢掉机器码再从方法第一行解释”。某方法的代码不再允许新调用进入，与它已没有任何活跃帧、可以回收存储，是不同条件；失效、在栈帧转换和代码回收需要协调。

HotSpot 的 ScopeDesc 等信息描述逻辑作用域、局部值与表达式状态，Deoptimization 负责恢复和物化。ART 有自己的帧与恢复格式。GC 只知道“哪个槽是引用”还不足以完成这一过程；对照几种元数据的职责。

参考：ART JIT 与 OSR · JDK 21 Deoptimization · JDK 21 ScopeDesc。

8.1 ART HEnvironment：恢复信息怎样从图走到运行时

在 Android 14 ART optimizing 编译器里，HEnvironment 是编译期间的状态描述：记录某个 DEX 位置需要的虚拟寄存器值，与对应的 HInstruction 建立关联；发生内联时还可通过 parent 环境描述外层逻辑调用。它使优化器知道哪些值即使不是当前计算的普通输入，也仍可能用于恢复。

示意：某个恢复点需要 DEX 寄存器 v0、v1、v2
编译期环境：v0→参数值，v1→常量 7，v2→某引用值
位置确定后：v0→机器寄存器，v1→常量，v2→栈槽
代码生成：把相应恢复点、位置及内联信息编码进运行时元数据
运行时：按当前 native PC 找信息，重建 DEX 执行状态

CodeGenerator::EmitEnvironment 及 EmitVRegInfo 把环境和位置结果写入 stack map、DEX register map、inline info 等信息。运行时使用随机器码保存的编码数据；不会直接保留编译器里的整个 HGraph / HEnvironment 对象图来执行反优化。

DEX 虚拟寄存器是字节码的逻辑槽，HInstruction 表示 SSA 值，物理寄存器是机器位置；三者不能混称“寄存器”。一个常量无需真实寄存器，也可能仍要能恢复；一个对象引用的位置既可能供 GC 定位，又可能是恢复某个逻辑变量所需的信息，两项职责并不相同。

图优化必须维护环境中的值关系，不能删除仍被恢复状态使用的定义。可恢复点、无效槽的处理、内联帧展开和异常续执行规则仍由实现限定；不能声称任意一条机器指令都能随时无损退回解释器。这里说明 ART 的元数据通路，不把前文 HotSpot 的所有对象物化能力直接套到 ART。

参考：HEnvironment · EmitEnvironment / EmitVRegInfo · 运行时 CodeInfo、StackMap 与 DEX 寄存器位置。

9. 用证据区分预热、编译与反优化

“第一次慢、后面快”可能来自类初始化、文件页与数据缓存、解释执行或 JIT。先分清一次进程启动与稳态吞吐，再将编译事件和业务耗时放到同一时间线上；不能用一次计时证明某个方法已内联或某对象已被标量替换。

观察、候选原因与补充证据
观察要区分的原因证据
多轮运行逐渐变快编译、初始化或缓存逐步就绪新进程与同进程分组，记录类加载 / 编译时间线及实际工作量
输入类型变多后变慢分派成本变化、优化依赖失效，或输入本身更昂贵匹配调用点、类型分布、编译 / 失效事件；不能只看一条 made not entrant
吞吐高但启动更差编译 CPU 与启动关键工作竞争编译线程 / 主线程调度、代码缓存、首轮延迟及稳态收益

HotSpot/JDK 21 可在受控测试中使用 -XX:+PrintCompilation观察编译记录，或用 JFR 关联编译、执行、分配等适用事件；日志中的 OSR 标记、编译级别和失效文字需按该版本格式解读。要证明具体优化还应检查适用的编译日志或生成代码，性能结果本身不是优化过程的证据。

一个类型变化实验可固定每轮输入数量和工作量，先主要调用实现 A，再引入实现 B，对齐记录类型切换和延迟。它是检验假设的设计，不保证特定 JIT 必然去优化；重复新进程试验并区分预热与测量。避免结果未使用导致死代码消除，也不要通过随意加 volatile 改变原问题。

严肃的 JVM 微基准可用 JMH 的独立进程、预热和结果消费机制；Android 启动场景则见编译状态对照。两者测试对象和环境不同，不直接比较一个毫秒数。
