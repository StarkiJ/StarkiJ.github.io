1. 编译阶段与中间表示

从源码到机器码
阶段输入 → 输出主要任务
词法分析字符 → token识别标识符、关键字、字面量等
语法分析token → AST按文法建立结构，报告语法错误
语义分析AST → 带类型/绑定信息的表示名字查找、类型检查、作用域与转换
IR 生成与优化高层结构 → 中间表示显式表达控制流、数据依赖与内存操作
代码生成IR → 目标指令指令选择、寄存器分配、调度与目标约束
汇编与链接汇编/目标文件 → 可执行程序或库编码指令、解析符号与重定位

AST保留源程序语法结构；IR为分析和变换提供规则更统一的表示。同一编译器可以有多层 IR，从接近语言语义逐步降低到机器指令。汇编器主要完成目标指令编码；解释器直接执行某种表示的语义，不必先生成本机代码。

record/结构体需要字段类型、偏移、大小与对齐规则；类继承还涉及基类子对象、访问与动态分派。先确定语言语义，再按 ABI 降低到布局和地址操作，不能仅把每个字段按字节相加。

2. 基本块与控制流图

基本块是一段从入口顺序执行到结尾转移的指令序列；中间没有控制流跳入。CFG以基本块为节点，以可能的控制流转移为边。

  1. 在线性三地址码中，把第一条指令、跳转目标和转移指令后的新指令标为块首。
  2. 相邻块首之间构成基本块；以跳转、条件分支、返回等确定终结。
  3. 按各终结指令建立后继边，构造前驱列表；异常控制流也要按 IR 模型纳入。

条件分支通常有两个后继，返回没有普通后继。不能仅按花括号切块：短路逻辑、循环与异常处理都可能产生额外边。

3. SSA 与 phi

SSA（静态单赋值）要求每个 SSA 值只有一个定义。源变量反复赋值时使用不同版本；控制流合并处用 phi 根据实际前驱选择对应版本。它不是同时执行所有分支，也不是求平均。

define i32 @choose(i1 %cond, i32 %x) {
entry:
  br i1 %cond, label %yes, label %no
yes:
  %a = add i32 %x, 1
  br label %merge
no:
  %b = sub i32 %x, 1
  br label %merge
merge:
  %result = phi i32 [ %a, %yes ], [ %b, %no ]
  ret i32 %result
}

支配：从入口到 B 的每条路径都经过 A，则 A 支配 B。支配边界描述某定义可能与其他路径定义相遇的合并位置。经典 SSA 构建先计算支配关系，在迭代支配边界放置 phi，再沿支配树用版本栈重命名定义与使用；可结合活跃性省掉无用 phi。

经典问题：SSA 是否表示内存永远只写一次？

不是。SSA 约束 IR 值名的定义；store 仍可反复修改内存。对内存的依赖分析需别名分析或 MemorySSA 等额外表示，不能把不同 load 的结果直接视为恒等。

参考：LLVM phi 语义 · LLVM MemorySSA。

循环里的 phi：静态一次定义，动态反复执行

循环头有入口边和回边，phi 合并初始值与上一轮结果。以下函数累加 0..n-1，演示 phi 的控制流语义；调用约定为 n 非负且结果能放入 i32。

define i32 @sum_to(i32 %n) {
entry:
  br label %loop
loop:
  %i = phi i32 [ 0, %entry ], [ %next, %body ]
  %sum = phi i32 [ 0, %entry ], [ %updated, %body ]
  %more = icmp slt i32 %i, %n
  br i1 %more, label %body, label %exit
body:
  %updated = add i32 %sum, %i
  %next = add i32 %i, 1
  br label %loop
exit:
  ret i32 %sum
}

n=3 时，进入循环头的 (i, sum) 依次为 (0,0) → (1,0) → (2,1) → (3,3)，最后返回 3。%i 只有一处静态定义，但该定义可以动态执行多次；“循环变量会变化，所以不能是 SSA”混淆了静态程序与动态执行。

在 LLVM IR 中，phi 必须集中在基本块开头，输入成对标明值与前驱；输入值的使用发生在对应边上。因此 %updated 只需在 body→loop 的边上可用，不需要在 entry→loop 的边上也有定义。同一块的多个 phi 同时选择对应边的输入。

phi、select 与优化收益

phi 按实际进入的前驱选值；select 按显式布尔条件从已可用的操作数中选值。把分支改成 select 时，不能随便把原本只在一个分支执行的可能抛异常、越界或有副作用的计算提升到公共路径。phi 通常在后端转成边上的复制或经寄存器合并消失，不要求 CPU 有名为 phi 的指令。

SSA 使定义—使用关系明确：沿值的唯一来源做常量传播，按使用关系删除死值，检查支配与别名后复用计算。它不会自动解决别名、内存依赖或正确性问题；“SSA 就等于更少寄存器”也不成立，寄存器压力还要看活跃区间。

面试追问：面试要求手工构建 SSA，按什么顺序？

先画 CFG 并标入口、回边与合并块；算支配关系，在需要汇合多个定义的迭代支配边界放 phi；沿支配树重命名定义与使用，给每条前驱边填入对应版本；最后去掉无用或输入相同的 phi。循环头的回边输入不要漏填。

4. phi 消除与寄存器分配

降低 SSA 时，可把 v = phi(a from A, b from B) 变成在边 A→合并块上执行 v←a、边 B→合并块上执行 v←b。若前驱有多个后继而目标有多个前驱，直接把复制放任一块可能在错误路径执行，应按需要拆分临界边。

同一条边上的多项复制具有并行语义。交换 a、b 不能依次执行 a←b、b←a，否则第二步读到已覆盖值；可用临时 t：t←a、a←b、b←t。寄存器合并可以消掉一部分复制。

虚拟寄存器是编译器表示中的值位置，不受硬件寄存器数量直接限制。分配器按活跃区间与干涉关系映射到物理寄存器；位置不足时 spill 到栈并插入 load/store。调用约定、寄存器类别和保存成本也属于约束。

经典问题：把所有 phi 换成合并块开头的普通 move 可以吗？

不可以。合并块必须知道来自哪个前驱才能选择输入；无条件顺序执行所有 move 会取错值。复制必须放到对应路径，并处理并行复制冲突。

5. 优化的前提与代价

常见优化
优化变换必须确认的前提
常量传播 / 折叠用已知值替代计算值确实确定，遵守目标语义与溢出规则
死代码删除删除不影响可观察行为的计算无需要保留的副作用、异常或 volatile 访问
公共子表达式消除复用已有计算结果操作数相同，相关内存未被可能的别名写入改变
循环不变量外提把不随迭代变化的计算移到循环外依赖、异常与执行条件允许移动
内联 / 去虚拟化展开调用或确定调用目标目标可确定，收益超过代码膨胀与编译成本
向量化一次处理多个数据元素依赖、别名、对齐与浮点语义允许

优化后的快慢需结合真实输入与热点衡量。浮点结合律通常不能像实数一样任意重排；C++ UB 也会影响编译器可以采用的推理，不能用“硬件会回绕”代替语言规则。

6. AOT、JIT 与热点统计

AOT在目标程序本次执行前生成机器码；JIT在运行过程中按需编译，可使用运行时类型和热点信息。解释执行、低成本编译、优化编译可组成不同层级，平衡启动、峰值性能与编译资源。C1/C2 是 HotSpot 的特定分层术语，不是所有 JIT 的统一级别。

一种热点设计是在方法元数据中保存饱和调用计数、回边计数和编译状态；达到阈值后入队，避免重复编译。采样或线程本地计数可降低竞争；计数合并、过期、代码缓存容量和反优化也要纳入。无需每次调用都建立字符串键哈希表。

经典问题：调低 JIT 阈值一定让启动更快吗？

不一定。较早生成机器码可减少热点解释成本，也会提前占用 CPU、内存和编译队列，可能与启动关键线程争抢资源。按冷/热启动、编译时间、执行节省和代码缓存占用做对照，不能只比较单个函数执行速度。

ART 的实际编译与 profile 流程见 ART 编译与启动。

参考：HotSpot：分层编译与代码缓存。

7. Inline cache、类型反馈与反优化

Inline cache（内联缓存，IC）是在调用点缓存接收者类型与调用目标的关系。同一个虚调用点往往反复遇到同一类对象；缓存命中时可缩短动态分派路径。这里的 inline 描述缓存贴近调用点，并不等于把被调用函数体展开。

调用点：receiver.work()
首次执行：尚无缓存 → 运行时解析 receiver 的类型与目标
单态路径（概念）：
    按语言要求处理 null
    if receiver.klass == cached_klass:
        call cached_target(receiver)
    else:
        进入 IC miss / 运行时分派路径

缓存键必须足以识别运行时类型，例如可靠的 Klass 身份；同名类可能由不同类加载器定义，不能只比较类名字符串。虚表按类描述方法槽位，IC 则利用某一个调用点的类型规律，两者可以配合。

  • 未链接 / 未初始化：第一次调用尚需解析。
  • 单态（monomorphic）：调用点反复看到一种接收者类型，可使用类型检查加直接目标。
  • 多态内联缓存（PIC）：一般设计中可缓存少量“类型→目标”对，按 guard 逐一检查。
  • 超多态（megamorphic）：类型过多时，维护长检查链得不偿失，可退回通用虚表 / 接口表等分派。

上面是通用设计词汇，不是每个 HotSpot 调用点都必经四级状态。JDK 21 的 CompiledIC 主要表达 clean、monomorphic、megamorphic 等状态；JIT 根据 profile 生成多个类型 guard 的优化代码，与 CompiledIC 自身是否维护 PIC 数组是不同问题。

类型反馈怎样支持内联和反优化

JIT 看到单态热点后，可以生成“类型 guard + A.work 的内联代码 + 失败路径”。原 IC 快速调用仍存在一次调用，内联则消除了调用边界，并给后续常量传播、逃逸分析等提供机会。内联要平衡收益、代码膨胀和指令缓存压力。

当接收者出现新类型时，普通 IC miss 可以进入运行时解析并更新状态，不必每次都反优化。如果机器码依赖了更强假设，例如类层次分析认定某方法只有一个实现，则新类加载可能使依赖失效，触发失效处理或反优化。反优化需要用元数据恢复解释执行所需的局部变量、操作数栈和内联帧状态。

修改目标与缓存类型还必须满足并发发布协议，避免其他线程看到“新类型配旧目标”；代码修补也需遵守目标架构的指令可见性要求。这是运行时实现细节，不能直接用两次普通赋值替代。

面试追问：IC miss、缓存状态变化、反优化是同一件事吗？

不是。miss 表示当前接收者不满足该缓存快速路径；运行时可能解析后更新缓存，或者走通用分派。反优化则是退出不再适用的优化机器码、重建可继续执行的状态。guard 失败可以设计为慢调用，也可以设计为 uncommon trap，取决于编译决策。

面试追问：如何把 inline cache 与 SSA 连起来回答？

IC / profile 提供类型证据，JIT 生成 guard 把快速与慢速路径分开；两条路径返回的值在合并块可由 phi 汇合。进一步内联后，SSA 的定义—使用关系帮助传播常量与删除冗余计算。
