范围与版本

本篇以 AOSP android-14.0.0_r1 为实现参照，沿 DEX 执行、ART 编译、Android 启动和 GC 展开。Java 语言与 JVM 规范的共同语义见JVM 与 HotSpot；编译器图分析的基础见LLVM 与编译原理。

DEX 与 ART 的运行时模型

JVM class 文件的方法使用局部变量槽和操作数栈；DEX 方法使用虚拟寄存器，并以类型、字段、方法等索引组织程序信息。虚拟寄存器是字节码层的位置，编译后仍须映射到机器寄存器或栈槽。两种表示都需要运行时类型信息、方法帧和异常处理状态。对照示例见同一次加法的两种表示。

ART 加载与解析 DEX 中的类型，类身份仍与定义它的加载器有关。Android 常见 BootClassLoader、PathClassLoader、DexClassLoader；JNI 的 FindClass 还受调用上下文影响。Java 的类初始化与同步语义见JVM 章节，ART 的类加载器上下文对编译产物的影响见产物有效性。

参考：DEX 格式 · DEX 指令 · PathClassLoader。

ART optimizing 编译器与恢复元数据

CFG、SSA 和 phi 的共同原理见LLVM IR 示例；这里说明 ART 自己的图和运行时元数据。

ART HGraph：把 CFG 与 SSA 落到编译器对象

HGraph 是 ART optimizing 编译器的图表示，不是 DEX 文件格式，也不是 LLVM IR 的别名。以 AOSP android-14.0.0_r1 为例，它组织一个编译单元的基本块、控制流与分析信息；HBasicBlock 保存前驱、后继以及指令，HInstruction 表达运算及其输入和使用关系，HPhi 表达合流值。图在构建、SSA 转换、优化和目标降低过程中逐步变化。

源方法：int choose(boolean c, int x) {
          int y;
          if (c) y = x + 1; else y = x - 1;
          return y;
        }

示意 HGraph（省略入口、退出及具体节点编号）：
B0：参数 c、x；HIf(c)       → B1 / B2
B1：a = HAdd(x, 1)        → B3
B2：b = HSub(x, 1)        → B3
B3：y = HPhi(a, b)；HReturn(y)

控制流边：B0→B1、B0→B2、B1→B3、B2→B3
数据依赖：HAdd/HSub 使用 x；HPhi 使用各前驱提供的值

这是关系图示，不是某次编译的逐字 dump；实际图还受空检查、异常边、常量节点和优化结果影响。阅读 dump 时先看块间路径，再看每个值的定义和使用，最后检查变换是否保持支配、phi 输入与异常语义；只按节点的显示顺序阅读会漏掉图关系。

可以顺着 HGraphBuilder → SSA 与优化 pass → 位置约束 / 寄存器分配 → CodeGenerator 追踪。需要异常或反优化状态的指令还可带 HEnvironment，它与普通输入边的职责不同，见编译期环境与运行时恢复。AOT / JIT 何时触发这条编译流程，放在ART 编译与启动中讨论。

参考：ART HGraph、HBasicBlock、HInstruction、HPhi · optimizing 编译流程。

Android 14 ART 的分配器工厂具有 linear-scan 与 graph-color 策略；实际选择须追踪编译选项，不能背成“JIT 必用前者、AOT 必用后者”。两种方法的原理和手算见寄存器分配。

参考：ART 寄存器分配策略。

ART HEnvironment：恢复信息怎样从图走到运行时

在 Android 14 ART optimizing 编译器里，HEnvironment 是编译期间的状态描述：记录某个 DEX 位置需要的虚拟寄存器值，与对应的 HInstruction 建立关联；发生内联时还可通过 parent 环境描述外层逻辑调用。它使优化器知道哪些值即使不是当前计算的普通输入，也仍可能用于恢复。

示意：某个恢复点需要 DEX 寄存器 v0、v1、v2
编译期环境：v0→参数值，v1→常量 7，v2→某引用值
位置确定后：v0→机器寄存器，v1→常量，v2→栈槽
代码生成：把相应恢复点、位置及内联信息编码进运行时元数据
运行时：按当前 native PC 找信息，重建 DEX 执行状态

CodeGenerator::EmitEnvironment 及 EmitVRegInfo 把环境和位置结果写入 stack map、DEX register map、inline info 等信息。运行时使用随机器码保存的编码数据；不会直接保留编译器里的整个 HGraph / HEnvironment 对象图来执行反优化。

DEX 虚拟寄存器是字节码的逻辑槽，HInstruction 表示 SSA 值，物理寄存器是机器位置；三者不能混称“寄存器”。一个常量无需真实寄存器，也可能仍要能恢复；一个对象引用的位置既可能供 GC 定位，又可能是恢复某个逻辑变量所需的信息，两项职责并不相同。

图优化必须维护环境中的值关系，不能删除仍被恢复状态使用的定义。可恢复点、无效槽的处理、内联帧展开和异常续执行规则仍由实现限定；不能声称任意一条机器指令都能随时无损退回解释器。这里说明 ART 的元数据通路，不把前文 HotSpot 的所有对象物化能力直接套到 ART。

参考：HEnvironment · EmitEnvironment / EmitVRegInfo · 运行时 CodeInfo、StackMap 与 DEX 寄存器位置。

DEX 与方法执行状态

DEX 保存 Android 运行时使用的字节码及相关信息；ART 负责类加载、执行、对象管理和运行时服务。同一应用的方法可以处于解释、JIT 编译或 AOT 编译状态，不是每次启动都只能选一种执行方式。

解释、JIT、AOT 的公共机制与成本见动态编译；DEX 虚拟寄存器与 JVM 操作数栈见共同执行基础，内存职责见运行时内存全景。这里关注 ART 如何为方法选择可用入口，以及编译状态怎样进入后续启动分析。

构建工具、DEX 与运行时分别做什么

ART optimizing 编译器如何表示方法、处理 SSA 并分配机器位置，见HGraph 实例与寄存器分配手推；这里继续讨论何时编译以及产物如何用于启动。

Java / Kotlin 源码
  → javac / Kotlin JVM 编译器产生 JVM 字节码
  → 按构建配置经 D8 或 R8 的处理路径
      D8：转为 DEX，并处理适用的语言特性降级
      R8：裁剪、优化、混淆并输出 DEX 等产物
  → APK / 分包中的 DEX
  → ART 加载、验证、解析，按可用入口解释 / JIT / AOT 执行

这里画的是职责路径，不是每次构建都顺序跑完 D8、R8 再 dex2oat。R8 属构建时优化，ART JIT 属设备运行时编译；减少 APK 中的代码与缩短某个热点方法的执行时间不是同一个指标。反射、JNI 注册和按名字访问的成员需要正确的保留规则，不能只依据静态直接调用图判断是否可删除。

类身份、初始化与方法分派统一见托管运行时基础；本篇不重新建立一套 Android 专属的语言基础。系统实例以 Android 14 为参照，构建与测量还要记录 AGP、R8、Profile 与 Benchmark 工具版本。

参考：D8 · R8 构建优化。

Profile、dex2oat 与编译产物

热度采集与编译调度

  1. 执行 DEX 或已有代码，采集方法热度、分支/类型等适用的运行时反馈；哪些信息持久化见下文 Profile 分类。
  2. 达到策略条件时安排 JIT 编译；生成代码与必要元数据，放入代码缓存并更新调用入口。
  3. 将可用 profile 信息持久化，供后续基于 profile 的编译决策使用。
  4. 系统在适当时机调用 dex2oat 等编译流程，根据过滤器/profile 选择工作，产生相应的验证、优化和编译产物。

dex2oat 与编译产物

dex2oat是 ART 的编译工具链组成部分，按配置加载和处理 DEX、执行验证/优化并生成相应输出。oat 文件不保证包含每个方法的机器码，也不能用后缀简单断定“全部已经 AOT”。系统版本会改变编译调度与产物细节。

编译代码与 Profile 生命周期

编译代码与 profiling 数据也有生命周期；代码缓存回收与 Java 堆对象的 GC 分属不同管理对象。ART 的字段、阈值、调度与产物细节应对照目标分支。

参考：ART JIT 与 profile 流程 · ART 配置与编译过滤器。

Android 14 常见过滤器中，verify 侧重验证，speed-profile 根据可用 profile 选择编译，speed 更广泛地编译适用代码；不是三个固定耗时或性能等级。dexopt 是设备侧优化工作，dex2oat 是其中使用的编译工具；系统构建侧的 dexpreopt 又是另一种生成时机。

复用产物还要核对输入 DEX、指令集、相关启动映像及类加载器上下文等条件。构建时看到的依赖类与运行时实际加载环境不一致时，不能把已有文件直接当成可用优化结果；具体回退、重新验证或编译行为由版本和调度决定。排查应同时记录编译原因、过滤器、profile 来源和失配日志。

参考：ART 产物与过滤器 · 编译与运行时类加载器上下文 · Baseline / Cloud Profile · Startup Profile 与 DEX 布局。

应用启动中的运行环境与编译状态

启动路径与方法执行

应用进程通常从 Zygote 派生，再完成运行环境配置、绑定应用并执行相应组件生命周期。这里关注应用启动路径上的执行成本：哪些方法需要解释，哪些已有可用编译代码，以及启动期间是否发生 JIT 编译。

Zygote 预加载与写时复制

Zygote预加载可复用的类和资源。fork 后父子私有映射起初可用写时复制共享物理页：读取共享，写入相关页时才形成私有副本。共享的是页级存储效果，父子不是持有同一个可随意共同修改的 Java 堆。

编译状态与启动成本

预加载与写时复制解释了应用进程如何复用已有运行环境；方法采用解释、JIT 还是 AOT，则决定相应代码的执行与编译成本。已有 profile 可指导提前编译；启动期间的 JIT 可能减少后续解释成本，也会占用 CPU。分析时还要分开观察类初始化、Binder 调用与首帧渲染，避免把全部启动耗时归因于编译。

经典问题：fork 是否立刻复制 Zygote 中的全部数据？

通常不会逐字节立即复制全部私有页。页表与进程状态需要建立，原数据页可按写时复制共享；后续写入越多，私有化越多。具体还要看映射类型与启动实现。

参考：AOSP Zygote · Linux fork。

启动优化与验证

JIT 阈值与提前编译的取舍

降低 JIT 阈值可能更早优化热点，也可能抢占启动关键路径资源；提高阈值则可能延长解释执行。profile/AOT 可以把一部分成本移到执行前，但仍有包体、编译和存储代价。

启动指标与对照验证

  • 区分冷启动、温启动、热启动，固定 profile、编译状态、设备温度和后台负载。
  • 记录首帧/完全可用耗时、主线程阻塞、CPU 调度、JIT 编译时段、GC 暂停和内存峰值，不能只报平均总时间。
  • 用 Perfetto 等时间线工具关联事件，再针对一项策略做对照。应用侧可减少主线程工作、延迟非必要初始化并使用适用的 baseline profile。

参考：Android 启动性能。

一次可以复查的启动对照

以下是实验设计，不是本项目的实测性能结论。以同一真机、同一业务入口和同一 release 构建为基础，用 Macrobenchmark 管理编译状态和启动模式，保存每次的 Perfetto trace；可调试构建的成本不能直接当作发布表现。

先比较编译状态，再比较布局
组控制方式回答的问题
A：无预编译基线按工具支持使用 CompilationMode.None，固定重置和启动模式；JIT 仍可能发生缺少提前编译时关键路径的成本
B：要求 Baseline ProfilePartial 并要求有效 Baseline Profile，固定额外预热迭代设置；规则未生效应暴露失败同一代码和入口下，规则覆盖是否带来收益

  1. 固定设备、系统、构建、数据规模、入口与测量工具版本；控制温度、电量策略和后台负载。
  2. 分别报告冷 / 温 / 热启动。冷启动通常需要新进程，但文件页缓存未必冷；JIT 预热与 Android 热启动不是同一分类。
  3. 采集 TTID（首次显示）与适用的 TTFD（完全绘制，需正确报告），同时检查主线程、Binder、类初始化、I/O、JIT 与 GC 时间段。
  4. 重复多次并交错安排对照，比较中位数和尾部波动、失败样本、CPU 与内存；解释 Profile 未命中或变化无收益的情形。

若 B 的 JIT 时间下降却首帧无明显改善，应检查关键路径是否主要在 I/O、锁或渲染。若 D 收益不稳定，要检查真实启动入口覆盖、布局是否生效以及页缓存条件。不要根据一次更快的启动直接降低全局 JIT 阈值。

ART 堆空间与垃圾回收

可达性、屏障和并发移动的共同机制见垃圾回收基础。

ART 的堆空间、分配与引用表示

以下空间名和引用编码来自 AOSP android-14.0.0_r1，用于具体说明托管堆如何组织分配与回收；它们不是所有 GC 的统一空间划分。

Android 14 ART 的空间角色
空间用途与机制
RegionSpace按区域管理对象，支持 TLAB 分配与选定区域的迁移；区域还可表达大对象及其尾部区域
LargeObjectSpace专门管理符合条件的大对象；通常避免搬动大块对象，分配和回收策略不同
NonMovingSpace承担要求或选择不移动的分配；不移动不等于不做可达性判断和回收
Image / Zygote 等空间启动映像、预加载与共享相关，收集中的处理方式依空间属性

在 AOSP android-14.0.0_r1 中，ShouldAllocLargeObject 同时检查大小阈值，以及对象是否为原始类型数组或 String。因此“任意超过 4 KB 的对象都进入 LOS”不成立；阈值也不是所有设备固定常量。降低阈值可能减少其他空间压力，却增加独立大块分配、碎片和映射管理成本。

复制预留空间用于容纳迁移中的活对象。逻辑堆上限、RegionSpace 映射容量、疏散预留和实际物理占用不能互相替代；经典半空间模型的二倍存储直觉不能直接当作所有 ART 配置的固定比例。

为什么区分 RegionSpace 与 LargeObjectSpace

RegionSpace 让分配与回收以区域组织：线程可从区域取得 TLAB，用指针推进完成常见小对象分配；收集器按区域状态和存活情况选择迁移与复用。空闲区域易于整批回收，代价是区域管理、尾部浪费以及复制期间的目标空间需求。这里的 region 是 GC 管理单位，不是操作系统的一页。

对大型数组，复制存活载荷的带宽成本可能很高；LOS 用不同的分配与回收策略，减少反复搬动大块数据的必要。它并非没有成本：仍需追踪存活和释放，可能需要映射管理或连续空闲块，也未必能靠压缩消除碎片。

该版本把原始类型数组和 String 纳入候选，与其主要载荷无需按普通对象引用数组逐项扫描、以及 LOS 的卡表覆盖边界有关。不能由此推导“LOS 对象完全没有对象头引用”，也不能把对象引用数组一律送入 LOS。RegionSpace 本身仍支持大对象区域及尾部区域；对象大、RegionSpace 的大对象表示、进入独立 LOS是三个不同判断。

该版本 HeapReference 内部保存 Atomic<uint32_t>，PtrCompression 负责与实际对象指针转换，并可处理引用 poisoning。它不是普通 native 指针大小，也不是 JNI jobject；扩大可寻址对象范围可能涉及引用编码、空间布局和访问路径，不能只改一个容量数字。

参考：Android 14 分配判断 · HeapReference 与转换 · RegionSpace。

ART ConcurrentCopying 的阶段安排

以 AOSP android-14.0.0_r1 的 ConcurrentCopying 为具体例子，RunPhases 的主线如下。不同配置会选择不同分支，不能把 CC 概括成“全程暂停复制”。

  1. InitializePhase 准备本轮状态；特定分代全堆场景先执行 MarkingPhase，计算存活情况。
  2. 启用相应读屏障入口、处理需要的卡信息，再通过 FlipThreadRoots 协调线程根与空间状态切换。
  3. CopyingPhase 与应用并发推进：复制需迁移的活对象，扫描引用、处理标记工作；读屏障帮助访问获得正确对象。
  4. ReclaimPhase 回收可释放区域，FinishPhase 收尾并更新统计。验证选项可能额外引入暂停。

这里的读屏障承担前文所述的引用访问协作职责；算法定义和 CPU 内存屏障的区别见屏障机制。具体检查、复制和标记条件须对照该版本源码。

Baker 读屏障：从持有者状态取得可用引用

以此版本的 Baker 字段读路径为例，读取 A.child 时检查的是持有字段的 A 的读屏障状态。普通路径直接得到引用；若 A 为灰色，则进入 Mark 慢路径，必要时复制目标、查询转发结果或参与标记，返回当前可用的对象引用。根读取有自己的状态检查，不能把字段读伪代码套到所有根。

字段读的概念流程（省略内存序与并发发布细节）：
  检查 holder 的读屏障状态
  ref = holder.field
  若 holder 为灰色：ref = Mark(ref)
  返回 ref

Mark 内部按空间、标记和转发状态处理，
不是每次读取都复制一次，也不是每次都查全局哈希表。

真实实现用状态读取与引用读取间的排序协议保证正确性，部分路径还会有条件地修复原引用槽。对象搬迁前后的别名要收敛到同一权威副本；复制竞争中的发布与失败副本处理见 ConcurrentCopying::Copy。选用 table-lookup 读屏障时快速检查不同，不能与 Baker 条件混写。

读屏障与卡表写屏障分别负责什么

CC 的读屏障参与保证当前读到的引用符合移动与标记协议；卡表写屏障记录引用图发生修改的源对象范围，供区域或代际扫描使用。例如老对象新增指向年轻对象的字段，仅让读取者取得新地址，并不能替代下一轮局部收集需要的入边记录。两者配合根切换、工作队列与终止协议，才构成完整收集器。

参考：Baker、table-lookup 与根读屏障。

经典问题：并发复制时为什么仍可能暂停？

切换线程根、同步关键状态等步骤需要与应用线程协调。大量复制可并发执行，但这不意味着无暂停；区分 GC 总耗时、暂停时长和应用受到的 CPU/屏障开销。

参考：Android 14 CC 源码 · ART GC 调试文档。

ART CMC：以页面访问协调并发压缩

这里的 CMC（Concurrent Mark Compact）指 AOSP android-14.0.0_r1 的 MarkCompact 实现。先标记活对象并规划压缩后的位置，再在应用运行期间逐页准备可访问的内容。移动空间来自 BumpPointerSpace；不能把 CC 的 RegionSpace 疏散过程直接改名为 CMC，也不能仅凭版本号推断某台设备实际选用它。

从标记到压缩：哪些阶段需要协调

  1. 初始化与并发标记：建立本轮状态，从根追踪对象；通过卡信息等处理并发修改，并预清理待重扫范围。
  2. 标记暂停：补充根与标记工作，撤销线程本地分配缓冲，建立后续新分配对象的处理边界。暂停后应用仍可继续分配，必须把这批 black allocation 纳入协议。
  3. 回收与压缩准备：处理可回收的非移动空间等工作，按存活信息计算移动对象的新位置和页面处理所需元数据。
  4. 压缩切换与线程根协调：更新根，安排旧内容保留和目标地址范围的映射，建立页面访问的拦截与处理条件；这一转换不能任由应用观察半完成状态。
  5. 并发压缩与收尾：后台推进页面整理，按访问需要完成尚未准备的页面，更新其中的对象引用；待工作及故障处理收敛后，撤销临时状态并释放可回收资源。

这是源码阶段的职责概括，实际顺序以 RunPhases、MarkingPause、CompactionPause 和 CompactionPhase 为准。功能不可用时存在 fallback 分支，部分压缩工作转入暂停；“并发压缩”不承诺任何配置下都无暂停。

userfaultfd 在 CMC 中解决什么问题

userfaultfd 让用户态为注册的地址范围接收和处理特定类型的页故障。在常见事件处理模型中，访问线程等待；处理线程通过文件描述符取得故障地址，准备好内容后用 ioctl 让该页可访问，访问线程再继续。它不是每次内存访问都调用的系统调用，也不是简单地“所有写入都触发写保护”。

简化的 CMC 页面场景：
旧内容仍可供收集器读取，根已按压缩计划调整
  应用访问目标页 P，P 尚未准备完成
    → 触发受管理的页故障
    → 收集器从旧内容构造 P，调整 P 中需要更新的引用
    → 按当前模式安装 / 放行完整的 P
    → 应用继续访问
  后台线程也可提前完成其他页面，避免等到访问时才处理

missing 模式可用 UFFDIO_COPY 提供内容，minor 模式可在处理已有页面后用 UFFDIO_CONTINUE 放行；具体支持范围取决于内核和映射类型。该 ART 分支还区分工作线程处理、SIGBUS 协作等路径，不能把上面的教学流程当成唯一实现。页故障基础复用操作系统中的访存流程，这里关注它如何服务对象压缩。

参考：Linux：userfaultfd 的注册、通知与页面完成 · Android 14 MarkCompact：阶段、映射准备与并发压缩。
