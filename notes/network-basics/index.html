1. 分层与通信端点

IP负责跨网络寻址与转发；TCP/UDP在主机间提供传输服务；HTTP规定请求与响应语义。socket 是操作系统暴露的通信端点接口，不是某个单独的网络协议。

先比较 TCP 字节流和 UDP 数据报，再看socket 的收发流程与应用消息边界；HTTP/HTTPS 在这些传输服务之上定义请求、响应和安全通信。

2. TCP 的可靠传输

2.1 序号、确认与重传

TCP提供有序、可靠的双向字节流。发送数据按字节编号，接收方确认已连续接收的范围；发送方保留未确认数据，通过超时或丢包反馈等机制重传。接收方按序号重排并去重。校验和用于发现传输损坏，不提供密码学认证。

2.2 流量控制与拥塞控制

几个容易混淆的机制
机制解决的问题
序号、ACK、重传丢失、重复与乱序
接收窗口 rwnd接收方缓冲容量：流量控制
拥塞窗口 cwnd网络承载能力：拥塞控制
发送限制受 rwnd、cwnd、在途数据和实际缓冲等共同约束

2.3 连接建立、关闭与业务确认

典型三次握手交换 SYN、SYN+ACK、ACK，建立双向序号与连接状态。关闭的两个方向独立完成 FIN/ACK，因此常说“四次挥手”，但报文可以合并，也有同时关闭等情况。TIME_WAIT 用于应对旧报文和关闭阶段的重传，不等于服务端必然进入的状态。

经典问题：TCP 可靠，是否说明对方业务一定处理成功？

不说明。ACK 通常只说明对端 TCP 收到数据，不能证明应用已读取、写库或完成事务。需要应用层响应、请求 ID、幂等或去重；连接断开时“请求未执行”与“执行了但响应丢失”可能无法直接区分。

参考：TCP 规范 RFC 9293 · Linux TCP。

3. UDP 与传输选择

3.1 数据报边界与丢失

UDP保留数据报边界，协议本身不提供重传、排序或连接握手。一份数据报一次接收；缓冲太小可能截断，具体报告方式依接口。大数据报还可能触发 IP 分片，增加丢失风险。

3.2 TCP、UDP 与应用需求

TCP 与 UDP
维度TCPUDP
数据单位字节流数据报
可靠性与顺序协议提供应用按需要实现
延迟来源重传和有序交付可造成等待可丢弃过时数据，但不天然更快
应用责任业务确认、消息分帧、超时还需按需增加丢包/乱序处理与拥塞控制

实时状态更新可偏好较新的数据而丢弃旧数据；文件传输通常需要完整性。QUIC 在 UDP 上实现可靠流与拥塞控制，说明应用使用 UDP 不等于最终传输服务“不可靠”。

参考：UDP 语义。

4. socket 收发与消息边界

4.1 连接端点与收发流程

TCP 连接通常由协议、两端 IP 和端口区分。同一监听端口可以接收许多连接：accept 返回每条连接对应的新描述符，监听描述符继续负责接入。

TCP 服务端：socket → bind → listen → accept → recv/send → close
TCP 客户端：socket → connect → send/recv → close
UDP：socket → 按需要 bind → sendto/recvfrom → close

4.2 阻塞、非阻塞与就绪

阻塞调用可等待数据/缓冲空间；非阻塞调用可能返回 EAGAIN/EWOULDBLOCK，需要结合 poll/epoll 等就绪通知重试。就绪表示某类操作可推进，不等于整个业务消息已到齐。

参考：Linux socket 接口。

4.3 长度协议与接收边界

一次 send 不对应一次 recv。TCP 不保留应用写入的消息边界；读取可能只有一部分，也可能包含多条消息。所谓“粘包/拆包”应通过应用协议处理，而不是假设调整缓冲大小即可消失。

发送协议：[4 字节网络序长度 N][N 字节正文]
接收状态：
  1. 累积到 4 字节头部；读到 EOF 时区分正常结束与半包。
  2. 解码 N，检查 N <= 协议上限，再分配或扩展缓冲。
  3. 累积到 N 字节，交给业务处理。
  4. 缓冲中剩余字节继续作为下一帧解析。
  • send 返回值可能小于请求长度，要循环发送剩余部分；EINTR、非阻塞暂不可写和永久错误分别处理。
  • 流 socket 请求读取非零字节时，recv 返回 0 表示对端有序关闭发送方向；仍需判断是否恰在一条消息的边界。请求长度本身为 0 也可能返回 0；UDP 收到空数据报同样可以返回 0，不能套用这一判断。
  • 长度字段要明确字节序、最大值、空消息、超时和错误策略，避免无限缓存或溢出。

参考：recv 返回值与边界情况。

经典问题：如何验证接收器真的处理了边界？

把同一条编码消息按每种切分位置分段喂给解析器；再一次喂多条、喂半个头、半个正文、零长度和超限长度。正确结果应与网络如何分段无关。

5. HTTP 与 HTTPS

5.1 请求、响应与幂等

HTTP定义方法、目标、状态码、字段和消息体语义。GET 通常用于读取；POST 常用于提交处理。幂等表示重复同一请求的预期效果与一次相同，不表示每次响应内容必须相同。

5.2 TLS 与身份认证

HTTPS在 HTTP 通信中使用 TLS 等安全传输机制。TLS 的握手完成版本/算法协商、密钥建立与通常的服务端身份认证；后续用对称加密与完整性保护传输数据。证书链校验还要匹配目标主机名，不能只检查“有证书”。

5.3 HTTP 版本与传输承载

协议版本与常见承载
版本机制
HTTP/1.1通常运行于 TCP；持久连接复用
HTTP/2通常运行于 TLS/TCP；多路复用流仍受 TCP 丢包的有序交付影响
HTTP/3运行于 QUIC/UDP；不同流的传输不必等待另一流的丢失数据
经典问题：HTTPS 是否只是“把内容用公钥加密”？

不是。现代 TLS 通常通过密钥交换建立会话密钥，用证书与签名认证身份，再使用对称加密保护数据；不是把全部 HTTP 正文直接交给证书公钥加密。

参考：HTTP 语义 RFC 9110 · TLS 1.3 RFC 8446 · HTTP/3 RFC 9114。

6. 串起一次 HTTPS 请求

以访问 https://example.com/items/42 为例，假设需要新建连接，采用 TLS 1.3 与 HTTP/1.1，没有代理，也未命中响应缓存。下面串起各层职责；连接复用、TLS 恢复与 HTTP/3 会改变部分步骤。

6.1 DNS 解析、TCP 连接与 TLS 认证

  1. 确定目标：URL 给出协议、主机与资源路径；未指定端口的 HTTPS 使用 443。域名与 IP 是不同标识，同一个 IP 可以承载多个站点。
  2. 解析域名：客户端先利用可用缓存；需要查询时，请解析器取得 A / AAAA 等记录。递归解析器可能使用缓存，也可能继续向 DNS 服务器查询。DNS 返回地址不等于该地址可连接，更不完成 HTTPS 身份认证。
  3. 建立 TCP 连接：客户端选择地址并连接目标端口，按 TCP 握手建立状态。域名解析成功而连接超时，应区分地址可达性、端口接入和服务负载。
  4. 完成 TLS 握手：协商安全参数并建立密钥，客户端验证证书链及目标主机名。证书验证失败时，不能靠跳过验证把连接当作成功；安全连接建立后，HTTP 数据由 TLS 记录保护。

6.2 请求、响应与连接复用

解密后的 HTTP/1.1 消息示意（行结束实际为 CRLF）：
GET /items/42 HTTP/1.1
Host: example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 9

{"id":42}

请求到达服务端后，HTTP 层解析方法、路径和字段，再调用业务逻辑生成响应。客户端按状态码、字段与消息边界读取完整结果；本例正文是 9 个 ASCII 字节。TLS 记录、TCP 分段和 HTTP 消息边界不同，一次底层读取仍可能只得到部分内容。

已读完响应不要求立即关闭连接：满足持久连接条件时可继续复用，省去重复建连的成本。HTTP/2 用流组织消息；HTTP/3 使用 QUIC，不能照搬这里的 TCP 握手步骤。

6.3 超时发生在哪一层

用阶段缩小问题范围
停在何处能判断什么
DNS 查询失败尚未取得本次连接所需地址，不能据此认定业务服务崩溃。
连接超时或拒绝TCP 接入没有完成；此时还未发送本例的 HTTP 请求。
TLS 认证失败TCP 可达，但安全参数或身份认证未满足要求。
等待响应超时、响应中途断开请求可能已经执行；TCP ACK 也无法证明业务事务完成。

客户端应同时限制各阶段等待与总耗时。重试还要看方法语义和业务约定：有副作用的提交不能因为“没有收到响应”就无条件重复；可通过业务请求标识、去重或查询执行状态处理不确定结果。传输完成、HTTP 成功状态和业务成功也应分别判断。

参考：RFC 1034：DNS 解析与缓存 · RFC 8446：TLS 1.3 · RFC 9110：幂等与重试。
