01. 指针和引用有什么区别？参数应该怎么传？

指针是保存地址的对象；引用是已有对象的别名。指针可以为空，也可以改为指向另一个对象；引用初始化后不能重新绑定，给引用赋值是在修改它所绑定的对象。合法的引用必须指向有效对象，但引用仍可能因对象销毁而悬垂。

传值会初始化一个独立参数；传指针也是传值，复制的是地址，因此能通过该地址修改原对象；传引用直接操作原对象。只读大对象常用 const T&，需要修改用 T&，允许没有对象时可用 T*。小型标量通常直接传值。

常见误区：形参 T* p 中执行 p = other，不会改变调用者的指针变量；需要重新设置调用者的指针，可传 T*&，也可以返回新指针。sizeof(ref) 得到被引用类型的大小，不能用来断言“引用底层一定不占空间”。

02. const 和 constexpr 有什么区别？指针上的 const 怎么读？

const 限制修改，constexpr 强调常量表达式能力。const int n = read_value(); 可以在运行时初始化；constexpr int n = 10; 的初始化必须满足常量表达式要求。constexpr 函数可以用于编译期求值，但也可以接收运行时参数并在运行时执行，并非每次调用都发生在编译期。

  • const int* p：可改 p 的指向，不能通过 p 修改那个 int，这是底层 const。
  • int* const p = &n：p 自身不可改为指向别处，但可以通过 p 修改 n，这是顶层 const。
  • const int* const p = &n：两种限制同时存在。

const 成员函数通过 const 的 this 访问对象，不能修改普通非静态数据成员；mutable 成员可作为例外，例如缓存或用于同步的互斥量。const 成员函数仍可能修改指针成员指向的外部对象，const 不等于递归的深度不可变。

常见误区：const_cast 只改变访问类型；若原对象本来就是 const，去掉 const 后写入它仍是未定义行为。

03. static 在局部变量、全局变量和类成员上分别表示什么？

static 的含义取决于声明位置。局部 static 变量保留到程序结束，名字仍只在局部作用域可见；需要动态初始化时，第一次执行到声明处才初始化。C++11 起这次初始化受到线程安全保证，但之后对该变量的修改不会自动变成线程安全。

命名空间作用域的 static 变量或函数具有内部链接，只在本翻译单元内指向该实体。类的 static 数据成员由该类的对象共享，不为每个对象各存一份；static 成员函数没有 this，不能直接访问某个对象的非静态成员。

例如 int next_id() { static int id = 0; return ++id; } 连续调用会递增，但多个线程同时调用会对 id 产生数据竞争。需要共享计数时应另用原子操作或互斥锁。C++17 的 inline static 数据成员可以直接在类内定义。

04. inline 会强制函数内联吗？和宏有什么区别？

不会。是否把调用展开由编译器决定。inline 更重要的语言作用是：满足 ODR 条件的 inline 函数或变量可以在多个翻译单元中定义，仍表示同一个具有外部链接的实体，因此适合在头文件中提供定义。它不代表“每个文件一份不同实体”。

宏在预处理阶段做文本替换，没有普通函数调用的类型检查和求值语义。例如 #define SQUARE(x) ((x) * (x)) 会把 SQUARE(i++) 展开成两个增量表达式，在这个表达式中导致未定义行为。函数 inline int square(int x) { return x * x; } 则只对实参求值一次。

追问答案：普通小函数即使没有 inline 也可能被优化展开；很大的 inline 函数也可能保持调用。头文件里定义普通非 inline 外部链接函数，可能造成多重定义链接错误。

05. auto、decltype 和 decltype(auto) 怎么推导类型？

普通 auto x = expr 按值推导，通常去掉引用和顶层 const；auto& 保留引用语义。底层 const 不会被随意去掉，例如从 const int* 推导的普通 auto 仍指向 const int。

decltype 对未加括号的变量名或成员访问，取得实体的声明类型；其他表达式按值类别决定：左值得到 T&，将亡值得到 T&&，纯右值得到 T。decltype(auto) 把同一套规则用于初始化表达式或返回表达式，因此括号可能改变结果。

常见误区：返回局部变量时，decltype(auto) 配合 return (local); 可能推导成引用，造成悬垂；不要把“保留类型”直接等同于“更安全”。

06. 默认初始化、值初始化和列表初始化有什么区别？

在 C++17 中，函数内的 int x; 是默认初始化，x 没有得到确定值，不能拿来读取；int x{}; 会得到 0。静态存储期的标量在相应初始化阶段会先被零初始化，所以 static int x; 不是同一种情况。

花括号可防止窄化转换，但不能机械替代所有圆括号。类类型的列表初始化会优先考虑合适的 initializer_list 构造函数。vector<int> a(3, 7) 得到三个 7，而 vector<int> b{3, 7} 得到两个元素 3 和 7。对具有用户提供默认构造函数的类，T{} 也不意味着所有成员必定被清零。

另外，T obj(); 可能声明了一个返回 T 的函数，并没有创建对象；想调用默认构造函数时，可写 T obj{};。这类问题应该先按语法判断，再讨论运行结果。

07. 四种强制转换、explicit 和 nullptr 分别解决什么问题？

  • static_cast：用于明确的常规转换，如 static_cast<double>(n)、向上转型；向下转型时不做运行时动态类型检查，必须由程序保证前提。
  • dynamic_cast：用于多态层次的运行时类型检查；常见的向下/交叉转换需要多态源类型。指针转换失败得到 nullptr，引用转换失败抛出 std::bad_cast。
  • const_cast：调整 const/volatile 限定，不让本来不可修改的对象变得可写。
  • reinterpret_cast：表达低层次的指针等转换；不会创建目标类型对象，也不保证解引用满足对齐、生命周期和类型访问规则。

explicit 限制隐式转换。例如 explicit Count(int n) 允许 Count c(3)，但阻止 Count c = 3。nullptr 具有专门的空指针类型，能避免整数 0 或某些 NULL 宏定义参与重载时的歧义：存在 f(int) 与 f(int*) 时，f(0) 选整数版本，f(nullptr) 选指针版本。

常见误区：C 风格转换把多种操作混在一个语法里，可读性和审查难度更差；转换成功编译也不代表之后的访问合法。

本章核对：初始化 · auto 推导 · decltype · inline。

02 / 内存与生命周期：先分清对象和存储

“这块内存还在”不等于“这个对象还活着”。C++ 中很多崩溃和偶发错误，来自把存储空间、对象生命周期和使用它的指针混为一谈。

08. 栈和堆有什么区别？局部变量都在栈上吗？

栈、堆是理解常见实现的模型；语言层面更准确的概念是存储期。普通局部对象通常具有自动存储期，离开作用域时自动销毁；动态对象通常由 new 创建，由对应的 delete 或资源管理对象负责释放；另外还有静态存储期和线程存储期。

例如 std::vector<int> v(100); 中，局部变量 v 本身是自动存储期对象，它管理的元素通常由默认分配器在动态存储区分配。static int n; 虽然写在函数内，却不是自动存储期对象。优化还可能把普通局部变量放入寄存器或完全消除。

典型实现中，线程栈由运行环境维护，动态分配器需要维护空闲块等信息，因此动态分配可能带来额外成本和碎片。但“栈一定更快”“堆一定无限大”都不是可靠结论。真正要判断的是分配频率、对象大小、存活范围和测量结果。

09. new/delete 和 malloc/free 的区别是什么？

new 表达式通常先取得存储，再在其中初始化对象；delete 表达式负责销毁对象并释放相应存储。malloc 取得原始字节存储，不调用 C++ 类的构造函数；free 不调用类的析构函数。不能用 malloc(sizeof(std::string)) 代替构造一个 string。

普通 throwing new 分配失败通常抛出 std::bad_alloc；malloc 失败返回空指针，new(std::nothrow) 的分配失败也用空指针表示。new 后构造函数若抛异常，通常会调用匹配的释放函数清理刚分配的存储。

配对关系必须正确：new T 配 delete，new T[n] 配 delete[]，malloc 配 free。对空指针调用 delete 或 free 都可以；对同一分配重复释放不可以。数组 cookie 是实现可能采用的记账机制，不能假定固定字节数。

追问答案：operator new 主要负责分配，不等同于完整的 new 表达式。常见的 placement new，例如 new (buffer) T(args)，在给定存储中构造对象，不负责为 buffer 重新分配空间；调用者还要保证对齐、大小和后续清理正确。

10. 什么是悬垂引用？string_view 为什么容易出错？

悬垂表示访问句柄仍存在，但它指向或引用的对象已经不再有效。返回局部对象的引用、对象释放后继续用旧指针、容器重新分配后使用旧迭代器，都属于这类问题。失效时通常不会自动变成 nullptr。

string_view 只是对字符范围的非拥有型视图，不复制字符、不负责释放，也不延长底层字符的生命周期。std::string_view v = std::string("abc"); 在语句结束后就留下悬垂视图；正确做法是让拥有字符的 string 活得足够久，或者直接返回 string。

追问答案：const std::string& r = std::string("abc"); 这种直接绑定可按规则延长临时对象的生命周期，但不能把规则传递给任意后续引用。函数返回局部对象的引用不因调用者再接一个 const 引用而安全；返回值应拥有自己需要的资源。

11. RAII 为什么能避免泄漏？异常安全的三种保证是什么？

RAII 把资源释放放进对象的析构函数，使资源随对象生命周期自动清理。对一个已经完成构造的局部对象，正常返回、提前 return，以及向外层处理器传播异常时的栈展开，都会触发相应析构。这样不必在每个退出分支手工释放内存或解锁。

如果一个对象自身构造失败，它的析构函数不会被调用，但已经完成构造的基类和成员会销毁。因此把资源放进 unique_ptr、vector 等成员，比构造过程中用裸指针临时持有资源更可靠。

  • 基本保证：失败后不泄漏资源，对象仍保持有效的不变量，但值可能改变。
  • 强保证：失败时对可观察状态没有影响，类似“要么成功，要么保持原样”。先在临时对象上完成工作、成功后 swap，是常见思路。
  • 无抛出保证：操作不会通过异常报告失败。资源清理和交换等基础操作常希望提供这一保证。

析构通常不应让异常逃逸。一个 noexcept 函数有异常逃出会调用 std::terminate；异常栈展开时，清理中的析构又抛出第二个异常并向外传播，也会导致终止。RAII 不代表强制终止进程时仍保证执行所有析构。

12. sizeof 为什么不等于成员大小之和？内存对齐有什么作用？

对象布局需要满足成员对齐要求，所以成员间和对象尾部可能插入填充字节。尾部填充让数组中的下一个对象也能正确对齐。例如在 int 按 4 字节对齐的常见平台上，struct A { char c; int n; }; 通常占 8 字节，而不是 5 字节；这个数字依赖平台与 ABI，应通过 sizeof 和 alignof 核对。

调整成员顺序有时能减少填充，但会改变布局，不应在存在序列化格式或二进制接口约束时随意调整。强行压缩布局也可能造成未对齐访问成本，甚至不被目标硬件允许。

sizeof 通常在编译期取得类型或对象的大小，不执行其表达式操作数；sizeof(array) 是整个数组的大小，但函数参数中的 int a[] 被调整为指针，函数里 sizeof(a) 得到的就是指针大小。string/vector 对象的 sizeof 也不包含其动态分配的全部内容。

本章核对：存储期 · 对象生命周期 · new 表达式 · delete 表达式 · RAII 建议。

13. 构造和析构的顺序是什么？初始化列表有什么用？

构造顺序由声明关系决定，不能按初始化列表的书写顺序猜。先由最派生类初始化虚基类，再按基类声明顺序初始化直接非虚基类，然后按类中声明顺序初始化非静态数据成员，最后执行构造函数体。正常销毁时顺序反过来：先执行析构函数体，再逆序销毁成员与基类。

初始化列表是在构造成员；在构造函数体里执行赋值时，成员已经初始化过了。引用、const 标量以及没有可用默认构造函数的成员，需要在进入构造函数体之前得到合适的初始化，常通过初始化列表或类内默认成员初始化器完成。

常见误区：写成 Demo() : second(first), first(1) {} 不会改变声明顺序；如果 second 在类里声明得更早，它可能读到尚未初始化的 first。

14. 深拷贝、浅拷贝和 Rule of Zero / Three / Five 是什么？

浅拷贝复制成员的值，裸指针成员因此只复制地址；深拷贝为资源建立独立副本。若一个类独占一块内存、析构时 delete，却保留默认的裸指针成员拷贝行为，两个对象会认为自己拥有同一资源，可能重复释放。

拷贝构造用于从已有对象建立新对象，如 T b = a;；拷贝赋值用于替换已存在对象的状态，如 b = a;。赋值还要考虑旧资源清理、自赋值和失败后的状态，不能只分配一块新内存就结束。

Rule of Three 提醒：需要自定义析构、拷贝构造、拷贝赋值中的一项时，通常需要一起审视三项。Rule of Five 加上移动构造与移动赋值。它们是设计经验，不表示每个类都应手写五个函数。

Rule of Zero：像上面这样，资源成员已经正确实现值语义，外层类无需再管理特殊成员函数。若资源应独占且不可复制，使用 unique_ptr 并明确禁用拷贝，通常比凭空实现深拷贝更符合语义。用户声明析构等特殊成员会影响隐式移动函数的生成，不能假定“没写移动就一定自动有”。

15. 重载、覆盖和隐藏有什么区别？虚函数如何工作？

重载是在可参与同一次查找的函数集合中，根据不同参数选择函数，普通函数不能只靠返回值区分重载。覆盖是派生类提供与基类虚函数相匹配的实现，需匹配参数以及相关 cv/ref 限定，返回类型还可符合协变规则。写 override 能让编译器检查是否真的覆盖。

隐藏发生在名字查找阶段：派生类声明同名成员后，可能遮住基类的一组重载，即使参数不同。例如基类有 f(int)，派生类新增 f(double)；需要同时保留时可写 using Base::f;。

通过基类指针或引用调用虚函数时，通常根据对象的动态类型调用最终覆盖函数。常见 ABI 用虚表和对象中的虚指针实现分派；标准不规定虚表的固定布局，也不保证每个多态对象只有一个虚指针。编译器能够证明具体类型时，还可能去虚拟化成直接调用。

常见误区：函数实参的静态规则与虚调用并非完全合并成一个步骤。虚函数的默认实参按调用点可见的静态声明决定，因此不宜在覆盖函数上设置不同的默认值。

16. 为什么基类析构常写 virtual？构造函数能是虚函数吗？

在本文 C++17 范围内，如果要通过基类指针 delete 派生对象，基类析构必须是虚函数，否则行为未定义。如果接口不允许这种销毁方式，可设计成 protected 的非虚析构，阻止外部从基类接口删除。不是所有类都必须添加虚析构。

构造函数不能声明为 virtual。构造/析构过程中，对正在构造或析构的对象进行虚调用，分派到当前构造/析构层次的最终覆盖函数，不会借此调用尚未构造或已经析构的更派生部分。

追问答案：纯虚析构函数仍然需要提供定义，因为派生对象析构时会调用基类析构；virtual ~Base() = 0; 不代表基类那一段清理工作可以不存在。

17. 对象切片和菱形继承分别是什么问题？

对象切片发生在把派生对象按值复制到基类对象时。Derived d; Base b = d; 得到的是一个独立的 Base 对象，派生类特有状态没有被保存，b 的动态类型也就是 Base。需要保留多态性时，使用基类引用或合适的智能指针，而不是按值存进 vector<Base>。

菱形继承中，若 B 和 C 都普通继承 A，而 D 同时继承 B、C，则 D 通常含有两份 A 子对象，访问 A 的成员可能歧义。让 B、C 都写 virtual public A，可以使 D 共享同一份虚基类 A，由最派生类负责初始化它。

常见误区：虚继承解决重复基类子对象的问题，虚函数解决动态分派的问题，二者不是一个机制。虚继承可能增加布局和访问成本，具体由 ABI 决定；如果只是想复用一段功能，组合往往更容易表达关系。

本章核对：构造顺序 · 拷贝与移动构造 · 虚函数 · 构造/析构期间的虚调用。

04 / 智能指针：所有权和访问是两回事

智能指针首先表达资源由谁负责，其次才是“自动 delete”。独占、共享和观察这三种关系选对了，释放时机才容易解释。

18. unique_ptr 为什么不能拷贝？get、release、reset 有何区别？

unique_ptr 表达独占所有权。如果允许直接拷贝，同一资源就会出现两个自认为独占的拥有者，所以拷贝被禁用；移动则把所有权交给新指针，原 unique_ptr 变为空。普通代码优先用 make_unique 创建它。

  • get() 只取得借用的裸指针，所有权仍在 unique_ptr；不要据此再造一个独立拥有者。
  • release() 放弃所有权并返回裸指针，不释放对象；接收者必须承担后续释放责任，否则泄漏。
  • reset() 释放当前资源并清空；reset(new_pointer) 则在释放旧资源后接管新指针。

按值接收 unique_ptr<T> 的函数通常表示接管所有权；如果函数只读取或修改对象本身，可用 const T& 或 T& 表达借用。自定义删除器还能把独占管理扩展到文件句柄等资源，但 unique_ptr 的大小未必始终等于一个裸指针。

19. shared_ptr 如何计数？为什么常用 make_shared？

同一所有权组中的 shared_ptr 共享控制信息，最后一个强拥有者离开时释放被管理资源。典型控制块记录强引用、弱引用相关状态和删除器等。复制 shared_ptr 增加强拥有者数量，移动通常只转交所有权；use_count() 表示当前共享拥有者数量，不是历史复制次数。

make_shared<T>(...) 通常把控制块和 T 放在一次分配中，减少分配次数并改善局部性。这是常见实现策略。对象仍在强计数归零时析构；如果还有 weak_ptr，共享控制信息要继续存在，合并分配的整块存储也可能延后到弱引用全部消失才释放。

常见误区：不要从同一个裸指针分别构造两个独立 shared_ptr，它们不会自动发现彼此，会建立两个控制块并可能重复释放。类需要得到与既有拥有者共享控制块的自身指针时，可使用 enable_shared_from_this；必须已经建立合适的共享所有权。在通常的对象构造过程中，内部弱引用尚未接上拥有者，此时调用 shared_from_this() 在 C++17 中会抛出 std::bad_weak_ptr。

20. 循环引用为什么泄漏？weak_ptr 怎么解决？

若 A 用 shared_ptr 拥有 B，B 又用 shared_ptr 拥有 A，外部指针全部消失后，环内每个强计数仍不为零，析构不会触发。引用计数不能自动回收这种强所有权环。

weak_ptr 观察同一所有权组，但不增加强计数。真正使用时调用 lock()：对象仍可拥有则取得一个 shared_ptr，否则得到空 shared_ptr。这一步把“判断还活着”和“取得临时所有权”结合起来，比先判断 expired 再假定对象仍在更合适。

应该根据业务关系决定哪条边只观察，而不是随便把任意一个 shared_ptr 换成 weak_ptr。若两个方向都不拥有资源，还必须有外部拥有者维持对象生存。

21. shared_ptr 是线程安全的吗？

必须分三层回答。第一层，不同 shared_ptr 实例共享同一个控制块时，库支持它们各自进行复制、销毁等所有权操作；第二层，同一个 shared_ptr 变量若被多个线程同时读写，不能只凭引用计数安全就忽略同步；第三层，被指向的 T 的读写依然由 T 自己的同步规则决定。

例如两个线程各持有一个指向同一普通 int 的 shared_ptr，各自执行 ++*p，仍会对那个 int 产生数据竞争。需要对 int 加锁或让它成为合适的原子对象。

需要原子地替换同一共享指针时，C++17 可使用标准库为 shared_ptr 提供的原子自由函数，或用互斥锁；C++20 提供 std::atomic<std::shared_ptr<T>>。use_count() == 1 也不能充当多线程独占访问的可靠同步条件。

本章核对：unique_ptr · shared_ptr · weak_ptr。

22. 左值、右值和 std::move 到底是什么？

C++ 的表达式分为左值（lvalue）、纯右值（prvalue）和将亡值（xvalue）。左值与将亡值合称 glvalue，强调对象身份；纯右值与将亡值合称右值。变量名表达式通常是左值，42 是纯右值，std::move(obj) 通常得到将亡值。

std::move 本身不搬运资源，主要把表达式转换成可参与右值重载选择的形式。资源怎样转移，由之后选中的移动构造或移动赋值来实现。如果只是单独调用 move 而不消费结果，不会神奇地清空对象。

上例的 inspect 并没有移动或修改字符串，所以 text 的内容仍是 C++。绑定到右值引用、调用 std::move、真正执行移动操作，是三个不同的步骤。

23. 为什么 move const 对象会拷贝？移动后还能使用吗？

常规移动构造参数是 T&&，因为转移资源通常要修改源对象。对 const T 使用 move 得到的是 const T&&，不能绑定到非 const 的 T&&，却可绑定到 const T&，因此可能选中拷贝构造。

标准库类型移动后通常处于“有效但未指定”的状态，除非类型另有明确保证。可以析构，可以进行不违反其前提条件的操作；要调用 front()，应先确认不为空。unique_ptr 移动后的源指针为空是明确保证，但不能推广成“所有移动后的 string/vector 都保证为空”。自定义类型应给出自己的移动后状态约定。

24. 什么是完美转发？T&& 为什么有时能接左值？

完美转发让包装层尽量保留调用者实参的值类别与 cv 限定。函数模板中，参与类型推导且形如无 cv 限定模板参数 T&& 的参数可形成转发引用：传左值 X 时 T 推导为 X&，传右值 X 时 T 推导为 X。

引用折叠规则是：只要组合里有左值引用，折叠结果就是左值引用；只有右值引用与右值引用组合才仍为右值引用。参数在函数体里有名字，因此直接使用它是左值；std::forward<T>(x) 根据 T 恢复应传递的值类别。

常见误区：const T&& 不是这种转发引用；类模板中已经固定的 T 对应的普通成员参数 T&&，也不会仅凭两个 & 自动获得转发能力。包装函数里一律用 move，会把调用者的左值也强行转为可消费的右值。

25. RVO、NRVO、noexcept 与 vector 扩容有什么关系？

拷贝消除是直接在目标位置构造；移动仍然是在构造另一个对象。C++17 中，像 T make() { return T{}; } 这样的同类型纯右值返回，可直接构造结果对象，不需要可用的拷贝或移动构造。返回命名局部对象 return local; 的 NRVO 则仍是允许但不强制的优化；未消除时可按规则尝试移动。

给返回局部变量随手加 std::move，可能破坏 NRVO 的适用条件，所以通常直接写 return local; 即可。需要先解释代码适用的语言规则，再讨论当前编译器做了哪项优化。

vector 重新分配时要把旧元素搬到新存储。若移动可能抛异常，搬到一半时旧元素可能已被修改，难以保持强异常保证；类型可拷贝时，实现常选择拷贝。如果移动保证不抛异常，就更适合直接移动。std::move_if_noexcept 表达了类似选择。

边界：只有可抛出的移动、没有可用拷贝时，vector 仍可能需要移动，特定异常保证也会减弱。noexcept 必须反映实际能力，不应为了“让 vector 更快”虚假承诺；异常一旦逃出 noexcept 函数，程序会终止。

本章核对：move 与 forward · 拷贝消除 · vector 扩容相关保证。

26. vector、deque、list 和适配器怎么选？

常用序列容器与适配器
类型关键能力主要代价或适用条件
vector连续存储，随机访问 O(1)，尾部插入摊还 O(1)。中间插入/删除通常 O(n)，重新分配会迁移元素。适合作为默认序列容器考虑。
deque随机访问 O(1)，首尾单元素插入/删除 O(1)。整体不保证连续，常见实现是分段存储；迭代器失效规则需要单独查。
list双向链表，已知迭代器位置的单元素插入/删除 O(1)。随机访问不支持，查找位置 O(n)，节点有指针和分配开销，缓存局部性通常较差。
stack / queue限制为后进先出 / 先进先出接口，默认底层通常是 deque。属于容器适配器；不提供任意位置遍历和修改的通用接口。
priority_queue默认最大元素在顶部，top O(1)，push/pop O(log n)。通常用堆维护优先级，不保证全部元素已经排序；比较器可调整优先方向。

为什么 list 的 O(1) 插入不一定更快？O(1) 的前提是已经知道位置。实际还可能需要遍历、分配节点和访问分散内存。vector 虽然会移动元素，但连续内存常能更好利用缓存；最终要结合元素类型、数量和操作分布测量。

比如 LRU 缓存可用 list 保持最近使用顺序，再用 unordered_map 把键映射到链表迭代器，避开每次在线性链表中查找。这样利用的是两种结构的配合，不是“链表天然适合所有插入删除”。

27. vector 的 size、capacity、reserve 和 resize 有何区别？

size 是已经存在的元素数；capacity 是当前存储最多容纳的元素数。reserve(n) 只请求至少 n 的容量，不创建额外元素；resize(n) 改变实际元素数，变大时构造新元素，变小时销毁尾部元素。对于默认分配器下的 vector<int>，resize 新增的 int 值为 0。

当插入超出当前容量，vector 会申请新存储、构造迁移后的元素并释放旧存储。常见实现采用几何增长以达到尾部插入的摊还常数复杂度，但标准不规定必须按 1.5 倍或 2 倍增长。每次 push 前都 reserve(size() + 1) 可能破坏增长策略，导致大量重新分配。

追问答案：resize 缩小 size 不等于缩小 capacity，clear() 也不要求归还容量；shrink_to_fit() 是非强制的缩容请求。不能用“容量足够”判断下标访问是否合法，应使用 size。

28. 哪些操作会让迭代器、引用或指针失效？

失效规则按“容器 + 操作 + 是否重新分配”判断。迭代器和引用并不总是一起失效，例如哈希容器 rehash 会改变迭代结构，但已有元素对象仍可保持原位。

最常用的失效规则
容器与操作迭代器元素引用 / 指针
vector 重新分配全部失效，包括旧 end()。全部失效。
vector 插入，未重新分配插入位置及之后失效；尾部插入使旧 end() 失效。插入位置及之后失效；尾部插入不影响已有元素引用。
vector erase被删位置及之后失效，包括旧 end()。被删位置及之后失效。
list / map / set 插入通常不影响已有元素迭代器。已有元素引用保持有效。
list / map / set 删除被删除元素的迭代器失效。被删除元素的引用失效。
unordered_map rehash全部迭代器失效。已有元素的引用 / 指针仍有效。
unordered_map erase仅被删除元素的迭代器失效。仅被删除元素的引用 / 指针失效。

例如先保存 int& r = v[0];，再通过 v.reserve(v.capacity() + 1) 触发重新分配，之后再读写 r 就不合法。需要跨变更定位元素时，可在语义允许的情况下保存索引并在操作后重新取元素；插入和删除同样可能改变索引对应的对象。

常见误区：reserve 只能减少某些重新分配，不能让所有迭代器永远有效。deque 的规则与 vector 不同，例如两端插入通常会使迭代器失效，但已有元素引用保持有效，不要直接套用 vector 的结论。

29. map 和 unordered_map 有什么区别？为什么不用哈希表替代一切？

map 按比较器有序，查找、普通插入等典型操作提供对数复杂度；unordered_map 不保证有序，查找平均 O(1)、最坏 O(n)。map 常见实现是红黑树，但标准规定的是接口、行为和复杂度，不强制某种具体树型。

map 适合有序遍历、上下界查找和范围查询；unordered_map 依赖哈希分布，可能需要额外桶空间，rehash 也有成本。哈希冲突多时，平均常数性能会恶化；要根据数据分布、内存与排序需求选择，而不是只比较 O(1) 与 O(log n)。

map 的键等价由比较器决定：!comp(a,b) && !comp(b,a)，不一定调用 operator==。unordered_map 使用哈希与相等谓词，若两个键被判为相等，它们的哈希值必须一致。

追问答案：m[key] 在键不存在时会插入并初始化对应值，读操作不应随意使用它。只查询可用 find；需要存在且不想插入可用 at，找不到会抛 std::out_of_range。C++20 增加了 contains 便于仅检查存在性。

30. remove 为什么不删除元素？排序比较器为什么不能写 <=？

std::remove 和 remove_if 操作的是迭代器范围，不负责改变容器大小。它们把保留元素移到范围前部，返回新的逻辑结尾；容器仍然拥有原先那么多个元素，需要再调用 erase 删除尾部。

遍历并删除时，vector 常用 it = v.erase(it) 接回新迭代器，不能先让 it 失效再继续 ++。C++20 可用 std::erase_if 简化适用容器的删除操作。

排序比较器必须满足严格弱序。最直观的条件是 comp(x,x) 必须为 false，还要满足相应传递性；把“小于”写成“小于等于”破坏这一前提，算法行为不再受正常保证。lower_bound 也有范围已按对应关系分区的前提；按同一比较器排好序是常见的充分条件，不能对任意无序区间直接做二分查找。

31. emplace_back 一定比 push_back 快吗？

不一定。区别在于元素怎么构造。push_back 接收已有的 T，随后拷贝或移动到容器；emplace_back 把参数转发给 T 的构造函数，直接在新元素的位置构造。传入构造参数时可能省掉一个临时 T，但若已经有一个 T，emplace_back 仍可能进行拷贝或移动。

emplace 也无法消除容器扩容时旧元素的迁移，而且转发构造参数可能选中意料外的构造函数。不要把“原位构造”理解为“没有任何分配、移动或异常”。如果持有的是独占资源，先用 make_unique 等建立所有权，再交给容器，别用裸指针转移中的异常窗口赌资源能被回收。

本章核对：容器要求 · vector 容量 · vector 修改与失效 · 无序关联容器 · 排序要求。

32. 模板定义为什么通常写在头文件？函数模板能偏特化吗？

隐式实例化通常需要在实例化点看见模板定义。如果头文件只声明 template<class T> T twice(T);，实现藏在普通 cpp 中，而别的 cpp 调用 twice(3)，那个调用方通常无法为 int 生成实现，最终可能出现链接缺失。

因此常把定义放头文件，或放进由头文件包含的 tpp 文件。并不是绝对不能分离：如果支持的类型集合已知，可在实现文件中显式实例化，例如 template int twice<int>(int);，为指定类型生成实现；代价是没有自动支持任意新类型。

类模板可以全特化和偏特化；函数模板可以全特化，但不能偏特化。函数需要区分部分类型情况时，通常用重载或约束。模板不是运行时的通用解释器，不同实例可能生成不同代码，带来编译时间和代码体积成本。

33. SFINAE、enable_if 和 concepts 是什么关系？

SFINAE 表示模板替换在规定的直接上下文中失败时，该候选被排除，而不是立即让整个程序报错。其余候选仍可继续参与重载选择。如果失败发生在已经选中函数的函数体内部，或属于其他不满足适用条件的错误，就不会自动被忽略。

enable_if 是利用这一规则的工具：条件为 true 时提供 type，false 时没有这个类型别名，从而让某个候选在替换阶段不可用。

C++20 的 concepts/requires 可以更直接地表达“类型必须满足什么条件”，例如 template<std::integral T> T twice(T value)。它通常比把约束藏在返回类型或默认模板参数里更容易阅读，也参与约束相关的重载选择；但仍需理解约束本身，不是所有模板错误都会被自动修好。

34. Lambda 捕获的是什么？mutable 会修改原变量吗？

Lambda 产生一个闭包对象，捕获列表决定闭包如何保存所需状态。值捕获把所需值保存在闭包中；引用捕获借用外部对象，不延长对象生命周期。普通值捕获的闭包调用运算符默认是 const；mutable 允许修改闭包内的副本，不会自动改原变量。

C++14 的初始化捕获可以移动资源进闭包，例如 [p = std::move(owner)] { return *p; }。若捕获的是 unique_ptr，闭包通常也不可拷贝，不能直接当作要求可拷贝目标的 C++17 std::function 使用。

常见误区：异步回调中的引用捕获可能悬垂；[this] 保存的是访问当前对象的指针，不拥有对象。即使写 [=]，在 C++17 中隐式捕获 this 也不会复制整个对象；C++17 的 [*this] 才是按值捕获对象的写法，还需考虑对象是否适合复制。

35. if constexpr、optional 和 variant 有什么实际用途？

if constexpr 用编译期条件选择分支。在模板实例化中，已能确定条件后，被丢弃的分支不会按普通分支那样实例化，因此不同类型可以使用不同合法操作。它不等于预处理器删除任意语法；在非模板环境中，不能用 false 分支藏随意的非法代码。

optional<T> 表示“有一个 T 或没有值”，适合查找结果、可缺省配置；访问前要检查是否有值，value() 在无值时抛异常。variant<A,B> 通常在若干候选类型中保存其中一种，可用 get_if 检查或 visit 按当前类型分派；它不同于可以同时保存多个字段的结构体，也不是任意类型容器。某些替换当前值的操作若抛异常，variant 还可能进入 valueless_by_exception 状态，这也需要纳入异常处理。

C++20 的 span 是连续对象范围的非拥有型视图；ranges 把范围与算法结合，部分 views 是延迟计算的视图，仍需注意底层对象生命周期。C++23 的 expected 更适合同时表达成功值或具体错误。协程支持挂起与恢复执行，本身不会自动创建线程，也不意味着异步 I/O 已经实现。

本章核对：模板替换与推导 · Lambda · if constexpr · optional · variant。

08 / 并发：线程生命周期、互斥与可见性

写并发代码时先回答：谁拥有共享状态，谁会修改它，哪些操作必须一起完成，线程何时退出。单独知道某个 API 并不能保证整个协议正确。

  2. 37. lock_guard、unique_lock 和 scoped_lock 怎么选？如何避免死锁？
  3. 38. 条件变量为什么要带谓词？通知会被“存起来”吗？
  4. 39. atomic、volatile 和内存序有什么区别？

36. thread 的 join 和 detach 有什么区别？析构会自动等待吗？

std::thread 析构不会自动 join。如果析构时仍为 joinable，会调用 std::terminate。joinable 表示线程对象仍关联着一个需要 join 或 detach 的线程，即使线程函数已经执行完，也可能仍是 joinable。

join() 等待线程完成并收回关联，完成操作与 join 返回之间建立同步；detach() 解除线程对象的管理关系，不会终止线程。分离的线程若访问已经销毁的局部引用、this 或其他资源，仍会出错，因此需要独立保证资源生命周期。

线程函数抛出的异常不能直接被创建线程的外层 try/catch 接住；未在线程内处理的异常会导致终止，可用 exception_ptr 或 promise/future 传递异常与结果。std::async 默认策略可能选择延迟执行，不能不加区分地认为它必定创建线程。

C++20 的 jthread 提供作用域结束时请求停止并 join 的行为，但停止是协作式的：工作代码仍需响应停止请求。

37. lock_guard、unique_lock 和 scoped_lock 怎么选？如何避免死锁？

它们都可以让锁按 RAII 释放，但控制能力不同。lock_guard 适合简单地从构造持锁到析构；unique_lock 支持延迟加锁、显式 unlock/lock、移动所有权，条件变量等待通常需要它；C++17 的 scoped_lock 可同时管理多个互斥量，并使用避免相互锁定死锁的加锁方式。

典型死锁是线程一拿着 A 等 B，线程二拿着 B 等 A。对多把锁采用一致的全局顺序，或者对需要同时获得的锁用 std::scoped_lock lock(a, b);，可以避免这类循环等待。不要把同一把非递归互斥锁重复作为两个参数传入。

同时要缩短临界区，避免持锁执行不可控回调或等待其他线程。即使一次多锁操作不会互相死锁，也不能证明整个程序没有其他等待环。recursive_mutex 只允许同一线程递归获取同一把锁，并不是通用的死锁解决方案。

常见误区：把每个变量分别保护好，还不一定保护了跨变量的不变量。例如转账必须让余额扣减与增加在同一协议下完成，否则中间状态仍可能被其他线程观察。

38. 条件变量为什么要带谓词？通知会被“存起来”吗？

条件变量用于等待共享状态发生变化，通知本身不是可累积的消息。线程应在锁保护下检查谓词；不满足时，wait 原子地释放锁并进入等待，醒来后重新获得锁再检查。唤醒可能是虚假的，也可能在拿回锁之前状态已被别的线程改变，所以必须循环检查条件。

cv.wait(lock, predicate) 表达了这套循环。即使通知先于等待发生，只要谓词已经在同一同步协议下变为 true，后来者也会直接继续；正确性依赖状态，不依赖“恰好接到一次通知”。

所有 queue 和 closed 的访问都受同一把互斥锁保护；输出放在解锁之后，避免拖长临界区。这里展示无界队列的最小协作协议；有界队列还要让生产者等待“未满或已关闭”，关闭时唤醒两端，并明确是否允许继续放入数据。并发对象销毁前必须先确保等待线程已经退出。

39. atomic、volatile 和内存序有什么区别？

volatile 不提供线程间的原子性或同步关系。它面向某些必须保留的可观察访问场景；对普通共享整数使用 volatile 后，多线程的 ++i 仍不能当作安全计数。atomic 则提供原子访问与可选择的内存序，但多步操作组成的业务事务不一定整体原子。

对 std::atomic<int> count，count++ 或 fetch_add 是原子读改写；count = count + 1 却包含分开的读取和写入，可能丢失并发更新。只需要统计且不借计数发布其他数据时，relaxed 的 fetch_add 常已足够。

  • relaxed：保证该原子对象的原子操作与相应修改顺序，不用它为其他普通内存建立发布关系。
  • release / acquire：acquire 读取到相应 release 发布的值或符合规则的释放序列时，可建立同步，让发布前的普通写入对读取后续访问可见。
  • seq_cst：默认的顺序一致操作提供更强的顺序约束，包含这些操作之间的单一总序；也不代表任意未同步普通访问都自动安全。

这个一次发布协议中，payload 只在发布前写一次，读取发生在成功的 acquire 之后，因此有相应 happens-before 链。把这两处都改为 relaxed，就不能靠该标志为 payload 建立所需同步。实际长时间等待通常更适合条件变量，示例自旋只是为了突出发布关系。

追问答案：atomic 不保证所有类型、所有平台都无锁，可查询 is_lock_free()；单次 CAS 无锁也不意味着整个算法正确，还要处理重试、ABA 和对象内存回收等问题。

09 / 编译与调试：从报错定位到性能判断

语言规则需要落到证据上。先区分错误发生在编译、链接还是运行阶段，再根据最小复现、调用栈和测量结果缩小范围。

  1. 40. 编译与链接分别做什么？undefined reference 和多重定义怎么查？
  2. 41. Debug 能跑、Release 崩溃，应该怎样定位？
  3. 42. 如何证明某个 C++ 优化真的更快？

40. 编译与链接分别做什么？undefined reference 和多重定义怎么查？

常见构建流程是预处理、编译、汇编、链接。预处理处理 include 和宏等；编译检查语法与类型并生成后续代码；汇编产生目标文件；链接把目标文件与库连接起来，解析跨文件的符号引用。实际工具可能把部分阶段合并执行。

声明告诉编译器名字和类型，例如头文件中的 extern int count;；定义建立实体，例如某一个 cpp 中的 int count = 0;。函数同理，int add(int, int); 不是函数体的定义。

undefined reference / unresolved external symbol：调用点通过了编译，但链接时找不到所需定义。检查实现文件是否参与构建、库是否链接、声明与定义的参数/命名空间是否一致、模板是否实例化，以及构建工具相关的链接顺序。

multiple definition：同一不允许重复定义的实体出现多份定义。常见原因是在头文件直接定义普通外部链接变量或函数，再被多个 cpp 包含。头文件防重只能防止同一翻译单元重复包含，不能替代跨翻译单元的 ODR 规则；应把普通定义放在一个 cpp，或在适合的场景使用 inline。

静态库通常在链接时提供所需目标代码，动态库在加载或运行时通过动态链接机制使用。两者都要考虑 ABI、版本和依赖，不能简单概括为“动态库一定更省内存或更快”。

41. Debug 能跑、Release 崩溃，应该怎样定位？

先怀疑隐藏的未定义行为、时序问题或构建差异，不应直接断言编译器优化有 bug。未初始化读取、越界、释放后使用、悬垂引用、数据竞争，都可能在一种构建里暂时没暴露，在另一种布局或优化下出现故障。

例如 int& r = v[0]; v.reserve(v.capacity() + 1); r = 9; 在 v 非空且 reserve 成功重新分配后，最后一条语句使用了失效引用。这段错误代码没有固定的合法输出；修复应该在变更后重新获取元素引用，或重新设计持有关系，而不是“加一行打印让它不崩”。

  1. 固定输入和运行步骤，记录编译器、标准版本、优化与依赖配置。
  2. 用调试器看首次故障的调用栈、相关对象和资源生命周期，缩减到最小复现。
  3. 在支持的平台用 AddressSanitizer 查越界/释放后使用，用 UndefinedBehaviorSanitizer 查部分语言层错误，用 ThreadSanitizer 查数据竞争。
  4. 修复根因后，用原始复现和必要边界场景验证，再回到完整项目检查。

例如支持 AddressSanitizer 的 Clang 环境可用 clang++ -std=c++17 -g -O1 -fsanitize=address -fno-omit-frame-pointer demo.cpp -o demo 构建最小复现。检测器发现问题是证据，但一次没报告不证明所有执行路径都安全；不同检测器与平台的支持和组合限制应查各自文档。

42. 如何证明某个 C++ 优化真的更快？

先定义要改善的指标，再测量真实瓶颈。吞吐量、平均延迟、尾延迟、内存峰值和启动时间不一定同向变化。单看某一行汇编或一次循环耗时，不能证明整个程序受益。

比较两种容器或写法时，应固定输入规模与分布、编译器与优化配置，区分初始化成本和稳态操作成本，重复测量并观察波动。用 profiler 确认时间究竟花在分配、拷贝、锁竞争、I/O 还是别处，避免优化一个几乎不占时间的环节。

微基准还要防止工作被编译器消除：如果计算结果不可观察，整个循环可能被优化掉。应采用可靠的基准工具或明确的结果消费方式；不能简单给所有数据加 volatile，因为它会改变访问约束，测出的可能是另一种程序。

例子：vector 预留容量可能减少扩容与元素迁移，但也会改变内存占用；把 list 替换为 vector 可能因局部性变快，也可能增加特定位置修改的成本。回答“更快”时，要一起给出数据规模、操作比例、测量指标、收益和代价，而不是只背复杂度。
