1. 先确定问题类型

现象、机制与证据
类型常见原因重点证据
泄漏丢失释放责任、强引用环未释放分配的调用栈与拥有关系
长期持有无界缓存、队列、回调捕获对象仍可达；数量随业务次数持续增长
占用未回落vector 容量、分配器缓存、碎片活对象已减少，但保留存储或驻留页仍较多
非法访问越界、释放后使用、重复释放首次非法访问及分配/释放调用栈
并发问题释放与访问竞争、缺少同步访问发生在哪些线程，保护协议是否一致

RSS 是驻留物理内存统计，PSS 对共享页按共享比例分摊；虚拟地址空间大小不等于物理占用。统计同一进程时还要区分托管堆、native 堆、映射、线程栈与图形资源。

经典问题：智能指针能解决所有内存增长吗？

不能。它能表达并执行所有权规则，但强引用环、缓存无上限、任务积压和过长的生命周期仍需业务策略。正确释放后，分配器也不一定立即把页归还内核。

参考：Linux /proc 内存统计。

2. 定位流程与检测工具

  1. 固定版本、输入、操作次数与线程条件，保存带符号构建；先拿到稳定复现。
  2. 根据问题类别选择证据：非法访问看检测器与崩溃栈；增长问题比较多轮操作前后的分配与存活对象。
  3. 找到首次错误及拥有关系，区分根因和之后的连锁崩溃。
  4. 修改释放责任、容器访问或同步协议，用原复现、边界和重复运行验证。
工具覆盖范围
工具适合检查限制
ASan堆/栈越界、use-after-free 等依赖插桩和实际执行路径；不能证明无 UB
LSan部分未释放分配仍可达的无界缓存可能不报告
UBSan对齐、有符号溢出等部分 UB检查项和平台支持不同
TSan数据竞争单独构建运行，通常不能与 ASan 合用
采样 / heap profiler分配热点、存活量与增长趋势采样有误差；观察窗口和开销需说明

参考：ASan · LSan · TSan。

3. 扩容后的释放后使用

错误程序填满容量后保存引用，再插入一个元素，保证这次成功插入触发重分配。此程序故意包含 UB，没有规定输出；应在支持 ASan 的环境中单独实验。

下载源码（invalid-reference.cpp）。使用 C++17 和支持的检测器编译运行。

错误复现：仅用于检测器实验 
#include <vector>
#include <iostream>
int main() {
    std::vector<int> v{7};
    const auto capacity=v.capacity();
    while(v.size()<capacity) v.push_back(0);
    const int& ref=v[0];
    v.push_back(9);
    std::cout << ref << '\n'; // 故意的 UB：只用于检测器实验
}
clang++ -std=c++17 -O1 -g -fsanitize=address,undefined \
  -fno-omit-frame-pointer invalid-reference.cpp -o invalid-reference
./invalid-reference

以上为 Linux/Clang 示例命令，不是本地 Windows 的实测报告。典型报告应关注三组栈：非法读取处、vector 扩容释放处、原缓冲分配处。真正的修复是恢复有效访问关系；给引用“重新赋值”只会访问它已经绑定的目标，不能重新绑定。

4. 非虚析构与工程防线

Base* p = new Derived; delete p; 若基类析构非虚，在这里的 C++17 场景中属于 UB，不是保证只调用 Base 析构。允许通过 Base 销毁时，把析构声明为 public virtual；修复后执行 Derived 析构，再执行 Base 析构。若禁止这种销毁，可设计 protected 非虚析构。

unique_ptr<Base> 的默认删除器仍执行 delete Base*，所以仅换智能指针并不能修复非虚析构。以下示例同时验证动态析构和扩容后重新访问。

下载源码（examples.cpp）。使用 C++17 编译；断言测试请勿定义 NDEBUG。

完整实现与断言测试 
#include <cassert>
#include <cstddef>
#include <memory>
#include <vector>
class Base {
public:
    virtual ~Base() = default;
};
class Derived final : public Base {
public:
    inline static int destroyed=0;
    ~Derived() override { ++destroyed; }
};
int main() {
    { std::unique_ptr<Base> p=std::make_unique<Derived>(); }
    assert(Derived::destroyed==1);
    std::vector<int> v{7};
    const auto capacity=v.capacity();
    while(v.size()<capacity) v.push_back(0);
    const auto index=std::size_t{0};
    v.push_back(9); // 必须扩容，随后通过下标重新访问
    assert(v[ index ]==7 && v.capacity()>capacity);
}

编译告警可启用 -Wall -Wextra -Wnon-virtual-dtor -Wdelete-non-virtual-dtor，再结合 clang-tidy 的 cppcoreguidelines-virtual-class-destructor。相关告警/检查主要针对多态类；原例若根本没有虚函数，不能假定工具一定诊断。代码评审仍需确认基类是否承担销毁接口。

经典问题：CI 中没有告警、ASan 没报告，就证明安全吗？

不能。静态检查有适用模式，动态检查只覆盖执行路径。应同时保留明确的接口约束、触发故障的回归用例，以及分配和释放次数等不变量断言。

参考：clang-tidy：虚析构检查。

5. 长期增长与监控开销

设计固定业务循环：基线 → 执行 N 次 → 等待任务结束 → 清理可清理缓存 → 再采样。比较多轮同阶段的存活量与引用链，不用单次峰值直接判泄漏。短期可达但业务上不再需要的对象，也可能是需要修复的长期持有。

  • 监控线程会占用栈、调度时间和 CPU；高频采集调用栈、扫描映射或争用分配器锁都会增加开销。
  • 对照启用/关闭监控的吞吐、延迟分位数、CPU 和内存；固定采样频率并记录丢样，避免监控改变原故障时序。
  • 堆转储用来查对象与引用关系；native 分配采样用来查分配热点。Android 的 Java heap dump / HPROF 不能替代所有 native 或图形内存的诊断。
