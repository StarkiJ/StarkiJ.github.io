ART 编译与启动

区分解释、JIT、AOT、profile 与 dex2oat，并连接 Zygote 和应用启动。

1. DEX、解释执行与编译代码

DEX 保存 Android 运行时使用的字节码及相关信息；ART 负责类加载、执行、对象管理和运行时服务。同一应用的方法可以处于解释、JIT 编译或 AOT 编译状态，不是每次启动都只能选一种执行方式。

执行方式
方式收益成本
解释无需先为所有方法生成本机代码反复解释热点指令有成本
JIT按运行热点生成代码并利用运行信息占用应用运行期间的 CPU、代码缓存与元数据
AOT提前生成可复用机器码编译耗时、磁盘体积；可能编译并不热的方法

运行时还需要在解释帧、编译帧和 native 调用间转换。编译代码依赖相应检查、类状态和 GC 协作信息，不是与运行时脱离的一段裸机器码。

2. 热点、Profile 与 dex2oat

  1. 执行 DEX 或已有代码，采集方法热度、分支/类型等适用信息。
  2. 达到策略条件时安排 JIT 编译；生成代码与必要元数据，放入代码缓存并更新调用入口。
  3. 将可用 profile 信息持久化，供后续基于 profile 的编译决策使用。
  4. 系统在适当时机调用 dex2oat 等编译流程，根据过滤器/profile 选择工作，产生相应的验证、优化和编译产物。

dex2oat是 ART 的编译工具链组成部分，按配置加载和处理 DEX、执行验证/优化并生成相应输出。oat 文件不保证包含每个方法的机器码，也不能用后缀简单断定“全部已经 AOT”。系统版本会改变编译调度与产物细节。

代码缓存回收处理 JIT 机器码及关联 profiling 等数据的生命周期与空间压力；Java 堆 GC 处理对象可达性。两者可有关联，但不是“清空 JIT 缓存就能回收 Java 堆”。

经典问题：“JIT 预编译”通常需要怎样澄清？

如果指运行前依据已有 profile 生成机器码，那更接近 profile-guided AOT；如果指在运行中提前安排将使用的方法编译，则仍是运行时策略。应明确生成时间、输入信息和代码保存位置。

参考：ART JIT 与 profile 流程 · ART 配置与编译过滤器。

3. Zygote、fork 与应用启动

典型 Android 启动主线是引导加载器 → 内核 → init → 启动 Zygote 等服务 → system_server 的系统服务初始化。应用进程通常从 Zygote 派生，再完成身份/运行环境配置，进入应用运行入口、绑定应用并执行相应组件生命周期。不同启动路径与预创建进程策略会改变细节。

Zygote预加载可复用的类和资源。fork 后父子私有映射起初可用写时复制共享物理页：读取共享，写入相关页时才形成私有副本。共享的是页级存储效果，父子不是持有同一个可随意共同修改的 Java 堆。

Framework 提供组件、窗口、包管理、进程管理等系统能力；应用通常经 Binder 与 system_server 等进程协作。zygote 预加载、类初始化、Binder 调用与首帧渲染分别可能成为启动耗时来源。

经典问题：fork 是否立刻复制 Zygote 中的全部数据？

通常不会逐字节立即复制全部私有页。页表与进程状态需要建立，原数据页可按写时复制共享；后续写入越多，私有化越多。具体还要看映射类型与启动实现。

参考：AOSP Zygote · Linux fork。

4. 启动优化与验证

降低 JIT 阈值可能更早优化热点，也可能抢占启动关键路径资源；提高阈值则可能延长解释执行。profile/AOT 可以把一部分成本移到执行前，但仍有包体、编译和存储代价。

  • 区分冷启动、温启动、热启动，固定 profile、编译状态、设备温度和后台负载。
  • 记录首帧/完全可用耗时、主线程阻塞、CPU 调度、JIT 编译时段、GC 暂停和内存峰值，不能只报平均总时间。
  • 用 Perfetto 等时间线工具关联事件，再针对一项策略做对照。应用侧可减少主线程工作、延迟非必要初始化并使用适用的 baseline profile。

ADB 是与 Android 设备通信和执行调试操作的工具。基础只读入口包括 adb logcat、adb shell dumpsys meminfo 包名；具体服务输出、权限和命令随系统而异。使用编译/清理 profile 命令会改变实验状态，应明确记录。

经典问题：热点统计应选择什么数据结构？

通常可把计数与状态放在方法关联元数据中，结合调用/回边计数或采样，降低查表和同步开销；编译队列要去重，计数可饱和。真实字段、阈值和队列实现需对照目标 ART 分支。
