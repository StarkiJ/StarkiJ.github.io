1. DEX 与方法执行状态

DEX 保存 Android 运行时使用的字节码及相关信息；ART 负责类加载、执行、对象管理和运行时服务。同一应用的方法可以处于解释、JIT 编译或 AOT 编译状态，不是每次启动都只能选一种执行方式。

解释、JIT、AOT 的公共机制与成本见动态编译；DEX 虚拟寄存器与 JVM 操作数栈见共同执行基础，内存职责见运行时内存全景。这里关注 ART 如何为方法选择可用入口，以及编译状态怎样进入后续启动分析。

1.1 构建工具、DEX 与运行时分别做什么

ART optimizing 编译器如何表示方法、处理 SSA 并分配机器位置，见HGraph 实例与寄存器分配手推；这里继续讨论何时编译以及产物如何用于启动。

Java / Kotlin 源码
  → javac / Kotlin JVM 编译器产生 JVM 字节码
  → 按构建配置经 D8 或 R8 的处理路径
      D8：转为 DEX，并处理适用的语言特性降级
      R8：裁剪、优化、混淆并输出 DEX 等产物
  → APK / 分包中的 DEX
  → ART 加载、验证、解析，按可用入口解释 / JIT / AOT 执行

这里画的是职责路径，不是每次构建都顺序跑完 D8、R8 再 dex2oat。R8 属构建时优化，ART JIT 属设备运行时编译；减少 APK 中的代码与缩短某个热点方法的执行时间不是同一个指标。反射、JNI 注册和按名字访问的成员需要正确的保留规则，不能只依据静态直接调用图判断是否可删除。

类身份、初始化与方法分派统一见托管运行时基础；本篇不重新建立一套 Android 专属的语言基础。系统实例以 Android 14 为参照，构建与测量还要记录 AGP、R8、Profile 与 Benchmark 工具版本。

参考：D8 · R8 构建优化。

2. Profile、dex2oat 与编译产物

2.1 热度采集与编译调度

  1. 执行 DEX 或已有代码，采集方法热度、分支/类型等适用的运行时反馈；哪些信息持久化见下文 Profile 分类。
  2. 达到策略条件时安排 JIT 编译；生成代码与必要元数据，放入代码缓存并更新调用入口。
  3. 将可用 profile 信息持久化，供后续基于 profile 的编译决策使用。
  4. 系统在适当时机调用 dex2oat 等编译流程，根据过滤器/profile 选择工作，产生相应的验证、优化和编译产物。

2.2 dex2oat 与编译产物

dex2oat是 ART 的编译工具链组成部分，按配置加载和处理 DEX、执行验证/优化并生成相应输出。oat 文件不保证包含每个方法的机器码，也不能用后缀简单断定“全部已经 AOT”。系统版本会改变编译调度与产物细节。

2.3 编译代码与 Profile 生命周期

编译代码与 profiling 数据也有生命周期；代码缓存回收与 Java 堆对象的 GC 分属不同管理对象。ART 的字段、阈值、调度与产物细节应对照目标分支。

参考：ART JIT 与 profile 流程 · ART 配置与编译过滤器。

“采集反馈 → 保存 profile → 根据 profile 编译”不是原样序列化所有内部数据。也不能把代码缓存清理、本地 profile 清理与卸载应用当成完全等价的实验重置。Baseline 与 Startup Profile 可配合，但分别验证提前编译和文件布局的作用。

2.5 编译产物、过滤器与有效性

不能仅凭文件后缀判断执行方式
表示职责
DEX字节码与相关类型 / 成员信息，是解释和编译的输入

Android 14 常见过滤器中，verify 侧重验证，speed-profile 根据可用 profile 选择编译，speed 更广泛地编译适用代码；不是三个固定耗时或性能等级。dexopt 是设备侧优化工作，dex2oat 是其中使用的编译工具；系统构建侧的 dexpreopt 又是另一种生成时机。

复用产物还要核对输入 DEX、指令集、相关启动映像及类加载器上下文等条件。构建时看到的依赖类与运行时实际加载环境不一致时，不能把已有文件直接当成可用优化结果；具体回退、重新验证或编译行为由版本和调度决定。排查应同时记录编译原因、过滤器、profile 来源和失配日志。

参考：ART 产物与过滤器 · 编译与运行时类加载器上下文 · Baseline / Cloud Profile · Startup Profile 与 DEX 布局。

3. 应用启动中的运行环境与编译状态

3.1 启动路径与方法执行

应用进程通常从 Zygote 派生，再完成运行环境配置、绑定应用并执行相应组件生命周期。这里关注应用启动路径上的执行成本：哪些方法需要解释，哪些已有可用编译代码，以及启动期间是否发生 JIT 编译。

3.2 Zygote 预加载与写时复制

Zygote预加载可复用的类和资源。fork 后父子私有映射起初可用写时复制共享物理页：读取共享，写入相关页时才形成私有副本。共享的是页级存储效果，父子不是持有同一个可随意共同修改的 Java 堆。

3.3 编译状态与启动成本

预加载与写时复制解释了应用进程如何复用已有运行环境；方法采用解释、JIT 还是 AOT，则决定相应代码的执行与编译成本。已有 profile 可指导提前编译；启动期间的 JIT 可能减少后续解释成本，也会占用 CPU。分析时还要分开观察类初始化、Binder 调用与首帧渲染，避免把全部启动耗时归因于编译。

经典问题：fork 是否立刻复制 Zygote 中的全部数据？

通常不会逐字节立即复制全部私有页。页表与进程状态需要建立，原数据页可按写时复制共享；后续写入越多，私有化越多。具体还要看映射类型与启动实现。

参考：AOSP Zygote · Linux fork。

4. 启动优化与验证

4.1 JIT 阈值与提前编译的取舍

降低 JIT 阈值可能更早优化热点，也可能抢占启动关键路径资源；提高阈值则可能延长解释执行。profile/AOT 可以把一部分成本移到执行前，但仍有包体、编译和存储代价。

4.2 启动指标与对照验证

  • 区分冷启动、温启动、热启动，固定 profile、编译状态、设备温度和后台负载。
  • 记录首帧/完全可用耗时、主线程阻塞、CPU 调度、JIT 编译时段、GC 暂停和内存峰值，不能只报平均总时间。
  • 用 Perfetto 等时间线工具关联事件，再针对一项策略做对照。应用侧可减少主线程工作、延迟非必要初始化并使用适用的 baseline profile。

参考：Android 启动性能。

4.3 一次可以复查的启动对照

以下是实验设计，不是本项目的实测性能结论。以同一真机、同一业务入口和同一 release 构建为基础，用 Macrobenchmark 管理编译状态和启动模式，保存每次的 Perfetto trace；可调试构建的成本不能直接当作发布表现。

先比较编译状态，再比较布局
组控制方式回答的问题
A：无预编译基线按工具支持使用 CompilationMode.None，固定重置和启动模式；JIT 仍可能发生缺少提前编译时关键路径的成本
B：要求 Baseline ProfilePartial 并要求有效 Baseline Profile，固定额外预热迭代设置；规则未生效应暴露失败同一代码和入口下，规则覆盖是否带来收益
C：广泛预编译对照按工具能力使用 Full，记录编译状态更多代码提前编译后的对照；不假设它必然最优
D：Startup Profile 布局单独构建仅改变相应布局输入的可比产物，保持 B 的编译 / 测量条件布局的增量收益，避免与编译收益混算
  1. 固定设备、系统、构建、数据规模、入口与测量工具版本；控制温度、电量策略和后台负载。
  2. 分别报告冷 / 温 / 热启动。冷启动通常需要新进程，但文件页缓存未必冷；JIT 预热与 Android 热启动不是同一分类。
  3. 采集 TTID（首次显示）与适用的 TTFD（完全绘制，需正确报告），同时检查主线程、Binder、类初始化、I/O、JIT 与 GC 时间段。
  4. 重复多次并交错安排对照，比较中位数和尾部波动、失败样本、CPU 与内存；解释 Profile 未命中或变化无收益的情形。

若 B 的 JIT 时间下降却首帧无明显改善，应检查关键路径是否主要在 I/O、锁或渲染。若 D 收益不稳定，要检查真实启动入口覆盖、布局是否生效以及页缓存条件。不要根据一次更快的启动直接降低全局 JIT 阈值。

参考：Macrobenchmark · CompilationMode 的重置与编译语义 · 启动类型与 TTID / TTFD。
