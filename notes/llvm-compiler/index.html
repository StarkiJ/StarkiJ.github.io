范围与实现边界

本篇用 LLVM IR 说明控制流、SSA、优化和代码生成。LLVM 专属规则以 LLVM 22.1.0 文档为参照；ART 和 HotSpot 的运行时编译分别见ART与JVM 与 HotSpot。

IR、优化与代码生成

本部分主要用到机器调用与寄存器约束；CFG 与 SSA 在本部分定义，托管类加载不是通用编译原理的统一前置。

先把程序表达成便于分析的控制流与数据流，再讨论变换的正确性和目标机器约束。词法、语法与语义分析在这里作为流程概览，重点是 IR、SSA 和代码生成。

编译阶段与中间表示

从源码到机器码
阶段输入 → 输出主要任务
词法分析字符 → token识别标识符、关键字、字面量等
语法分析token → AST按文法建立结构，报告语法错误
语义分析AST → 带类型/绑定信息的表示名字查找、类型检查、作用域与转换
IR 生成与优化高层结构 → 中间表示显式表达控制流、数据依赖与内存操作
代码生成IR → 目标指令指令选择、寄存器分配、调度与目标约束
汇编与链接汇编/目标文件 → 可执行程序或库编码指令、解析符号与重定位

AST保留源程序语法结构；IR为分析和变换提供规则更统一的表示。同一编译器可以有多层 IR，从接近语言语义逐步降低到机器指令。汇编器主要完成目标指令编码；解释器直接执行某种表示的语义，不必先生成本机代码。

record/结构体需要字段类型、偏移、大小与对齐规则；类继承还涉及基类子对象、访问与动态分派。先确定语言语义，再按 ABI 降低到布局和地址操作，不能仅把每个字段按字节相加。

基本块与控制流图

基本块是一段从入口顺序执行到结尾转移的指令序列；中间没有控制流跳入。CFG以基本块为节点，以可能的控制流转移为边。

  1. 在线性三地址码中，把第一条指令、跳转目标和转移指令后的新指令标为块首。
  2. 相邻块首之间构成基本块；以跳转、条件分支、返回等确定终结。
  3. 按各终结指令建立后继边，构造前驱列表；异常控制流也要按 IR 模型纳入。

条件分支通常有两个后继，返回没有普通后继。不能仅按花括号切块：短路逻辑、循环与异常处理都可能产生额外边。

从 CFG 计算支配与活跃性

对可达块，入口只被自己支配；其他块的支配集合可初始化为全部可达块，再反复计算 Dom(B) = {B} ∪ ∩ Dom(P)，P 为 B 的前驱，直到不再变化。菱形 CFG 的两条分支互不支配，合并块的共同支配者可以只有入口与自己。

entry → left  → merge
      → right → merge

Dom(left)  = {entry, left}
Dom(right) = {entry, right}
Dom(merge) = {entry, merge}

源变量 v 分别在 left / right 定义，merge 使用：
  需要把各路径值汇合，后面的 SSA 例子用 phi 表达。

活跃性问的是“这个值以后是否还会在被覆盖前使用”。在非 SSA 的块级模型中，可迭代计算 OUT[B] = ∪ IN[S]、IN[B] = USE[B] ∪ (OUT[B] − DEF[B])；USE 指块内先使用后定义的值，S 为后继。SSA 的 phi 输入使用发生在前驱边上，不能把所有输入都当作合并块同时需要的普通使用。

支配帮助判断某定义是否覆盖所有到达路径；活跃性帮助决定哪些值必须保留、哪些值能共用寄存器。两种分析都不直接证明内存没有别名。

SSA 与 phi

SSA（静态单赋值）要求每个 SSA 值只有一个定义。源变量反复赋值时使用不同版本；控制流合并处用 phi 根据实际前驱选择对应版本。它不是同时执行所有分支，也不是求平均。

define i32 @choose(i1 %cond, i32 %x) {
entry:
  br i1 %cond, label %yes, label %no
yes:
  %a = add i32 %x, 1
  br label %merge
no:
  %b = sub i32 %x, 1
  br label %merge
merge:
  %result = phi i32 [ %a, %yes ], [ %b, %no ]
  ret i32 %result
}

支配：从入口到 B 的每条路径都经过 A，则 A 支配 B。支配边界描述某定义可能与其他路径定义相遇的合并位置。经典 SSA 构建先计算支配关系，在迭代支配边界放置 phi，再沿支配树用版本栈重命名定义与使用；可结合活跃性省掉无用 phi。

经典问题：SSA 是否表示内存永远只写一次？

不是。SSA 约束 IR 值名的定义；store 仍可反复修改内存。对内存的依赖分析需别名分析或 MemorySSA 等额外表示，不能把不同 load 的结果直接视为恒等。

参考：LLVM phi 语义 · LLVM MemorySSA。

循环里的 phi：静态一次定义，动态反复执行

循环头有入口边和回边，phi 合并初始值与上一轮结果。以下函数累加 0..n-1，演示 phi 的控制流语义；示例输入前提为 n 非负且数学结果能放入有符号 i32。这是便于演算的数值范围，不是 ABI 调用约定；代码中的普通 add 未附加 nsw / nuw，溢出时按位宽回绕。

define i32 @sum_to(i32 %n) {
entry:
  br label %loop
loop:
  %i = phi i32 [ 0, %entry ], [ %next, %body ]
  %sum = phi i32 [ 0, %entry ], [ %updated, %body ]
  %more = icmp slt i32 %i, %n
  br i1 %more, label %body, label %exit
body:
  %updated = add i32 %sum, %i
  %next = add i32 %i, 1
  br label %loop
exit:
  ret i32 %sum
}

n=3 时，进入循环头的 (i, sum) 依次为 (0,0) → (1,0) → (2,1) → (3,3)，最后返回 3。%i 只有一处静态定义，但该定义可以动态执行多次；“循环变量会变化，所以不能是 SSA”混淆了静态程序与动态执行。

在 LLVM IR 中，phi 必须集中在基本块开头，输入成对标明值与前驱；输入值的使用发生在对应边上。因此 %updated 只需在 body→loop 的边上可用，不需要在 entry→loop 的边上也有定义。同一块的多个 phi 同时选择对应边的输入。

phi、select 与优化收益

phi 按实际进入的前驱选值；select 按显式布尔条件从已可用的操作数中选值。把分支改成 select 时，不能随便把原本只在一个分支执行的可能抛异常、越界或有副作用的计算提升到公共路径。phi 通常在后端转成边上的复制或经寄存器合并消失，不要求 CPU 有名为 phi 的指令。

SSA 使定义—使用关系明确：沿值的唯一来源做常量传播，按使用关系删除死值，检查支配与别名后复用计算。它不会自动解决别名、内存依赖或正确性问题；“SSA 就等于更少寄存器”也不成立，寄存器压力还要看活跃区间。

面试追问：面试要求手工构建 SSA，按什么顺序？

先画 CFG 并标入口、回边与合并块；算支配关系，在需要汇合多个定义的迭代支配边界放 phi；沿支配树重命名定义与使用，给每条前驱边填入对应版本；最后去掉无用或输入相同的 phi。循环头的回边输入不要漏填。

ART 的图表示见HGraph 实例。

phi 消除与寄存器分配

降低 SSA 时，可把 v = phi(a from A, b from B) 变成在边 A→合并块上执行 v←a、边 B→合并块上执行 v←b。若前驱有多个后继而目标有多个前驱，直接把复制放任一块可能在错误路径执行，应按需要拆分临界边。

同一条边上的多项复制具有并行语义。交换 a、b 不能依次执行 a←b、b←a，否则第二步读到已覆盖值；可用临时 t：t←a、a←b、b←t。寄存器合并可以消掉一部分复制。

虚拟寄存器是编译器表示中的值位置，不受硬件寄存器数量直接限制。分配器按活跃区间与干涉关系映射到物理寄存器；位置不足时 spill 到栈并插入 load/store。调用约定、寄存器类别和保存成本也属于约束。

线性扫描：按活跃区间起点分配

经典 linear scan 把程序位置线性编号，按区间起点遍历，维护按结束位置排列的 active 集合。处理新区间前释放已结束区间的寄存器；有空位就分配，没有空位则选择 spill。下面采用“比较结束位置，优先移出结束最晚的区间”的教学策略；真实实现可按使用位置拆分区间、处理空洞并估算溢出成本。

两个同类寄存器 R1、R2；半开区间 [start, end)：
a = [0, 8)    b = [1, 3)    c = [2, 6)    d = [6, 9)
位置 2 同时活跃 a、b、c，两个寄存器无法容纳三个值。
位置 6 的 c 已结束，因此 c 与 d 不干涉。
按起点扫描与选择溢出
到达位置处理分配后状态
0：a 开始取空闲 R1a→R1
1：b 开始取空闲 R2a→R1，b→R2
2：c 开始a 在 8 结束，比 c 的 6 更晚；选择 a 溢出c→R1，b→R2；a 的值须保存到栈
6：d 开始b、c 已结束，释放其寄存器d 可取 R1；a 后续使用需 reload

这个表是在手算区间的分配决定。实际生成代码时要在覆盖寄存器前保存仍需使用的值，并在使用前重载；重载产生的短临时区间也要满足指令约束。分裂区间的实现可保留 a 的前段寄存器位置，整段溢出的简化实现则重写其定义与使用；不能只把分配表中的 a 改成“栈”就认为机器码已经正确。

参考：Poletto、Sarkar：Linear Scan Register Allocation。

图着色：不能共用寄存器的值连边

干涉图的节点代表待分配的值，边表示两值不能占用同一个寄存器。用 K 个颜色代表 K 个可用同类寄存器：相邻节点必须不同色。对上面的区间，边为 a—b、a—c、a—d、b—c；其中 a、b、c 构成三角形，所以 K=2 时不可能全部留在寄存器中。

  1. Simplify：反复删除度数小于 K 的节点并压栈。先删 d，它只有邻居 a。
  2. 选择候选：剩余三角形没有度数小于 2 的节点。为与前例对照，这里选 a 为潜在 spill 候选，暂时移除；真实选择还应看使用频率、循环和代价。
  3. 继续简化：剩下 b—c，可依次压栈 b、c。
  4. Select：逆序恢复：给 c 分 R1，b 分 R2；恢复 a 时两个颜色都被邻居占用，确实需要 spill。d 恢复后可分 R1。
  5. 重写与重试：为 a 加入必要的栈存取，重新分析新增短区间与干涉，再完成分配。

“度数大于等于 K”本身不证明必须 spill：某些图仍可着色，乐观着色允许候选在恢复时找到颜色。本例必须溢出的证据是三角形需要三个颜色。复制合并还能减少 move，但若合并引入过多干涉，也可能增加溢出；实际算法要处理预着色寄存器、寄存器类别及目标指令限制。

线性扫描通常较容易控制编译开销，图着色显式处理全局干涉；不能把名称直接等同于“一个总快、另一个生成代码总好”。具体后端如何选择分配器，须看目标与配置。

参考：Appel：带预着色节点的分配示例。

经典问题：把所有 phi 换成合并块开头的普通 move 可以吗？

不可以。合并块必须知道来自哪个前驱才能选择输入；无条件顺序执行所有 move 会取错值。复制必须放到对应路径，并处理并行复制冲突。

参考：LLVM 代码生成。

从值运算到目标指令

目标 lowering 还要处理硬件支持的类型、指令寻址和调用约束，之后才能分配寄存器、安排指令顺序。调度可重排独立工作以隐藏延迟，但必须保留数据依赖、内存顺序与必要的异常语义。

Java：static int tripleSum(int a, int b) { return (a + b) * 3; }

等价的 i32 值运算（不附加“不会溢出”的标记）：
  t = add a, b
  r = mul t, 3
  return r

一种按基础 AAPCS64 传参的 AArch64 运算示例：
  add w0, w0, w1
  add w0, w0, w0, lsl #1
  ret

第二条指令把 t 与 2t 相加；这里都保留低 32 位，符合该 Java int 运算的回绕语义。本示例另约定按基础 AAPCS64 在 w0/w1 接收 a/b，并从 w0 返回结果；它展示运算如何降低到机器指令，不代表 HotSpot 或 ART 实际编译该 Java 方法时使用这套入口。VM 的托管调用约定与 native ABI 需要通过适配代码衔接。

a 最后一次使用后 w0 可承载 t，再承载返回值。指令选择消除了显式乘法，不代表所有处理器上它一定更快；这里只验证运算语义与所指定的位置安排。

参考：JDK 21 AArch64：Java 与 C 调用约定及适配。

跨调用活值为什么需要保存

概念 IR：
  t = a + b
  r = call opaque()
  return t + r

一种 AAPCS64 保存方案（省略展开指令等汇编元数据）：
  stp x19, x30, [sp, #-16]!
  add w19, w0, w1
  bl opaque
  add w0, w19, w0
  ldp x19, x30, [sp], #16
  ret

t 跨调用仍活跃，不能只留在允许 opaque 覆盖的 w9。这里让 w19 保存 t，同时保留调用者原来的 x19 与返回位置，栈仍满足对齐。也可选择 spill 槽，在调用后 reload；寄存器不足时要综合活跃区间、寄存器类别、调用频率和保存成本。spill 是值的位置变化，不是创建新的语言层对象。

优化的前提与代价

常见优化
优化变换必须确认的前提
常量传播 / 折叠用已知值替代计算值确实确定，遵守目标语义与溢出规则
死代码删除删除不影响可观察行为的计算无需要保留的副作用、异常或 volatile 访问
公共子表达式消除复用已有计算结果操作数相同，相关内存未被可能的别名写入改变
循环不变量外提把不随迭代变化的计算移到循环外依赖、异常与执行条件允许移动
内联 / 去虚拟化展开调用或确定调用目标目标可确定，收益超过代码膨胀与编译成本
向量化一次处理多个数据元素依赖、别名、对齐与浮点语义允许

优化后的快慢需结合真实输入与热点衡量。浮点结合律通常不能像实数一样任意重排；C++ UB 也会影响编译器可以采用的推理，不能用“硬件会回绕”代替语言规则。

有两个相同 load，为什么不一定能合并

前提：p / q 有效，访问普通非 volatile 内存
a = load p
store q, 9
b = load p
return a + b

若 p 与 q 指向同一位置，第二次读取应看见 9；把 b 无条件替换成 a 会改变结果。只有证明写入不影响 p、没有其他相关干扰等条件，才可能复用。MemorySSA 用 MemoryDef、MemoryUse、MemoryPhi 表达内存依赖候选关系；结合别名分析查可能覆盖的写入，不是把每个内存字节变成永不修改的 SSA 变量。

类似地，循环不变量外提不仅看操作数不变。循环可能执行零次时，把原本位于循环里的可能故障的 load 或有副作用的调用移到入口，可能凭空增加一次访问。需要证明可安全提前执行，或保留必要的执行条件。

LLVM 的表示、优化与目标生成

前端、LLVM 与目标代码的职责

Clang 等前端处理源语言语法与语义，产生 LLVM IR；LLVM 的优化与目标生成组件处理 IR 并生成目标代码。前端须把语言规则正确表达在 IR 中，后续变换也必须遵守 IR 的语义。ART HGraph 和 HotSpot C1/C2 各有自己的表示与实现，不能因都使用 SSA 就视作 LLVM IR。

阅读 LLVM IR 时检查什么

先看函数签名、类型、基本块和终结指令，再沿定义—使用关系追踪 SSA 值。phi 按实际前驱边选择值；load、store 与调用还涉及内存效果，单靠 SSA 值名不能证明两次访问等价。整数运算的溢出标志、指针与别名约束会影响允许的优化；示例须注明输入前提。

一个 module 可以含函数、全局对象和目标信息；函数内的基本块以分支、返回等终结指令结束。i32 表示 32 位整数，ptr 表示不在指针类型中编码被指对象类型的指针；访问时仍要根据 load、store 等指令指定操作类型。IR 的文本形式便于阅读，二进制 bitcode 则是另一种序列化形式。

普通 add i32 按位宽计算；加上 nsw 会把有符号溢出纳入更强的语义约束。优化器不能仅因为“数学上应该不溢出”就自行假定该标志。poison 等值的传播与使用也有规则，不能把所有未定义情况简化为一个任意整数。

参考：LLVM 22.1.0 IR 语义 · MemorySSA。

优化 pass 与可观察结果

一个 pass 可分析或变换 IR，例如传播常量、删除无用计算、整理控制流或循环。变换结果受目标信息、优化级别、pass 顺序以及程序可证明的语义约束影响。检查优化前后的 IR，并核对函数行为和前提，比背诵某优化级别必然产生哪条指令更可靠。

Pass 可以按 module、函数、循环等处理单位组织。分析结果如支配树可以供变换使用；改变控制流后，pass 须报告哪些分析仍有效，让管理器重新计算失效结果。LLVM 22.1.0 的中端流水线使用新 pass manager，目标代码生成仍有自己的管理机制；两者不能仅因都叫 pass 就当成相同的执行层。

参考：LLVM 22.1.0 New Pass Manager。

从 IR 降到目标指令

目标生成需要把 IR 操作映射到目标支持的指令与调用约定，处理合法化、指令选择、寄存器分配及机器级安排。源级变量、IR 值和物理寄存器不存在固定的一对一关系；最终汇编仍需结合目标架构和 ABI 阅读。

参考：LLVM 22.1.0 代码生成。

一个可复查的 IR 对照

下载与前文 choose 与 sum_to 一致的 IR 示例文件，安装 LLVM 22.1.0 后在文件所在目录运行：

llvm-as ir-examples.ll -o ir-examples.bc
opt -S -passes=instcombine ir-examples.bc -o ir-examples.opt.ll
llc -mtriple=x86_64-pc-linux-gnu ir-examples.opt.ll -o ir-examples.s

对照原始 .ll、优化后的 .opt.ll 与目标汇编 .s，观察合并块的 phi 在 IR 优化或目标生成中如何处理。记录工具版本、目标三元组和 pass 设置；输出取决于目标和流水线，本篇不预设某条固定汇编指令。

llvm-as 负责文本 IR 到 bitcode；opt 运行 IR 分析和优化；llc 将 IR 或 bitcode 编译为目标汇编。三者回答的问题不同，目标汇编还需要汇编、链接等步骤才能形成可执行程序。

参考：llvm-as · opt · llc。
